# Live sessions — presence, access loss, watching, recording, command rules

- **Console session events (`session_audit.rs`; test `tests/session_events.rs`):** the web terminal, file manager and remote browser write `terminal_open` (`lan_terminal` for a LAN hop) / `files_open` / `browser_open` when a session starts and `terminal_close` / `files_close` / `browser_close` with the duration ("… closed after 12m03s (session <id>)") when it ends, into the tunnel's gateway events (Logs, badges `logs.event.*`); remote desktop has its own `desktop_open` / `desktop_close`. `util::fmt_duration` formats the durations.
- **Presence — who is using a tunnel (`presence.rs`; test `tests/presence.rs`):** in-memory registry; every live session holds a `PresenceGuard` (drop = leave; handlers drop it as soon as their loop ends, before the teardown; dead browsers are caught by the WS heartbeat, a dead laptop by the gateway's SSH keepalive): web terminal / file manager / remote-browser WS (IP from `ClientMeta` at the upgrade), a laptop's ssh through the gateway (user-key `direct-tcpip`, IP = gateway peer) and an AI session (`AiSession._presence`, IP = the MCP request's, client = app name). Changed tunnels are marked dirty; `monitor::runner::dispatch_presence` (1 s loop) pushes `UPDATE-TUNNEL-PRESENCE {tunnel_id, count}` to owner + sharees. List items carry `presence {count, sessions}`: the count (distinct users) for everyone, `sessions [{user, kind, ip, since, client}]` only for owner / ADMIN / superuser (`permissions::can_see_presence_details`; other users' IPs can't be learned from the device, so this is stricter than `endpoint`). Frontend `TunnelPresenceButton` (a "N using" button beside the access badges; a click opens a popover — sessions grouped per user, identical kind + IP + app folded into ×N, scrolling inside the popover with a "More below" cue so the list never grows; count-only viewers get a one-line note); the page updates the count from the notification and quietly reloads when it can see details. The MCP middleware stores the client IP on `McpPrincipal.ip`; `telepy_ai_audit_event.ip` records it (shown on the AI activity page).
- **Live sessions — see and end them (`api/sessions.rs`; test `tests/live_sessions.rs` on the SSH lab):** every presence entry has an `id` and can be ended: `Presence::end(id, by)` signals the connection, whose loop waits on `PresenceGuard::ended()` in its `select!` — web terminal (incl. LAN), file manager, remote-browser and desktop sockets close with **4009** and the reason = who ended it; a laptop's ssh through the gateway has its `direct-tcpip` bridge dropped (the ssh is cut at once); an MCP agent session is closed as `closed_by_user`. `GET /api/sessions` lists your own sessions plus everyone's on tunnels you own or ADMIN (`?scope=mine`, the default — admins too; `scope=all` = everything, admins only; ending / watching still follow the permission, so admins may end any) with tunnel, user, kind, IP + geo, since, client, `mine`; `DELETE /api/sessions/{id}` ends one under the same rule (404 otherwise), notifies that user (`SESSION-ENDED {tunnel_id, kind, by}`) and writes a `session_ended` gateway event. Ending is not revoking: they can reconnect. Frontend: `/tunnels/sessions` (nav "Live sessions", mine) and `/tunnels/admin/sessions` (admin section, all, + a user filter; Watch adds `&from=admin` so the watch page's back link returns there), one `components/sessions/LiveSessionsView.tsx` with `scope` (`hooks/useLiveSessions.ts` refetches on presence / AI-session / SESSION-ENDED notifications and every 15 s; filters kind / tunnel (`?tunnel=`) / mine, pure helpers in `lib/liveSessions.ts`), the presence popover's "Manage sessions" link, `components/layout/SessionEndedNotice.tsx` (toast on any page), 4009 is non-retryable (`lib/wsCommon.ts`) and the terminal / LAN terminal print who ended it; copy under `sessions.*`.
- **Access loss ends every kind of session (`access_recheck.rs`; tests `tests/access_loss.rs` (files, laptop SSH, watchers, disabling an account), `*_ends_when_access_is_lost` in `tests/desktop_api.rs` / `tests/rustdesk_api.rs` / `tests/remote_browser_api.rs`, the terminal ones in `tests/terminal_e2e.rs`):** one place decides, for every presence entry of the affected tunnel(s) / user(s), whether its owner still has what that session needs — the pure `lost(SessionView, AccessNow)` (unit-tested): account active → the kind's feature (`Feature::needed_by`, LAN shells also `network`) → terminal / files / remote browser / desktop / RustDesk: VIEW + the account it runs as (`presence::Entry.account`, set at every join; shells from `state.shells.list()`) still allowed, detached shells also the detach policy; laptop SSH: the gateway's own rule `permissions::can_reach_device` (owner / ADMIN / ≥ 1 allowed account; the gateway's `user_can_reach` uses the same function); watchers: still `terminal_watch::may_watch` (owner / ADMIN / superuser). A loss ends the entry through `Presence::end_because(id, ENDED_BY = "Telepy (access changed)", why)`, so each kind's own teardown runs: sockets close 4009 with that reason, the gateway drops the `direct-tcpip` bridge and writes `session_ended` (laptop SSH has no close event of its own), desktop / RustDesk stop (their reapers no longer check access — `revoke_lost` is gone), the remote browser stops its kasm session, and every `*_close` / `terminal_watch_end` event appends `ended by …: <why>` (`PresenceGuard::ended_note`); the person gets `SESSION-ENDED {kind, by, reason: account_disabled|feature_disabled|access_removed|login_removed|detach_off, detached[, feature]}`. MCP agent sessions and agent browsers are skipped there — `crate::ai`'s reaper keeps its own rule (incl. the OAuth grant) and `ai::recheck(tunnel?, user?)` runs it at once for the same scope. Triggers (no second mechanism): `access_recheck::kick(state, tunnel?, user?)` right after unshare / leave / share expiry, a permission or allow-list change, a username rename / delete, a temporary grant ending, the tunnel's detach policy turning `never` and feature writes; `access_recheck::run` (10 s, `main.rs`) catches the rest (group changes, site ceilings). **Disabling an account** (`POST /api/user/users/{id}` `is_active: false`; `access_recheck::account_disabled`): every web sign-in revoked with reason `disabled` (open pages 4010, access tokens refused at once through the revoked-sid cache, a refresh answers 401 `signed_out: disabled`), every live session ended (`account_disabled`) and every MCP agent session closed; personal API tokens and OAuth grants are **suspended, not revoked** (`auth::mcp` refuses a disabled user; they work again after re-enabling, web sign-ins don't); the gateway refuses the account's personal keys. Keys Telepy installed for the account leave the devices (see Device key lists; hand-added lines stay). The response adds `disabled {web_sessions, live_sessions, agent_sessions, api_tokens, connected_apps, device_keys {devices, accounts, offline_devices}}` (`DeviceKeyImpact::count`, pure); `GET /api/user/users/{id}/disable-preview` (admins) gives the same counts beforehand. Frontend: the Manage-user modal's "Account enabled" switch opens `components/users/DisableAccountDialog.tsx` (summary sentence + a device-key sentence (`keysLine`: offline devices lose them when they reconnect) + `DisableImpactMap` on `components/flow/PathFlow`: account ─ browsers ─ live sessions ─ API tokens ─ connected apps ─ device keys, each with count and outcome; pure `lib/accountDisable.ts`, tested), `useUserManagement` toasts what was done, `lib/auth.tsx` explains a `disabled` sign-out, and `SessionEndedNotice` words access changes per kind (`lib/liveSessions.ts` `lostToast`: laptop SSH / watching have their own sentence, plus what the kind needs, `sessions.need.*`); copy under `settings.disable.*`.
- **Terminal watching — moderated sessions (`terminal_watch.rs` = pure `Watchers` state machine (one typist at a time), notice texts, `change_event`, `may_watch` / `may_force`; `ws/terminal_watch.rs` = the watcher socket; the shell side in `ws/terminal.rs` `Shell::on_watch` / `answer` / `revoke`; test `tests/terminal_watch.rs` on the echo-shell lab):** the tunnel's owner, ADMIN sharees and superusers (never on their own shell) watch a web terminal (LAN terminals too) at `GET /ws/terminal-watch/{shell_id}/` (auth frame + optional `step_up`; needs the `terminal` feature (4012; `Feature::for_presence(Watch)` = terminal, `PAGE_FEATURES` gates the page, `shell_id` is only listed with it); unknown = **4015** `shell_gone`, not allowed = 4004, 4008 step-up). The shell id is the detach one (`Shells::watch_target` / `by_presence`; each slot carries an `mpsc::Sender<terminal_watch::Cmd>` the shell's loops — attached and kept — `select!` on, so a detached shell can be watched too). Join is answered inside the shell task (subscribe to the shell's `broadcast::Sender<Frame>` + `LineTracker::screen_formatted()` at one instant): binary `{type:"watch", shell, you, user, tunnel, account, lan_host, size, detached, can_force, recorded, watchers, reset}`, one text frame = the vt100 redraw, then live output (text) and binary `resize` / `watchers` / `detached` / `command` (can_decide forced false); a lagging watcher rejoins (`reset: true`); the shell ending = 4015 `ended`, 4009 / 4010 as usual. Watchers are presence kind `watch` (`Entry.watching {shell, user_id, username}`); `GET /api/sessions` adds `shell_id` (managers, not yours), `watched_by`, `watching`. The watched user is told: a grey `[Telepy] <name> is watching this session.` line (`Shell::announce`: notice + `redraw_cursor_row` so the prompt and half-typed text reappear; skipped in full-screen apps; goes into the backlog, the recording and to watchers), a `watchers` binary frame (re-sent on reattach), `TERMINAL-WATCHED {tunnel_id, tunnel_name, shell_id, by, watching}` and the personal webhook `session.watched` (audience = the watched user). **Control:** watcher `{type:"control", want}` asks / gives back / withdraws, `{type:"control", force:true}` takes it (tunnel owner / ADMIN only — superusers not on the tunnel only ask); the watched user answers `{action:"watch_answer", watcher, allow}` / `{action:"watch_revoke"}` on `/ws/terminal/`; with control the watcher's `pty_input` goes through the same `Shell::input` and **command rules attribute the line to the typist** (`Shell::controller` → `line_requester`). Gateway events `terminal_watch` / `terminal_watch_end` (with duration) / `terminal_control_granted` / `terminal_control_revoked`; the device sees one SSH login. MCP agent shells (`ai/shell.rs`) can't be watched (not in `state.shells`). Frontend: `/tunnels/sessions/watch?shell=<id>` (`hooks/useTerminalWatch.ts`: xterm at the session's size, scaled to fit like `CastPlayer`, keys sent only with control; ask / withdraw / give back / take control with a confirm), the Live sessions row's Watch button + "Watched by" chip + `watch` kind, `components/watch/WatchersBar.tsx` (`WatchersChip` in `TerminalHeader` and the LAN terminal overlay, `WatchRequestBanner` Allow / Deny / shared-control bar next to the command banner), toast in `SessionEndedNotice`, `components/watch/WatchFlow.tsx` + `WatchInfoDialog` (their browser ─ Telepy ─ device with your browser branching straight down from Telepy; states from the pure `lib/terminalWatch.ts` `watchPhase` / `watchSpots`, tested) behind the watch page's and the Live sessions page's info buttons; copy under `watch.*`.
- **Terminal recording (`recording/mod.rs`, `api/recordings.rs`, `db/recordings.rs`; test `tests/terminal_recording.rs` on the SSH lab):** a tunnel with `record_sessions` (owner / ADMIN `PUT /api/reverse/server/{id}/recording {enabled, reauth?}`; turning it off needs `reauth` when you have a factor) records every web terminal session (LAN-host terminals included): the terminal first prints `[Telepy] This session is recorded.`, then `Recorder` writes asciicast v2 — header + `[seconds, "o", output]` and `[seconds, "r", "COLSxROWS"]` — to `DATA_DIR/recordings/<tunnel>/<random>.cast` (flushed every second, capped at 64 MB → `truncated`); **keystrokes are never recorded**. Index rows in `telepy_terminal_recording`; `recording::resolve` only accepts `<digits>/<alnum>.cast`. `GET /api/recordings[?tunnel_id=]` = your own plus everything on tunnels you own / ADMIN (`?scope=mine`, the default — admins too; `scope=all` = everything, admins only; reading / deleting still follow the permission), `GET /api/recordings/{id}/cast` (`application/x-asciicast`, a live one returns what is recorded so far), `DELETE` for managers only (the recorded person can't; 409 while recording). `recording::run` closes recordings a restart left open (length from the last event) and purges hourly per the site setting `recording_retention_days` (default 30, 0 = keep); deleting a tunnel removes its files (`recording::forget_tunnel`). Gateway events `recording_setting` / `recording_deleted`. Frontend: `/tunnels/recordings[?tunnel=]` (nav "Recordings", mine) and `/tunnels/admin/recordings` (admin section, all, + a user filter), one `components/recordings/RecordingsView.tsx` with `scope` (`hooks/useRecordings.ts`), `components/recordings/CastPlayer.tsx` (xterm at the recorded size with the device's terminal look, scaled to fit, play / seek / 1–8×; `lib/asciicast.ts` parses and squeezes pauses over 2 s), `components/tunnels/RecordingSetting.tsx` on the tunnel page's Sessions tab, a "Recorded" card chip and a tunnel-menu item; copy under `recordings.*`.
- **Command rules — block or approve commands (`command_rules/` = `matcher.rs` (pure shell splitting + matching), `line.rs` (vt100 screen reader), `terminal.rs` (input splitting), `mod.rs` (cache, approvals, expiry); `api/command_rules.rs`, `db/command_rules.rs`; tests: unit tests in each module, `tests/command_rules.rs` on the SSH lab with `MachineOpts { echo_shell: true }` (a tty-like fake shell: echo, `$ ` prompt, `ran:<line>` + `Machine::commands()`), `command_rules_block_and_hold_agent_commands` in `tests/mcp_api.rs`):** rules in `telepy_command_rule` are **personal or site-wide, like webhooks** (`scope` user + `user_id` / site; test `personal_rules_cover_picked_tunnels_and_only_me`): anyone writes their own (`POST /api/command-rules`, default `scope: personal`), superusers write site-wide ones (`scope: site`); both cover `all_tunnels` or the tunnels in `telepy_command_rule_target` (≤ 200; the old index name `telepy_command_rule_tunnel` is taken, hence the table name). A personal rule's `who` is everyone / sharees / **me**: everyone / sharees count only on tunnels whose owner or ADMIN the author is **right now** (`matcher::Ctx.managers` = owner + ADMIN sharees, evaluated per check, so losing ADMIN switches it off there without a cache flush; "all tunnels" = every tunnel they manage, later ones too; picking a tunnel you don't manage is a 400 `tunnel_ids`, tunnels already on the rule aren't re-checked while `who` is unchanged), **me = only the author's own commands on any tunnel they use** (a self-guard, e.g. for their own MCP agent on a shared tunnel; approver = the author, no named approvers; hidden from everyone else: other people's lists, `/api/command-requests` (`rule_scope = self`), webhooks to the owner, and the Logs line says "their own rule" without the pattern). Only the author edits a personal rule (403 when it covers a tunnel you see, else 404), only superusers site ones. `GET /api/command-rules` = `{mine, site, can_edit_site, limit, tunnels [{id, name, manage}], approver_candidates, site_approver_candidates, site_tunnels}`; rule JSON adds `scope` site / personal, `owner`, `mine`, `all_tunnels`, `tunnels [{id, name, applies?}]` (only visible ones; `applies` on your own rules), `hidden_tunnels`. `GET /api/reverse/server/{id}/command-rules` (VIEW) = the rules in force there: personal rules of its current managers + your own "only me" ones, plus the site rules covering it; `POST` there = a personal rule limited to that tunnel. Deleting a tunnel deletes the rules limited to it alone and drops it from other lists. Data migration `2026-10-28-personal-command-rules` turned each old tunnel rule into its creator's personal rule for that tunnel (the tunnel owner's when the creator no longer managed it). **Overriding site rules (the user's rule: what only affects you, you may override; a tunnel's owner / ADMIN decides for everyone on it; admins can lock; test `site_rules_can_be_overridden_and_reminders_muted`):** a site rule has `mode` default (overridable; new rules and every pre-upgrade rule) | enforced (🔒; the admin UI shows a "Let people override" switch, on by default). An owner / ADMIN turns an overridable site rule off on tunnels they manage — `PUT/DELETE /api/command-rules/{rid}/off {all_tunnels | tunnel_ids}` (feature `command_rules.manage`; 400 `enforced` / `not_site`; tunnels must be managed; gateway event on each tunnel) — and their own exceptions also exempt overridable site rules there; it counts while they still own / ADMIN the tunnel (`matcher::Ctx.off` from `RuleSet::off_for(managers)`, cached with the rules). **Reminder rules** (`action` warn, "Remind"): the command runs, the terminal shows a `warned` notice (`CommandHoldBanner` with "Mute this reminder"), MCP `ssh_exec` returns `reminder`, `shell_send` `reminders`; nothing is recorded; anyone mutes a non-enforced reminder for themselves (`PUT/DELETE /api/command-rules/{rid}/mute`, `Ctx.muted`). Overrides live in `telepy_command_rule_override` (`kind` off / mute, `all_tunnels`) + `telepy_command_rule_override_target`, dropped with the rule / tunnel. Order per side: block > approve > warn. A rule's own `approval_timeout` (seconds, ≤ the site setting = a ceiling; `approval_timeout_max` in the list) replaces the site wait for its requests. Rule JSON adds `mode`, `approval_timeout`, `my_override {off: {all_tunnels, tunnels} | null, muted}` and, on a tunnel, `off_here [{id, username}]`. Frontend: per-row "Who decides?" → `RuleLayers.tsx` (rule → this tunnel's owner / Admins → you → result, straight lines, chips locked / overrides / follows, the deciding box outlined; pure `lib/commandRules.ruleLayers`), `OffDialog` (all my tunnels / only these), "Off on this tunnel" switch (`flipOffHere`), mute links, the dialog's Remind action, override switch and "Wait for an answer" select. Fields `action` block / approve / warn / allow, `kind` command (program + required arguments: program basename case-insensitive, short flags letter by letter `-rf` = `-fr` = `-r -f`, `*` / `?` globs) / regex (whole line, `regex` crate, 1 MiB size limit), `who`, `via` all / terminal / agents, `note`, `enabled`, `approver_ids`; ≤ 100 per person and site-wide, exact duplicates (same targets too) refused. **Block wins over approve.** **`allow` = an exception that exempts matching commands from the block / approve rules of the same owner only** (site = one owner): a personal allow never overrides a site-wide block, a site allow never overrides a personal rule, one person's allow never overrides another's (so an "only me" allow can't lift the owner's block); `who` / `via` apply to allow rules too; the personal outcome is the strictest owner's, then site and personal combine as block > approve > allowed. `matcher::evaluate(rules, lines, &Ctx {approver, user, managers, source})` returns a `Verdict {site, personal}` (`ScopeVerdict {hit, allowed_by}`, `decision()`, `allowed_by()`); `command_rules::check` returns only the decision, `command_rules::may_apply(tunnel, user)` is the terminal's "any rule for this typist?" fast path. **Per-rule approvers (`approver_ids`, JSON array in `telepy_command_rule`; empty = owner + ADMIN sharees):** only for `action = approve` and not "me" (cleared for others); a personal rule may name only owners / ADMIN sharees of tunnels its author manages (or superusers) and counts per tunnel only the named people who manage that tunnel (or are superusers) — none left = the default; a site rule names any active user (400 field error otherwise; `MAX_APPROVERS` 20); the list **replaces** the default — a site rule's list approves on every tunnel and the owner can't decide (403 `not_approver`). `approvers_for` / `request_approvers` / `decides` are the single source: the request's `approver_ids` snapshot (`telepy_command_event.approver_ids`, in the rule snapshot of `event_json`), `COMMAND-APPROVAL-REQUESTED.approver_ids`, the webhook audience, `can_decide` (list and the terminal's pending notice, so "Run it" shows only for a requester on the list) and `decide` all follow it. `GET …/command-rules` returns `approver_candidates` (tunnel: owner + ADMIN sharees, editors only; site: every active user, superusers only) and each rule carries `approvers [{id, username}]`. The matcher splits a line at `;` `&&` `||` `|` `&` newlines `$(…)` backticks and subshells, drops assignments, keywords and redirect targets, and sees through `sudo` / `doas` / `env` (`-S` too) / `nohup` / `nice` / `timeout` / `xargs` / `watch` / `busybox` / `sh|bash|zsh… -c` / `su -c` / `eval` (wrappers count as commands themselves). `POST /api/command-rules/check {command, tunnel_id?, source?, rule?, scope?}` = verdict for approvers and for sharees, one of them being you (`you_approve`; `action`, `rule` with `owner`, `allowed_by`, per-scope `site` / `personal {hit, allowed_by, exempted}`, `approvers {default, users}` when approval is needed; no tunnel = the site's and your own every-tunnel rules as on a tunnel you manage; `scope: site` = site-wide rules only), the split commands, and whether an unsaved `rule {kind, pattern}` matches (the rule dialog's live test). **Web terminal (`ws/terminal.rs`):** every PTY output byte goes through `LineTracker` (vt100, scroll counter via `on_scroll`); the first key after a reset notes the cursor (= where the prompt ends) and Enter reads from there to the end of the cursor's logical line (completion, history, Ctrl+R and pastes are read as the shell drew them; text after the cursor that is all grey/dim = an autosuggestion and is dropped; a later line starting with the same prompt restarts the read; only echoed text is ever read). `TerminalGuard::split` holds the first Enter that needs a decision (not inside a bracketed paste, not in the alternate screen, not when nothing was typed or the tunnel has no rules) and waits for the echo (`read_at`: 40 ms quiet after output, ≤ 600 ms). Allowed → `\r`; blocked → `\x03` + a `command_blocked` event; approve → a request, keys are dropped while it waits (Ctrl+C or `{action:"command_cancel"}` withdraws), approved → `\r` and the queued input continues, anything else → `\x03`; closing the socket withdraws. The socket tells the browser through **binary** JSON frames `{type:"command", state: blocked|error|pending|approved|denied|cancelled|expired, …}` (pending carries `request` + `can_decide`; outcomes carry `request_id`, `by`, `reason`) — binary frames are no longer only `pong` (`lib/commandRules.parseTerminalFrame`). **MCP `ssh_exec`:** the same check with `source = agent`; blocked = tool error; approve = a request the call waits on for `AGENT_WAIT` (45 s), then "still waiting, run the same command again"; an approved agent request is reused once within 10 min (same grant, tunnel, account, command; `used_at`). **Approvals:** approvers = owner + ADMIN sharees, **including the requester** (an approver's own terminal command shows "Run it" in the banner; their agent's commands still need their click); `telepy_command_event` keeps every block and request (status blocked / pending / approved / denied / cancelled / expired, rule snapshot, `decided_by`, `reason`, ≤ 20k rows, 90 days in `db::retention` because commands can hold secrets); decisions are compare-and-set; pending requests expire after the site setting `command_approval_timeout` (default 300 s, 30–86400; Settings → Command rules tab) through `command_rules::run` (5 s loop; a restart cancels what was pending). `GET /api/command-requests[?status=pending&tunnel_id=&limit=]` (what you decide + your own; superusers see all, but only approvers get `can_decide`), `POST …/{id}/approve`, `…/deny {reason?}`, `…/cancel` (requester). Notifications `COMMAND-APPROVAL-REQUESTED {request, approver_ids}` / `COMMAND-APPROVAL-DECIDED {request}` to approvers + requester. Gateway events `command_blocked` / `command_held` / `command_approved` / `command_denied` / `command_expired` / `command_cancelled` / `command_rule` name the rule but **never the command** (VIEW sharees read Logs).
