# Webhooks, notification preferences, installable app, push

- **Webhooks (`webhooks/` = `catalog.rs` (event names, groups, who receives each, which are site-wide; pure), `text.rs` (the sentence + title in en / zh-TW / ja; pure), `format.rs` (Telepy JSON / Slack / Discord / Google Chat / Teams Adaptive Card / Telegram / ntfy + detection from the URL; mentions neutralised; pure), `sign.rs` (Standard Webhooks HMAC, tested against the spec's vector), `target.rs` (SSRF: public addresses only, `PublicResolver` for delivery), `mod.rs` (dispatch, retries, records, pause); `api/webhooks.rs`, `db/webhooks.rs`; user doc `docs/webhooks.md`; tests `tests/webhooks.rs` + unit tests):** personal webhooks (`telepy_webhook.scope = user`, owner only, others get 404) carry exactly the notifications their owner already gets — every source calls `state.webhooks.emit(Event::new(kind).tunnel(t).to(audience, except_actor).data(…))` with **the same audience as the matching hub notification** (tunnel audience, owner + ADMIN, requester…), and `webhooks::matches` (pure) checks enabled, subscribed, owner ∈ audience, `notify_user_webhooks`, and the tunnel filter (`all_tunnels` or `telepy_webhook_tunnel`; account events ignore it). Site-wide webhooks (`scope = site`, any admin manages them) get only the curated `Kind::site()` set (status ×4, `tunnel.ip_changed`, `tunnel.host_key_changed`, `device.claim_attempt`, `account.sign_in_failed`, `user.created`) for every tunnel or a picked list (`site_tunnels` in `GET /api/webhooks` lists every tunnel for admins). **Site webhook modes + opt-outs (test `tunnel_managers_can_opt_their_tunnels_out_of_default_site_webhooks` + the status test in `tests/webhooks.rs`, unit tests in `webhooks/mod.rs` and `lib/webhooks.test.ts`):** `telepy_webhook.mode` = `default` (the column default, so pre-upgrade site webhooks are default) | `enforced` (create / PATCH `mode`, site only; JSON `mode`, a mode change is an extra `webhook` event). A tunnel's **owner or ADMIN sharee** opts that tunnel out of a *default* site webhook (`telepy_webhook_optout (webhook_id, user_id, tunnel_id)`; `PUT /api/webhooks/{id}/optout {tunnel_ids}` replaces *my* opt-outs — ids must be tunnels I manage (400 `not_manager`) that it covers (`not_covered`), enforced = 400 `enforced`, personal / unknown = 404, answers my summary; `DELETE …/optout` clears mine, enforced too; both ungated in `features::for_route`; each change = a `webhook_optout` event on that tunnel's Logs). Delivery rule (pure `webhooks::opted_out`, checked in `Webhooks::send_to`, so `emit` and the monitor's status alerts both honour it; tests / re-sends don't): a tunnel event is skipped for a default site webhook when **any current** manager of the tunnel (`db::webhooks::tunnel_managers` = owner + sharees whose permission *in force* is ADMIN, read at delivery time) opted it out — losing ADMIN ends that person's opt-out; enforced and personal webhooks ignore opt-outs; account events can't be opted out. Opt-outs ride the 30 s hook cache (invalidated on every write) and go with the webhook / the tunnel (`forget_tunnel`). `site_summary` adds `mode`, `my_optout` and `managed [{id, name, opted_out, by, mine}]` (tunnels I manage that it covers); admins' full rows add `optouts [{tunnel_id, tunnel_name, by, at, active}]`. Frontend: the site dialog's "Let people override" switch (on = default, off = enforced with the `EnforcedChip` lock), the card's enforced chip + "N opted out" popover (`OptOutsChip`), the personal page's site section: enforced chip / note, "Opt my tunnels out" (`components/webhooks/OptOut.tsx` `OptOutDialog`, switches per managed tunnel, others' opt-outs shown) only where the viewer manages a covered tunnel, and the info button → `OptOutInfoDialog` (event ─ site webhook ─ opt-out ─ admins' channel on `PathFlow`, webhook + tunnel pickers, lit by the pure `lib/webhooks.optOutPath`); copy under `webhooks.mode.*` / `webhooks.optout.*`. `GET /api/webhooks` also returns `site_summary` to **everyone** — redacted site webhooks `{id, name, service (effective format), events, all_tunnels, tunnels (only the picked ones the caller can see, by name), hidden_tunnels, enabled, paused}`, never URL / headers / secret / deliveries / creator; non-admins get only enabled or paused ones — shown read-only as the "Site-wide webhooks" section under my webhooks on `/tunnels/webhooks` (`components/webhooks/SiteWebhooksSection.tsx`, pure `siteCoverage` / `siteHookState` / `sortSiteSummary` / `knownEventOrder` in `lib/webhooks.ts`; admins get a Manage link there instead of the old admin-view link). `key.expiring` / `key.expired` are about **personal SSH keys** (Keys page; tunnel keys never expire) and come from `webhooks/keys.rs` (10-minute loop: within 7 days / expired in the last 48 h, once per key + stage + expiry in `telepy_key_expiry_notice`, a renewal re-arms it). Custom headers (≤ 10, `validate_headers` pure: HTTP-token names, Telepy's own headers refused, visible ASCII values) are sealed in `telepy_webhook.headers` (AAD `telepy-webhook-headers:<id>`) and returned to the webhook's managers; PATCH with `headers` replaces the set. Every delivery is recorded as `sending` before it goes out and finished afterwards (`db::webhooks::fail_unfinished` at startup turns leftovers into failed), stores the event as `event_json`, and can be re-sent (`POST …/deliveries/{id}/redeliver`: same `webhook-id`, current format / language / headers, no retries, not counted, `redelivered_from`; test sends can't). **When adding a notification worth a webhook: add a `Kind` (catalogue order = UI order), its sentence in `text.rs` for all three languages, `EVENT_KEYS` + `webhooks.ev.*` keys in the frontend, and emit it next to the hub notification.** Status events don't go through `emit`: `monitor::runner` keeps one `alerts::Alerts` (pure state machine: a condition must outlast the delay, only announced ones send the end, going down silently clears degraded) **per webhook** with its own `delay` and calls `send_to`; only changes after a webhook exists are tracked. Delivery: per-webhook format + language, `webhook-id` / `webhook-timestamp` / `webhook-signature` / `x-telepy-event` headers (secret `whsec_…` sealed with the vault, AAD `telepy-webhook:<id>`, created lazily, `GET/POST …/secret`), retries after 10 s and 60 s on network errors / 408 / 429 / 5xx (`set_retry_delays` for tests), no redirects, ≤ 30 per webhook per minute (first skip recorded as `skipped`), paused after `PAUSE_AFTER` (20) failures in a row (`paused_reason = failing`, `WEBHOOK-PAUSED` to the owner / every admin; PATCH `enabled: true` clears it), latest 50 deliveries kept with the body (≤ 16 KB, 30 days via `db::retention`). Personal URLs must resolve to public addresses only (save-time `target::check` + the delivery-time resolver + IP-literal check; `private_target`) unless the site setting `notify_private_targets` is on; site webhooks may target anything. Site settings `notify_user_webhooks` / `notify_private_targets` / `notify_max_webhooks` (Notifications tab, which now links to the Webhooks page); the old `notify_webhook_url` / `notify_down_delay` columns stay but left the API — data migration `2026-10-26-site-webhook-from-settings` turned a set URL into a site webhook “Status alerts”. Webhooks are cached 30 s in memory and invalidated by every write; deleted tunnels leave every webhook's list. Site webhook changes are `webhook` gateway events. Frontend: `/tunnels/webhooks` = my webhooks only (admins too; a legacy `?scope=site` redirects) and `/tunnels/admin/webhooks` = site-wide (admin section, nav "Site webhooks"), one `components/webhooks/WebhooksView.tsx` with `scope` (`useWebhooksPage(scope)`; `hooks/useWebhooksPage.ts`, `components/webhooks/` — `WebhookCard`, `WebhookDialog` (URL with live service detection, format, language, grouped event checklist with who receives each + presets, delay, tunnel picker), `DeliveriesDialog`, `SecretDialog` (headers + Node.js / Python verification), `EventCatalog`, `WebhookPausedNotice` in `AppLayout`), pure `lib/webhooks.ts` (tested); copy under `webhooks.*`. `UPDATE-TUNNEL-STATUS` carries `tunnels [{id, name}]`; desktop notifications are per browser (`hooks/useDesktopNotifications.ts`, localStorage `telepy.desktopNotify`, toggle in Preferences → Notifications, mounted in `AppLayout`), shown only while the tab is hidden. No email (no SMTP in Telepy).
- **Notification preferences — in-app toasts and desktop notifications (`notify_prefs.rs` pure + unit tests, `db/notify_prefs.rs`, `api/notify_prefs.rs`; test `tests/notify_prefs.rs` on the lab; frontend pure + tested `lib/notifyPrefs.ts`, store `hooks/useNotifyPrefs.ts`, `components/notify/`):** per catalogue event (`webhooks::catalog::Kind`, only those with an in-app notification: `notify_prefs::channels` — online / offline / command awaiting approval are desktop-only) × channel `toast` | `desktop`, four layers: built-in on → **site default** (`telepy_notify_default (event, channel, enabled NULL = built-in, locked)`; per event "Let people override" = `locked` false, off = **Enforced**) → **my default** (`telepy_notify_pref`, only overrides stored) → **this tunnel** (`telepy_notify_tunnel_mute (user_id, tunnel_id, scope all|status)`, deleted with the tunnel; status = online / offline / degraded / recovered; account events ignore mutes). Effective = locked ? on : (mute covers ? off : mine ?? site ?? on), with the deciding layer as `source` (`locked | muted | mine | site | builtin`) — `notify_prefs::resolve` and `lib/notifyPrefs.resolveNotify` must agree. API: `GET/PUT /api/notifications/preferences` (`{events [{event, group, audience, tunnel, status, channels, locked, site, mine, effective, source}], mutes [{tunnel_id, tunnel_name, scope}]}`; PUT `{prefs: [{event, channel, value: on|off|inherit}]}` changes only what is sent, turning off an enforced event = 400 `{code: locked, event}` and nothing is written), `PUT/DELETE /api/notifications/mute/{tunnel_id}` (`{scope}`; anyone who can see the tunnel, else 404), admins `GET/PUT /api/notifications/defaults` (`{defaults: [...], locks: [{event, locked}]}`; 403 `admin_only`; writes a tunnel-less `notify_default` gateway event). **Only the showing is gated, in the browser:** hub notifications are still sent (pages refresh on them); every toast that surfaces a notification and every desktop notification calls `allowNotification(msg, channel)` / `shouldNotify(kind, channel, tunnelId)` (`notificationKind` maps `action` → event; refresh-only actions are never gated; not loaded yet = shown); desktop also needs the per-browser switch. Personal webhooks are unaffected. UI: Preferences → **Notifications** tab (`NotifyPrefsPanel`: the desktop switch, `NotifyMatrix mode="mine"` with "Follows site default" / "Overrides" chips, 🔒 "Enforced" only on locked rows, reset per row, muted tunnels), the tunnel menu's "Notifications" submenu (show all / mute status / mute all), the admin page `/tunnels/admin/notifications` (nav "Site notifications", `NotifyMatrix mode="site"`), and "How it works" on both = `NotifyFlowDialog` (event ─ site ─ my default ─ this tunnel ─ result on `PathFlow`, from `notifyFlow`). Copy under `notifyPrefs.*`. When adding an in-app notification for a catalogue event: `notify_prefs::channels`, `notificationKind`, and gate its toast / desktop call.
- **Installable app (PWA, phase 1; `app_manifest.rs` pure + unit tests, `api/app.rs`; test `tests/app_manifest.rs`; frontend `public/sw.js`, `lib/serviceWorker.ts`, pure + tested `lib/installApp.ts`, `hooks/useInstallApp.ts` / `useAppName.ts` / `useLeaveGuard.ts`, `components/app/` (`AppBoot` in the root layout, `InstallAppPanel`, `InstallAppInfoDialog`), `components/settings/AppNamePanel.tsx`):** `GET /api/app/manifest.webmanifest` is public (`application/manifest+json`, `no-cache`; linked from every page's `<head>`), so it carries only name, icons, `standalone`, `start_url` / `scope` `/` and the light background — never a description (discreet sign-in rule). Its name follows the site settings `app_name_mode` (`telepy` default | `domain` = PUBLIC_URL's host, else the request's host, else `SERVER_DOMAIN` | `custom` = `app_name`, tidied, ≤ 30 characters; custom without a name = 400 field error on `app_name`), edited on Site settings → **App** (`?tab=app`, keys `app_*`; segmented choice + preview of a home-screen label and a notification); desktop notifications use it as their title (`useAppName`, cached in localStorage `telepy.appName`). **The service worker caches nothing and intercepts no request** (no fetch handler — installing doesn't need one since Chrome 108/112, and a caching worker would pin old builds); it only shows notifications (`registration.showNotification`, the fallback when `new Notification` throws, i.e. Chrome on Android) and on `notificationclick` focuses an open window and posts `telepy:open` so `AppBoot` navigates in place (no reload — terminals survive). `AppBoot` also keeps `beforeinstallprompt` (preventDefault: no Chrome install bar on the sign-in page; the Install button lives in Preferences). Preferences → **Install as an app** (tab id `install`): install button or per-platform steps (`installGuide`: installed / insecure (http://, no install) / prompt / ios / android / macSafari / chromium / firefox / other), what changes (Ctrl+W/T/N reach the shell on Windows / Linux; Ctrl+W outside the terminal closes the window; iOS apps have their own sign-in and open new-window links in Safari) and the "Where Ctrl+W goes" diagram (`keyPath`). The terminal page and the LAN dock ask before the tab / window closes while a connected shell would end with it (`terminalDetach.endsWhenLeaving`: no grace / 0 s; `useLeaveGuard`). Per device, Preferences → Notifications → "Show the command in notifications on this device" (localStorage `telepy.notifyDetails`, off by default): off = the approval notification names the person and tunnel only (`notify.commandApprovalHidden`). `<meta name="theme-color">` follows the theme (bootstrap script + `userPrefs.setThemeColor`, `THEME_COLORS` = the Rust `BACKGROUND_*`, checked by `installApp.test.ts`). Icons: `public/icons/icon-192.png`, `icon-512.png`, `icon-maskable-512.png` from `scripts/app-icons.mjs`. Push: see the next bullet. Copy under `app.*` / `appName.*`.
- **Push notifications (Web Push, phase 2; `push/` = `crypto.rs` (RFC 8291 `aes128gcm`, tested byte for byte against the RFC's appendix A), `vapid.rs` (P-256 key in `<DATA_DIR>/push/vapid.key`, 0600, **not** sealed with SECRET_KEY — a new key ends every subscription; ES256 JWT, `aud` = the push service origin, 12 h, `sub` = the https PUBLIC_URL else the project page), `notice.rs` (pure: which events, text, tags, endpoint allow-list), `mod.rs` (`Push`, owned by `Webhooks` and shared as `state.push`); `db/push.rs`, `api/push.rs`; tests `tests/push.rs` against a fake push service + unit tests; frontend `public/sw.js` `push` handler, `hooks/usePush.ts`, pure + tested `lib/push.ts`, `components/notify/PushSection.tsx` + `PushFlow.tsx`):** every `Webhooks::emit` also calls `push.event` — same event, same audience as the in-app notification. Pushed kinds = `notice::pushed`: those with a desktop channel in `notify_prefs::channels` plus `tunnel.recovered` (decided by degraded's preference, `pref_kind`); `Push::event` skips the four status kinds, which come from the monitor instead (below). Each recipient's **desktop** preference decides (`notify_prefs::layers_for` + `resolve`: site default → mine → tunnel mute, enforced), so the Notifications matrix's Desktop column also governs pushes. Body = `webhooks::text::sentence` in the subscription's language; title = the app name (`push::app_name`); `tag` = the page's own desktop-notification tag (`command-<request>`, `ip-<tunnel>`, `share-<tunnel>`, `watch-<tunnel>`, `sign-in`…) and the same string as `Topic`; a command approval hides the command unless that device's `details` is on (`telepy.notifyDetails`, sent with the subscription and PATCHed on change), TTL 600 s for approvals, 1 day otherwise, `Urgency: high` for approvals / new-device sign-ins / claims / host-key changes. **Subscriptions (`telepy_push_subscription`)** are bound to the web session that made them (one row per session — a new endpoint from the same sign-in replaces the old, ≤ 20 per person) and are deleted when that session is revoked (`auth::sessions::revoked` → logout, Your devices, reuse, account disabled), on 404 / 410 from the push service, and hourly when the session expired (`db::retention`); sending only selects rows whose session is live. Endpoints must be https to a known push service (`googleapis.com` / `google.com` — Chrome hands out `jmt17.google.com` endpoints, found by testing — `push.apple.com`, `push.services.mozilla.com`, `notify.windows.com`; `push_endpoint` otherwise) and are reached through the webhooks' `PublicResolver`; ≤ 30 pushes per device per minute. Site setting `notify_push` (default on). API (web sign-ins only; tokens get `token_route`): `GET /api/push` (`{enabled, available, public_key, key_error, per_minute, subscriptions [{id, user_agent, lang, details, service, current, created_at, last_success_at, last_error, last_error_at}]}`), `POST /api/push/subscriptions` (`{endpoint, keys {p256dh, auth}, lang, details}`; 400 `push_endpoint` / `push_keys` / `push_session`, 409 `push_off`), `PATCH /api/push/subscriptions/{id}` (`details`, `lang`), `DELETE …/{id}`, `POST …/{id}/test` (`outcome` sent / gone / skipped / failed); others' rows are 404. Doctor check `push` (key readable; group keys). Frontend: Preferences → Notifications → "Push notifications" (switch asks for permission inside the click; why it can't: http, iOS not on the Home Screen → link to the install tab, unsupported, site off, no key; device list with test / remove; "How it works" = Telepy ─ encrypted ─ push service ─ this device on `PathFlow`, lit by `pushSpots(on, lastDelivery)`, plus what the service sees and when pushes stop); a device with push on skips the page's own desktop notification for pushed kinds (`pushActiveHere`, `showPushed`), `usePushSync` keeps the subscription's language in step, logout unsubscribes the browser (`dropPushHere`). **Online / offline / degraded / recovered pushes (phase 3; test `status_pushes_wait_follow_the_audience_and_stop_at_the_hourly_cap` in `tests/push.rs` on the lab with a real tunnel):** `monitor::runner` keeps one `alerts::Alerts` **per person with a live subscription** (`Runner.push_alerts`, the same pure state machine as the webhooks': a drop must outlast the delay, only an announced one sends "back online", going down silently clears degraded), fed by `status_change` for every viewer of the tunnel (owner + sharees) and drained each cycle with that person's delay (`Push::status_listeners` = `db::push::status_listeners`: the user setting `push_status_delay` (`user_management_usersettings`, `/api/user/settings`; one of `push::STATUS_DELAYS` 0 / 60 / 120 / 300 / 600 / 900 / 1800 / 3600 s, default 60; the answer adds `push_status_delay_max`) clamped by the site setting `notify_push_max_delay` (default 3600, 0–86400; `push::status_delay`)); `Push::status` then checks the desktop preference (tunnel mutes with scope status apply) and the per-person hourly cap — site setting `notify_push_per_hour` (default 20, 1–500), `StatusCap::admit` (pure): below the cap = send, at the cap = one `notice::held` push (tag `status-held`) and then nothing until the hour frees a slot. Status pushes link to `/tunnels/<id>` and share the tag `tunnel-<id>` with the page's own status notification, which a device with push on no longer shows itself. Only changes after someone subscribed are tracked. `GET /api/push` adds `status {delay, effective, max_delay, per_hour, choices}`; the Notifications tab's push block has "Tell me a tunnel is offline after" (`StatusWait`, `lib/push.delayChoices`: choices above the site max hidden, a current one above it marked "shortened to …") and the info dialog an online / offline timeline (drops 0:00 ─ waits ─ still down ─ "offline" ─ when it's back ─ "back online"). Verified end to end through Google's real push service from headless Chrome for Testing — with a persistent profile: Chrome refuses push in incognito (Playwright's default contexts), which `enable()` reports like a denied permission. Copy under `push.*`.
