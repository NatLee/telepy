# Groups — sharing with groups, tunnel groups + key groups, pins and labels

- **Sharing with groups — admin-kept and personal (`group_shares.rs` = pure `wants` / `plan` / `personal_share_counts` / `diff` / `changed` + unit tests, `load` / `reconcile` / `preview` / `active_shares` / `tick` / `kick`; `db/group_shares.rs`; handlers in `api/sharing.rs`, personal groups in `api/personal_groups.rs`; tests `tests/group_shares.rs` on the SSH lab; frontend `components/tunnels/ShareModalGroups.tsx` (+ `GroupShareInfoDialog`), `components/groups/PersonalGroupDialog.tsx`, `hooks/useGroupShares.ts`, `hooks/usePersonalGroups.ts`, pure + tested `lib/groupShares.ts` / `lib/peopleGroups.ts`; copy under `share.group.*` / `personalGroups.*`, user doc `docs/sso.md`):** one admin table once did two jobs (feature permissions and, with `shareable`, sharing), which people found mysterious; **roles and groups are now split by job and never influence each other** (see **Feature permissions / roles**): roles decide features and are never share targets; groups decide sharing and never features. Two kinds of groups can be shared with. **Admin-kept groups** (`owner_id` NULL, `purpose = 'group'`; admins via `/api/access/share-groups*`, SSO rules, SCIM when the provider pushes groups) are offered to every tunnel manager and always count. Data migration `2026-11-09-roles-and-groups` (`db::schema::roles_and_groups`, one transaction; test `the_upgrade_keeps_everyones_tunnels_and_features`): every organization group with a group share became a group — converted in place (`purpose = 'group'`, `display_name = name`, `name` = placeholder, same id — its SSO rules, grant records and SCIM mapping stay on it, so the identity provider keeps feeding it) when it had **no feature grant** (only feature rules make a group a role; membership without them decides nothing), else **copied** (new admin-kept group, same display name unless one is taken → `" (shared)"` / `" (shared N)"`, same members, its `telepy_group_share.group_id` rows repointed, and its SSO rules + grant records **copied to the new group too**, so someone the provider removes from the team also leaves the copy — found by the security review: without that they kept the tunnel; a SCIM mapping can't follow, so such copies are named in a startup warning; `shareable` stays 1 on admin-kept groups only so a rollback to an older build still counts their shares; the role keeps members, grants, rules and mapping; `tunnels_tunnelsharing` rows point at group *share* ids, so nobody gains or loses access); shares of organization groups closed to sharing (they never counted) were deleted; personal groups got `purpose = 'group'`; `shareable = 0` everywhere. After the copy, SSO / SCIM keep feeding the role, not the copy. **Personal groups** (`GET/POST /api/user/groups` → `{groups [{id, name, description, members, member_names, shares [{id, tunnel_id, tunnel_name, permission_type, active}], created_at}], member_of [{id, name, description, kind, owner, synced, tunnels [{id, name, permission_type, through}]}] (others' personal groups + admin-kept groups I'm in; roles are never listed, `db::group_shares::member_of`), can_share, users (other active accounts), limit 50, max_members 200}`; GET is open to everyone (no feature gate) so anyone can see and leave the groups they're in, `PATCH/DELETE /api/user/groups/{id}`, `POST …/{id}/preview` `{members}` | `{delete: true}`, `DELETE …/{id}/membership` = leave someone else's personal group (anyone can add you, so you can always leave; admin-kept groups, roles and your own = 404; `group_share` event per tunnel, `PERSONAL-GROUP-LEFT` to the owner; the tunnel page's Access tab has the button — list items carry `share_group_id` + `share_group_owner`, and a self-unshare of a group row answers `group_id` + `personal`); owner only — every handler touches only `owner_id = me` rows, so others' groups, admin-kept groups and roles are 404; the account list and adding members need `db::group_shares::manages_any` (owner or ADMIN of ≥ 1 tunnel, the available-users bar — else `can_share: false`, `users: []`, members = 403 `{code: no_tunnels}`, so member ids can't be probed to list accounts); a paused share on a tunnel the maker can no longer see has `tunnel_name: null`; field errors `name` (unique per owner) / `members` (active, not yourself), 400 `{code: limit}`; POST / PATCH / preview gated by `tunnels.share`, GET / DELETE / leave open; no audit events of their own — the per-tunnel `group_share` events say what happened) are made by anyone in the share dialog, seen only by their maker, never used for features. **A personal group's share counts only while its maker manages the tunnel** (`counting` over `Candidate`s, one pure pass: the maker's direct row in force, else the higher of what admin-kept groups give them via `wants` and a raise in force (`Held`) — never through a personal group, or two people could keep each other in; never read from existing group rows, so a maker leaving an admin-kept group pauses in the same reconcile and shows up in that group's preview; `personal_share_counts`); otherwise it is **paused** (`active: false` in the JSON, rows removed by `plan`, back when it counts again); unshare / update-permission / direct share / enabling or disabling an account kick a reconcile so pauses bite at once. Choices = the viewer's personal groups then every admin-kept group (`db::group_shares::share_choices`); POST with any other id (a role, someone else's personal group) = 404; `load` skips any group share that points at a role (defence in depth), and `synced_groups` / `member_of` / `covering` / `my_groups` / `row_groups` only read `purpose = 'group'` rows. A tunnel can be shared with a group (`telepy_group_share (tunnel_id, group_id, shared_by_id, permission_type, expires_at)` unique per tunnel + group, accounts in `telepy_group_share_username`). **Materialised, not derived at check time:** every member gets an ordinary `tunnels_tunnelsharing` row marked `group_share_id`, so every gate (permissions, `allowed_usernames`, device keys, presence, notifications, access recheck, webhooks) works unchanged. `plan` merges a person's group shares (highest permission, union of accounts, latest end or none; source = the highest, earliest on a tie), skips the owner **and the group share's own sharer** (an ADMIN sharee sharing with a group they're in must not keep access through it after losing their ADMIN; test `a_sharer_gets_nothing_from_their_own_group_share_and_writes_follow_the_row`), **never touches a direct row** (direct wins), updates a group row's `base_permission` instead while an access-request raise runs (decided by the row at write time: `db::group_shares::update_row` is one conditional UPDATE — CASE on `base_permission`, `AND group_share_id IS NOT NULL` — so a raise ending or a conversion to direct between plan and write is never overwritten; a Remove step re-checks the row id and that it is still a group row; one failing step is logged and the rest run; the direct-share handler `share()` takes `group_shares::lock()` around its read + convert) and only its permanent accounts (temporary ones stay; `set_permanent_accounts`), and removes group rows nobody wants any more through `end_share` with `EndReason::Group` (sharee told; the owner only refreshes; webhook `share.ended` reason `group` to the member only). `reconcile` holds one lock; triggers: the group-share API and admin-kept / personal group writes (inline), OIDC `apply_roles` when it touched an admin-kept group, SCIM writes to an admin-kept group (`kick` / `kick_with` names for deleted groups) and the 30 s `sharing::run_expiry` loop (`tick`: expired group shares deleted, then reconcile — the safety net). API: `GET/POST /api/reverse/server/{id}/group-shares`, `PATCH/DELETE …/{gsid}` (`{group_id, permission_type, allowed_target_username_ids, expires_at}`; owner / ADMIN via `check_share_access`, GET for anyone who sees the tunnel; member names and the group choices only for managers; POST/PATCH need feature `tunnels.share`, DELETE stays open) → `{can_manage, shares [{…, kind org|personal (`org` = an admin-kept group; the wire value is kept), owner, mine, active, synced (an admin-kept group an identity provider keeps — SCIM or an SSO rule, `db::group_shares::synced_groups`), members, member_names, through, direct, elsewhere (members holding it through another group share), owner_in}], groups [{id, name, members, kind, synced, shared}]}` (`member_of` entries carry `synced` too). A group row can't be revoked / changed / left on its own (400 `{code: via_group, group}`); `POST /tunnels/share` on a group row turns it direct (`converted: true`); `unshare` answers `still_via_groups` when a group re-grants. `shared-users` rows carry `via_group`, list items `share_group`. Events `group_share`. Deleting a group or tunnel deletes its group shares; deleting an account drops it from group shares' accounts. **Ordinary users see one concept, "groups"** (the user's decision: they couldn't tell the two kinds apart): the admin area says roles and groups, and every group is labelled only by who keeps its members — you / <owner> / admins / synced from company accounts (pure `lib/peopleGroups.groupKeeper`, `components/groups/GroupKeeper.tsx`); copy `peopleGroups.keeper.*`. Long lists everywhere: the share dialog's group picker is one searchable, paged radio list (`sortedChoices`, `GroupSearch` blocks), each share's members popover searches from 8 and pages by 20 (`components/groups/MemberNames.tsx`), the Groups page folds member names / tunnels after 5 (`FoldedItems`) and searches + pages "Groups you're in" (`filterMemberOf`). Frontend: the sidebar's **Groups** page (`/tunnels/groups`, `nav.peopleGroups`, `components/groups/GroupsPageView.tsx`: your personal groups with member names and the tunnels using them, and "Groups you're in" with `LeaveGroupButton`; refetches on `PERSONAL-GROUP-LEFT` / share notifications; copy `peopleGroups.*`), the personal-group list + editor shared by it and the share dialog (`components/groups/PersonalGroupsManager.tsx` `PersonalGroupsSection` + `usePersonalGroupEditor`), and the share dialog's **Groups** tab (list with a kind chip (Organization / Personal · yours / Personal · <owner>), a paused line, counts, members popover, accounts / permission / end, remove; add form with optgroups; "Your personal groups" with new / edit / delete, edits and deletes of a shared group previewed first; info diagram with an Organization / Personal switch: identity provider or you ─ group ─ this tunnel ─ each member), the people tab marks `via <group>` rows (controls off, "Set this person on their own"), the sharee's card / tunnel page show the group.
- **Pins and labels (`db/tunnel_tags.rs`, test `tests/tunnel_tags.rs`):** pins are per user (`telepy_tunnel_pin`; `PUT/DELETE /api/reverse/server/{id}/pin`, anyone who can see the tunnel); labels are shared (`telepy_tunnel_label`; `PUT /api/reverse/server/{id}/labels {labels}` replaces the set, EDIT and up, then `UPDATED-TUNNELS` to the audience). Labels: `[a-z0-9][a-z0-9._=-]{0,31}`, ≤ 12, lower-cased / de-duplicated / sorted by `normalize_labels` (mirrored client-side in `lib/tunnelLabels.ts`); errors are `{labels: [msg]}`. Both are deleted with the tunnel; unsharing drops the sharee's pin. List items (and the single retrieve) carry `pinned` + `labels`; MCP `list_tunnels` returns `labels` and `health`. Frontend: `components/tunnels/TunnelTags.tsx` (`PinButton`, clickable `TunnelLabels` that add `label:x` to the search), pinned tunnels sort first under any sort, `label:` / `tag:` (also the labels of the tunnel's group) and `pinned:yes|no` query keys, label editing in the tunnel page.
- **Tunnel groups + key groups (`db/groups.rs`, `api/groups.rs`; test `tests/groups.rs` on the SSH lab):** both are **personal** (only the owner sees them; sharing is untouched). A **tunnel group** is a folder for the tunnel list (`telepy_tunnel_group` with `position`, `telepy_tunnel_group_member` keyed by (user, tunnel) — a tunnel is in at most one of a person's groups, and only tunnels they can see); `GET/POST /api/reverse/tunnel-groups`, `PATCH/DELETE …/{id}`, `PUT …/{id}/tunnels` (whole member list; ticked tunnels move in from other groups), `PUT …/order {ids}`, `PUT /api/reverse/server/{id}/group {group_id | null}`; list items (and the single retrieve) carry my `group_id`. A **key group** holds the caller's own keys (`telepy_key_group`, `telepy_key_group_member` keyed by key — one group per key; key JSON carries `group_id`, `POST/PATCH /api/reverse/user/keys` take it) and is **granted as a unit** (`telepy_key_group_grant`: exactly one of `tunnel_id` / `tunnel_group_id` (own tunnel groups only), optional `accounts` = account **names**, NULL = all): `GET/POST /api/reverse/user/key-groups`, `PATCH/DELETE …/{id}`, `PUT …/{id}/keys`, `POST …/{id}/grants` (same target again = change accounts), `PATCH/DELETE …/{id}/grants/{grant_id}`. Names: 1–48 characters, whitespace collapsed, unique per person ignoring case (`groups::normalize_name`, mirrored in `lib/groups.ts`); every write answers `{groups, group}`. Both kinds also carry a `description` (≤ 500 characters, trimmed, newlines kept; `groups::normalize_description`) and `labels` (JSON column, the tunnel label rules via `tunnel_tags::normalize_labels`, ≤ 12), optional on create; PATCH changes only the fields given (`name` / `description` / `labels`, null clears). The editors share `components/groups/GroupMetaFields.tsx` (`useGroupMetaForm`; `lib/groups.groupPatch` sends only what changed); tunnel group section headers show the labels (click = `label:x` in the search) and the description under the name, the manager / Move-to-group / grant dialogs and key group cards / list rows show them too, `GroupSearch` matches name + description + labels (`groupMatches`), and a tunnel's search `label:` / free text also match its group's labels (`MatchContext.groupLabels`). **Grants are live and never copied into key lists:** `db::device_keys::group_entries_*` derive entries from grants × key group members × tunnel group members every time, `effective_entries_for_*` = direct ∪ derived, and `device_keys::desired` uses them (`Entry::covers` checks direct account ids or grant account names; several entries for a key add up), so adding a key to a group, a tunnel to a granted tunnel group, or narrowing a grant installs / removes keys on the next sync — `allowed_usernames` stays the ceiling. `tunnels_with_state` / `tunnels_with_key` include granted tunnels; every group write kicks the affected devices. Unsharing (`end_share`) drops the sharee's grouping of that tunnel and their key groups' grants to it (`groups::forget_tunnel_for_user`); deleting a tunnel drops all of both; deleting a key leaves its group. Device-key JSON says where a key comes from: entries / matrix keys have `direct` + `groups [{id, name, tunnel_group, accounts}]`, view rows `direct` + `groups`, `my_keys[].via_groups`, and `my_key_groups` (direct `grant` / `via_tunnel_group` per group); only direct entries can be removed from a list (derived ones 404 there). Frontend: tunnels page sections by group (`lib/groups.groupSections`, `components/tunnels/TunnelGroupSection.tsx`; collapsed sections in localStorage `telepy.tunnelGroupsCollapsed`, "By group / One list" in `telepy.tunnelGrouping`), the "Groups" manager / editor / "Move to group" (tunnel menu) dialogs (`TunnelGroupsDialog`, `TunnelGroupEditor`, `MoveToGroupDialog`, state in `hooks/useTunnelGroupsUi.ts`, data in `hooks/useTunnelGroups.ts`), query key `group:<name>|none`; keys page "Key groups" sub-page (`components/keys/KeyGroupsSection.tsx` — cards or list rows by the account's view mode, `hooks/useKeyGroups.ts`) with the grant dialog (`KeyGroupGrantDialog`: tunnel group or device, every account or named ones, live preview) and the info button's `KeyGroupFlow` (keys → given to → devices with accounts and install progress; an example before the first group); a key-group field in the add / details dialogs, a group chip on key cards, matrix / details ticks mean **direct** entries with group-derived ones marked "via group"; the device panel's Your keys tab grants / revokes a group from its section header. Both group editors pick members with `components/groups/MemberPicker.tsx` (pure `lib/memberPicker.ts`, tested): removable chips of what is picked on top (+N after 10 opens "Picked"), from 7 items a search, all / picked / in no group (= not grouped when the editor opened) buckets and "select / deselect all N" for every current match, a one-column list in pages (`telepy.groupPickerPageSize`); the fieldset is `min-w-0` and the buckets are a native select on phones / a wrapping full-width segmented row from `sm` (a fieldset is otherwise as wide as its widest child, which pushed the Japanese phone dialog off screen), and an "in X" chip wraps under the name instead of truncating it; an empty group name is flagged only after Save. With a search / filter active the tunnels page offers "Group these N" (every result, all pages; opens the editor with them picked), and "Move to group" plus the grant dialog's tunnel-group list use `components/groups/GroupSearch.tsx` (search from 7 groups, pages in `telepy.groupListPageSize`, the current choice appended when it is on another page); unticking inside "Picked" keeps the row until the bucket changes.
