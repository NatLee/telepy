# SSH gateway, tunnel names, keys, health

- **SSH gateway (`gateway/`):** the backend listens on 2222 (published as `REVERSE_SERVER_SSH_PORT`) with the host keys from `ssh/ssh_host_keys`. Only public-key auth (tunnel / user keys from the DB) and `tcpip-forward` are accepted — the service key is deliberately **not** accepted (the backend reaches devices in-process; that key sits in every device's `authorized_keys`), a tunnel key may only forward its own port and a user key only ports of tunnels the user owns; `tcpip-forward` only records port → connection — **nothing is bound on the host**, `reverse_port` is just a number; **a tunnel key identifies its tunnel** (test `tests/key_identified.rs`): whatever number the device asks for in `-R` (0 included) the forward is registered under the tunnel's own `reverse_port`, which is also the number the device is told (a user key still has to ask for the number of a tunnel it owns); **a key may be both its owner's tunnel key and their personal key** (the computer they work from is also a device; test `tests/own_device_key.rs`): `identify` then returns `Identity::Tunnel { person: true }` (only when the personal key is the same user's, unexpired, the account active and `keys.personal` on) — forwards follow the tunnel's rule, while the greeting, `direct-tcpip`, laptop presence, step-up and `last_used_at` go through `Identity::person()`; across users a key is never shared; `direct-tcpip` accepts `<tunnel name>:<any port>` as well as `localhost:<number>` (names are unique; matched **ignoring case** because OpenSSH lowercases `HostName` before ProxyCommand's `%h` — `gateway::port_by_name`: the exact match first, then the first case variant this identity may reach, else the exact / only one so the refusal is logged on it; test `a_tunnel_name_with_capitals_survives_ssh_lowercasing_it`), and the generated ssh config's device stanza is `HostName <tunnel name>` / `Port 22`; everything the backend does on a device opens a forwarded-tcpip channel in-process (`Gateway::open_stream`) and, except AI sessions and LAN scans (their own connection via `ssh::device::connect`), runs over `ssh::pool`: one connection per (tunnel, OS account), idle 5 min; **only session channels count** (that is all MaxSessions limits): ≤ 8 per connection via `session_channel` — web terminal tabs, exec (file-manager fallback, desktop screens), device key lists and the macOS resolver's lookups — and a MaxSessions refusal teaches that connection a lower limit for `RELEARN` (2 min); direct-tcpip users (remote-browser SOCKS, desktop / RustDesk, the LAN hop) hold a transport lease from `acquire` that takes no slot; SFTP REST and every file manager share **one** sftp channel per connection (`pool.sftp`, one slot) — except bulk transfers (downloads, zips, upload parts ≥ 1 MiB), which open their own short-lived one (`pool.bulk_sftp` → `TransferSftp`, falls back to the shared one) with a 120 s per-request limit (`BULK_REQUEST_TIMEOUT`: russh-sftp's deadline starts at *send*, so 16 pipelined ~255 KiB reads timed out at the default 10 s on device links under ~3 Mbit/s — measured: 12 MB at 200 KB/s died after 2 MB; and listings no longer queue behind them), replaced when `ssh::sftp_watch` sees it closed or with requests unanswered for 15 s (the device's sftp-server answers one request at a time), closed after 5 min unused; the file manager renews it on a failed listing. A bare `russh::Channel` sends no close when dropped — close it yourself (a `ChannelStream` does). **direct-tcpip targets that are names go through `ssh::resolve` first**: Apple's sshd-session aborts on a hostname direct-tcpip and drops the whole connection (every channel on the pool with it), so on Darwin devices (`uname -s`, once per connection) the name is resolved on the device with `/usr/bin/dscacheutil` and the channel opened to the IP — never send a name to a Mac; other OSes get the name as before. See `docs/device-connections.md`. `direct-tcpip` serves the generated ssh config's `ProxyCommand ssh -W` for user keys. **No shell:** a tunnel key's session channel is refused; a personal key gets ≤ 2 session channels per connection that only print a greeting (`gateway/greeting.rs`, pure: the user's language, how to reach devices — `ssh <device>` / `telepy ssh <tunnel>` — and up to 8 reachable devices by the `can_reach_device` rule; Tapi in colour with a pty, plain text for exec) and exit 1 — nothing is ever run, the exec command is ignored; subsystem (sftp), x11, env and agent requests fail (test `tests/gateway_greeting.rs`). **PROXY protocol (`gateway/proxy_protocol.rs`; test `tests/proxy_protocol.rs`):** from `GATEWAY_PROXY_PROTOCOL_FROM` (IPs / CIDRs) the header is **optional and auto-detected**: the gateway peeks at the first byte (`P` / `\r` = v1 / v2 header, SSH always starts with `S`; nothing within 5 s = a client waiting for our banner, treated as direct), reads the header byte-exactly before SSH, and its source replaces the peer everywhere (events, endpoint, presence); `UNKNOWN` / `LOCAL` keep the peer; a malformed header = `refused_proxy` event, a connect-and-close (health check) is dropped silently. Every other source never has a header read (never trust one from unlisted peers — anyone could claim any IP, defeating the IP-change alert). **Finding the sources (`gateway/peers.rs`, `api/address_sources.rs`; test `an_unlisted_proxy_is_recognised_but_never_trusted`):** the gateway counts, per raw peer address since start (memory, ≤ 512, stalest dropped), connections that sent data and how many began with a PROXY header — listed sources from the existing peek, unlisted ones through `FirstRead` (sees the first chunk once, detection only; russh accepts nothing before a client's banner, so an unlisted proxy's connections fail at the handshake) — and writes `proxy_unlisted` (at most hourly per address, a Logs "needs attention" kind). `GET /api/site/address-sources` (superusers, 403 `admin_only`) → `{since, peers [{ip, scope, connections, proxy_headers, first_at, last_at, last_header_at, listed}] (header senders, internal and listed addresses; other public ones only counted in `other_public`), presets [loopback | private | cloudflare (`server_settings::CLOUDFLARE_RANGES`)]}`. The Server tab's field is `components/settings/AddressOptions.tsx` `ProxySourcesControl` (seen addresses with advice add / trusted / idle / internal and one-click add, presets; pure `lib/proxySources.ts`); `ClientIpHeaderControl` does the same for `client_ip_header` from the address check's `headers` plus `lib/clientIpHeaders.ts` (who sends which header; its test reads `CANDIDATE_HEADERS`). Both only fill the input; `.env` locks them but the observations stay. `Lab::start_with(|config| …)` sets it in tests. Device-side scripts are unchanged.
- **Tunnel names = ssh host names (`tunnel_name.rs` pure + unit tests, mirrored by `lib/tunnelName.ts` whose test reads the Rust file; tests `tests/tunnel_names.rs`, `lib/tunnelName.test.ts`):** the generated ssh config is `HostName <name>` through `ProxyCommand ssh -W %h:%p`, so names follow OpenSSH: ASCII letters, digits, `.`, `_`, `-`, starting with a letter or digit, ≤ 63 (`tunnel_name::problem` → `name_empty` / `name_too_long` / `name_first_char` / `name_chars`). Why each exclusion (researched, keep in sync with the "Why?" popover): OpenSSH 9.6's `valid_hostname` refuses a leading `-`, shell metacharacters, whitespace and control characters on the command line (CVE-2023-51385); in ssh_config whitespace separates `Host` patterns, `* ? ! ,` are pattern syntax, `%` is a token in `HostName`, `#` a comment; Telepy uses `@` (`tunnel@account`) and `:` (`tunnel:path`, `-W name:port`). `Host` matching is case-sensitive but ssh lowercases the host it connects to (`ssh.c` `lowercase(host)`), so names are **unique ignoring case** (`db::tunnels::name_taken_ignoring_case`; the UNIQUE constraint itself is case-sensitive, so the check is in the app). Enforced on every way in through `api::tunnels::new_name_problem` (`{host_friendly_name: [msg]}`; taken = `NAME_TAKEN`, which the rename dialog matches on "already exists"): `POST /api/reverse/server/keys`, the wizard's `create/key/{token}` (its duplicate pre-check adds `host_friendly_name_problem`), renames (`PUT/PATCH …/keys/{id}` — **only a changed name** is checked, so an older name still saves its other fields; changing only your own case is allowed) and the one-command join (`--name` / the web name; a hostname becomes a name through `tunnel_name::suggest`, also used by `join::tunnel_name_from`). **Older non-conforming names keep working:** `scripts::render_client_config` writes `HostName localhost` / `Port <reverse_port>` for them (the gateway's loopback form), test `an_older_name_keeps_working_through_the_generated_config`. Frontend: `components/tunnels/TunnelNameHelp.tsx` under the name field of the create wizard, the join panel (`rulesJoin`: empty = hostname) and the details rename — the rules always visible, the offending characters named while typing with a one-click "Use …" (`suggestTunnelName`), a "Why?" popover with the reasons; an older name gets `SshNameChip` on cards / rows (opens the details) and a rename callout with the suggestion; copy under `tunnelName.*`. The lab names generated config files with `file_safe` (an older name may hold spaces).
- **Connection history + uptime (`db/tunnel_sessions.rs`, test `tests/tunnel_connections.rs`):** `telepy_tunnel_session` holds one row per forward (ip, connected_at, disconnected_at), opened next to `remember_endpoint` (closing any row still open for that tunnel) and closed in `remember_release`; rows left open are closed at startup (`close_orphans`, at the tunnel's last-seen time); ≤ 500 rows per tunnel, 90-day retention (`db::retention`, IPs), deleted with the tunnel. Uptime is pure math over those spans (`spans` / `covered` / `uptime` / `buckets`, unit-tested) counted **from the first recorded session** (before that there is no data, not downtime). `GET /api/reverse/server/{id}/connections` (anyone who can see the tunnel) → `{tracked_since, uptime {h24, d7}, hourly [24 × 0..1|null], sessions [20 × {ip, geo, public_ip, public_source, public_geo, connected_at, disconnected_at, seconds}]}`, IPs only per `permissions::can_see_endpoint`; MCP `tunnel_status` adds `uptime_24h`. **Behind an internal peer** (SSH-port devices behind Docker / OrbStack port publishing, an LB or a proxy all arrive from one internal address): `device_info::store` also writes the device-reported public IP onto the tunnel's open row (`tunnel_sessions::set_public_ip`, columns `public_ip` / `public_source`), so each row keeps where that connection really came from; web-port (WSS) devices already have a public `ip` via `ClientMeta`. Frontend: the "Connections" section of the tunnel page (`components/tunnels/TunnelConnections.tsx`, `hooks/useTunnelConnections.ts`): pure + tested `lib/connectionAddress.ts` picks direct / reported (shows the public IP with "Telepy saw <peer>") / internal, and "Why an internal address?" opens `PeerAddressDialog` (device ─ internet ─ the hop in front of the SSH port ─✗ source replaced ─ gateway, how the device's own report fills it in, admins: PROXY protocol / `GATEWAY_PROXY_PROTOCOL_FROM`); copy under `tunnelDetails.peer*`.
- **Personal key expiry (test `tests/key_expiry.rs`):** `authorized_keys_userauthorizedkeys.expires_at` (NULL = never) and the site setting `user_key_max_days` (0 = no limit; when set, new / renewed keys must expire within it and keys added without a date get the full lifetime). `POST/PATCH /api/reverse/user/keys` take `expires_at` as RFC 3339 or `YYYY-MM-DD` (end of that day, UTC; the web sends the end of the local day with its offset), validated by the pure `api::user_keys::{parse_expiry, check_expiry}`; serialised as `expires_at` + `expired`. Expired keys: `user_key_owner_by_prefix` ignores them, so the gateway refuses them and logs an `expired_key` event (Logs badge); `device_keys::desired` drops them, so the next sync (15 s tick) removes them from devices, and renewing puts them back; the create wizard leaves them out of the authorize command. Frontend: `lib/keyExpiry.ts` (tested presets / state), `components/keys/ExpiryPicker.tsx` in the add and details dialogs, `KeyExpiryText` on cards (amber within 7 days, red when expired) and a banner on the Keys page. No tunnel (device) key expiry on purpose: an expired device key would cut off a remote device that nobody can reach to renew it. **Admin import (`import_keys.rs`, `telepy-server import-user-keys <file.json> [--dry-run]`; test `tests/import_user_keys.rs`):** for moving personal keys onto accounts from inside the backend container (`docker exec telepy-web-<project> telepy-server import-user-keys /path/keys.json`) instead of touching the live SQLite from outside; input `[{username, name, key, expires_at?, description?}]`; the account must exist and be active; every entry goes through the API's own `api::user_keys::prepare_new` (`validate_full` → `checked_key`: parse / weak keys / taken by any user, comment ignored / tunnel or service key → `new_key_expiry` with `user_key_max_days`) and `insert_new` (unique name → `unique_error`); the same key already on that account = `already there`, not an error; `--dry-run` also checks names and in-file duplicates and writes nothing; output `#<n> <user> "<name>" <SHA256 fingerprint>: added | would add | already there | skipped: <reason>` + a summary line (fingerprints only, never key blobs), exit 1 when anything was skipped; each insert writes a tunnel-less `user_key_import` gateway event "<name> (<fingerprint>) added to <user> by import-user-keys". No hub notification or key-group placement (the key is on no device list yet).
- **Tunnel health (`monitor::health`, after Cloudflare's healthy / degraded / down / inactive; test `tests/tunnel_health.rs`):** `online` = forward up and the device's sshd banner comes back through it; `degraded` = forward up but `DEGRADED_AFTER` (2) probes in a row failed (`StatusState::record_probes` counts per port, reset on success) — sshd stopped, firewalled or hung behind a live tunnel; `offline` = connected before, no forward now; `never` = no connection on record (`telepy_tunnel_endpoint` ∪ forward/disconnect gateway events, because the endpoint table is newer than some tunnels). List items carry `health` and `last_seen_at` (time only, no IP, so every viewer gets them). The gateway writes `degraded` / `recovered` events (Logs page badges) and the runner pushes `UPDATE-TUNNEL-HEALTH {tunnel_id, port, health}` to the tunnel audience; MCP `tunnel_status` returns `health`. Frontend: `lib/tunnelHealth.liveHealth` merges the fetched `health` with the live `portsMap`; `TunnelStatusPill` / `StatusDot` (dot: solid green / amber / grey, dashed ring for never), `TunnelLastSeen`, open buttons look offline while degraded, a warning toast when a tunnel degrades.
- **Per-tunnel service keys (`ssh/tunnel_keys.rs`, `db/tunnel_keys.rs`; test `tests/tunnel_service_keys.rs` on the SSH lab):** every tunnel gets its own ed25519 service key pair on first use (`tunnel_keys::ensure`; private key sealed with the vault, AAD `telepy-tunnel-key:<id>`, in `telepy_tunnel_service_key`; public line `<type> <base64> telepy-tunnel-<id>`). The device authorizes only that key: the wizard's create response, the single retrieve (`service_key`), the join registration's `SERVICE_KEY` and the docker scripts all carry it. `ssh::device::connect` tries the tunnel's key first and falls back to the shared `SSH_IDENTITY` key (devices not migrated yet); a success with the tunnel key marks the account verified (`telepy_tunnel_key_account`, `DeviceConn.auth`). The key-list reconciliation installs the tunnel key into every login account and removes the shared key from an account only once **every tunnel on that machine** (same pinned host key) that lists the account has verified its own key there (`tunnel_keys::shared_removable`; event `service_key_migrated`); the device-keys view marks the shared key `legacy`, and `authorized-keys/remove` lets a manager remove it by hand under the same rule. `KEEP_SHARED_SERVICE_KEY=true` makes `shared_removable` always false (automatic and manual) — for a move where the previous Telepy server still logs in to the same devices with that key (`view.keep_shared` switches the legacy chip's tooltip). Deleting a tunnel always removes its own key from the device (`remove_service_key` now only governs the shared one). A tunnel's service key can be neither a device key nor a personal key. A changed `SECRET_KEY` makes the sealed keys unreadable: the backend falls back to the shared key and `doctor` warns (`tunnel keys`).
- **Device host-key pinning (`ssh/host_keys.rs`, `db/host_keys.rs`, `api/host_keys.rs`; test `tests/host_keys.rs`):** every backend connection to a device goes through `ssh::device::connect`, whose russh `check_server_key` compares the presented key with the tunnel's pins in `telepy_device_host_key` (cached in `state.host_keys`): nothing pinned → pin it (trust on first use, usually the backend's own login check right after the device joins; `host_key_pinned` event); pinned → allow; different → refuse the handshake (fail closed, also on a lookup error), store it as `rejected` with an attempt counter, and on the first sighting write `host_key_mismatch` and send `HOST-KEY-CHANGED` to the tunnel audience. The error starts with `device host key changed` (desktop maps it to `host_key_changed`). `GET /api/reverse/server/{id}/host-key` (VIEW) lists pinned and rejected keys; `POST …/host-key/accept {fingerprint}` and `DELETE …/host-key` are owner / ADMIN only (`host_key_accepted` / `host_key_forgotten`). List items carry `host_key_changed`; the UI shows a red chip on the card / row and a "Device identity" section in the tunnel page (fingerprint, how to check it on the device, Trust this key). Rows are deleted with the tunnel. The same pins go into the laptop's generated ssh config (see the SSH config dialog bullet), so laptops check the device too. LAN-host hops (OpenSSH from the backend to a LAN machine) are not pinned. **A pinned key is also the machine's identity (test `tests/machine_identity.rs`; `docs/device-connections.md` §七):** devices cannot tell Telepy users apart (one service key), so anyone who can point a tunnel at a machine's sshd could log in with their own tunnel's account list. Before pinning (first use, `accept`, join) `db::host_keys::claimants` looks up who else trusts the key: another account's tunnel → refused (error prefix `device managed by another account`, code `device_claimed`; `claim_refused` event on the refused tunnel, `claim_attempt` + `DEVICE-CLAIM-ATTEMPT` to the owner and ADMIN sharees, reported once per key, kept in memory as `refused_claim` / list `device_claimed`), your own other tunnel → pinned and listed as `same_machine`. The join script sends the device's host keys (`ssh-keyscan` → `host_keys`): a machine owned by another account is refused at registration (409), your own other tunnel comes back as `SAME_MACHINE_AS` (ticket `same_machine_as`, JoinPanel callout), and a new tunnel's keys are pinned at once (`source = join`). Device keys are unique across users (`api::reverse_keys::device_key_problem(state, key, owner)`: comment ignored, never another user's personal key or a service key — the owner's own personal key is allowed; the duplicate check returns `key_reason`, and `key_personal {id, name}` when the key is one of your own personal keys, which the wizard's step 1 shows as an info note), and the gateway's `direct-tcpip` needs owner / ADMIN / at least one allowed account.
