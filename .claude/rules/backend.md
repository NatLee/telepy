# Backend — general notes

## Module map (`src/backend-api/src/`)

```
      main.rs         # CLI: serve (default) | migrate | create-superuser | seed-service-key
      config.rs       # env → Config (same variable names as before: DEBUG, SECRET_KEY, REVERSE_SERVER_SSH_PORT, …)
      app.rs          # axum Router: REST (+compression) merged with /ws routes, CORS mirror, tracing
      db/             # sqlx over the Django-named tables; schema.rs = idempotent DDL (creates missing tables/columns, never alters existing)
      auth/           # jwt.rs, password.rs (Django pbkdf2_sha256), google.rs (JWKS), extractor.rs (Bearer → AuthUser; API tokens / OAuth app tokens → `Delegated`), api_tokens.rs (personal API tokens: REST allow-list, lookup cache)
      api/            # REST handlers per former Django app: auth, tunnels, usernames, user_keys, reverse_keys, scripts, sharing, users, site_settings, logs, sftp, remote_browser, browser (scripted browsers for tokens), api_tokens (+ call log, endpoint catalogue)
      ws/             # WebSockets: auth.rs (first-message JWT), notifications, tunnel_connection, terminal (PTY), filemanager (SFTP), remote_browser (KasmVNC relay)
      gateway/        # in-process SSH server: pubkey auth from DB, tcpip-forward registry (binds nothing locally; `open_stream` = in-process channel), direct-tcpip, status + latency probes, sshd-style log
      monitor/        # StatusState (listening ports / latency), ports.rs (debounce + latency throttle), runner.rs (5 s cycle → notifications)
      hub.rs          # in-process notification hub (per-user / per-tunnel broadcast; replaced the Redis channel layer)
      ssh/            # device.rs (russh client, in-process via the gateway), pool.rs (one shared connection per tunnel + OS account), terminal.rs (PTY channel per tab), socks.rs (remote-browser SOCKS5), bridge.rs (one-shot entry for the LAN hop), resolve.rs (macOS: resolve direct-tcpip names on the device), exec.rs, process.rs (OpenSSH for the LAN hop's last leg + PTY spawn)
      sftp/           # path resolution, structured listing, zip download, upload
      remote_browser/ # session store (in-process SOCKS over the pool), kasm session-manager client, reaper
      desktop/        # RDP / VNC over guacd: guac.rs (protocol codec + handshake), bridge.rs (guacd rendezvous ⇄ device direct-tcpip), sessions + tickets + reaper
      scripts/        # connection-script / ssh-config rendering ($var substitution, templates/)
      permissions.rs  # VIEW/EDIT/ADMIN hierarchy, allowed target usernames
      oauth/          # OAuth 2.1 authorization server logic for MCP clients (scopes, PKCE, redirect URIs, metadata)
      oidc/           # OIDC single sign-on as a relying party: mod.rs (pure: PKCE, authorize URL, id_token checks, usernames), client.rs (discovery / JWKS / code exchange), flow.rs (pending sign-ins, tickets, intents)
      mcp/            # MCP server at /mcp (rmcp, stateless Streamable HTTP): tools + bearer middleware
      ai/             # SSH sessions opened by AI agents: registry, exec/SFTP, expiry, reaper
      command_rules/  # command rules for the web terminal + MCP exec: shell matcher, vt100 line reader, approvals
      webhooks/       # personal + site-wide webhooks: event catalogue, localized sentences, per-service formats, signing, SSRF guard, delivery
    templates/        # ssh / autossh / systemd / PowerShell / docker scripts, ssh_config
    tests/            # integration tests (router in-process, real listener for WS, real OpenSSH client for the gateway); common/lab.rs = reusable SSH topology
```

## Notes

- **Status / latency:** forward registration and release update `StatusState` immediately; a banner round-trip through a forwarded channel every 15 s measures RTT. `monitor/runner.rs` runs the 5 s cycle (debounce FLAP_THRESHOLD 2, latency throttle 5 ms / 6-cycle keep-alive) and emits the `UPDATE-TUNNEL-*` notifications through the in-process hub.
- **WebSocket:** first frame `{type:"auth", token, …}` within 10 s; close codes 4000/4001 (auth), 4002/4003/4004/4005/4006 (terminal/file manager), 4010 (LAN terminal: the chosen saved login is missing / undecryptable), 4007 (2FA enrolment required), 4008 (step-up required), 4009 (ended from the live sessions page; reason = who), 4015 / 4016 (terminal: the shell to resume is gone / was resumed in another window), 4010 (this browser's sign-in was revoked; reason = user / admin / logout / reuse), 4012 (the feature is turned off for this person — terminal / LAN terminal / file manager / remote browser; reason = feature id), 4403/4404/4011/4013 (remote browser), 4404/4403/4011/4013/4014/4400 (remote desktop — no auth frame there: a one-time `?ticket=` and the `guacamole` subprotocol; the code is repeated as the close reason because guacamole-common-js only reads the reason), 4007 (the admin requires two-step sign-in and the account has not enrolled; every socket except `/ws/notifications/` — the desktop socket needs a ticket from the REST start, which is refused already). Terminal pong is a **binary** frame (so are the terminal's command-rule notices, see Command rules); the other sockets answer `{"type":"pong"}`. **Liveness:** the terminal, file-manager and remote-browser sockets read through `ws::Heartbeat` — a WebSocket Ping every `WS_PING_INTERVAL_SECS` (20; browsers answer on their own, background tabs too), and no frame within `WS_PEER_TIMEOUT_SECS` (40) of a ping ends the session; every send goes through `ws::send` (30 s timeout). Without it a client that vanished without a close frame (laptop asleep, network switch, dropped proxy) kept its session and its presence forever. Test helpers that read a socket must skip `Ping`/`Pong` frames.
- **Startup / health:** the backend creates missing SSH keys (`keygen.rs`: the gateway host keys in `GATEWAY_HOST_KEYS_DIR` — ed25519 + rsa — and the service key at `SSH_IDENTITY`, only when that variable is set; `ssh-keygen` when present, else russh ed25519; existing keys are never touched, a missing `.pub` is recomputed), reconciles the schema, seeds the `web-service` key from `/root/.ssh/id_rsa.pub` (the shared fallback key; new devices never get it), stops orphaned remote-browser sessions, starts the gateway and the monitor, then listens. `GET /api/auth/setup-status` is the public health endpoint used by the compose `healthcheck` and Traefik's `healthCheck`.
- **API docs (`api/doc.rs`, `api/schemas.rs`):** every REST handler carries a `#[utoipa::path]` attribute and each `api/*::router()` is a `utoipa_axum::OpenApiRouter` (`routes!`), so the OpenAPI document is generated from the real routes; `app::openapi()` returns it without state. Swagger UI is at `/api/__hidden_swagger`, the spec at `/api/openapi.json`; **both need a login** — the spec takes a Bearer token (`AuthUser`), the page is a same-origin shell whose initializer verifies/refreshes the frontend's localStorage token and redirects to `/login` otherwise (`OPENAPI_ENABLED=false` removes them). Handlers still return `serde_json::Value`, so the `schemas.rs` structs are documentation only — **when you change a response/request shape, update the matching struct** (and `tests/openapi.rs` asserts the key paths/security). A PUT+PATCH pair needs two handler fns (`update` + `replace`), one per `#[utoipa::path]`.
- **Logging:** `tracing` → stdout + daily rolling `/logs/telepy.log` and `/logs/error.log` (a bare `LOG_LEVEL=debug` silences sqlx/hyper/russh internals; pass a full EnvFilter directive to override). Gateway events (accepted / forward / disconnect / refused …) go to the `telepy_gateway_event` table (capped at 100k rows; 90 days via `db::retention` — rows carry source IPs) and are also appended sshd-style to `/logs/ssh-gateway.log`; `/api/log/ssh/events?limit=&tunnel_id=` returns them as JSON (what the Logs page uses; oldest first) and `/api/log/ssh` renders the last 500 as sshd-style text (200 with an empty string when there are none). **Both are scoped by `?scope=`:** `mine` (default, **admins too**) = events of tunnels you own or that are shared with you (a foreign `tunnel_id` is a 404, except that an admin may name any tunnel); `all` = admins only (403 `admin_only`): every event incl. the tunnel-less ones (`listening`, groups, tokens…; `tunnel_id=none` = only those). Events carry `tunnel_name`; `GET /api/log/tunnels` (admins) lists every tunnel with its owner for the admin filters. The Logs page (`/tunnels/logs?tunnel=<id>`, mine) and the admin section's **Audit log** (`/tunnels/admin/logs`, all: owners in the tunnel select, a "Site events" choice / chip, Verify integrity) share `components/logs/LogsView.tsx` (`useLogsPage(scope)`); keeps the tunnel filter in the URL and the tunnel actions menu deep-links to it; event badges key off the structured `event` field (`logs.event.*` i18n keys), not message text; the kind → badge tone / category table (needs attention / connections / sessions / settings & actions) and the filters are pure helpers in `lib/gatewayLogs.ts` (`gatewayLogs.test.ts`) — add every new gateway event kind there. **Day-grouped event lists** (the Logs and AI activity pages) share `lib/timeline.ts` (local day keys, today / yesterday headings, search-hit segments; `timeline.test.ts`), `components/ui/timeline.tsx` (`TimelineDay`, `Highlighted`) and `hooks/useStickyBar.ts`: the page scrolls as a whole (no inner scroll box — the card is `overflow-clip`, which keeps sticky working), the filter bar sticks under the header from `sm`, each day heading under the bar (`--sticky-bar`, measured), and "Load older" raises `limit` (Logs: steps of 500 up to 5000); a refresh / load keeps the list and the scroll position, and the end text waits until the larger page arrived. **Tamper evidence (`db/audit_chain.rs`; tests in the module + `tests/audit_chain.rs`):** `telepy_gateway_event`, `telepy_sign_in_event` and `telepy_ai_audit_event` are SHA-256 hash chains (`prev_hash` / `hash` = length-prefixed fields + row id + previous hash; pre-upgrade rows stay NULL and count as `unhashed_before`); **every insert goes through `audit_chain::append`** (per-table mutex, one transaction) and every delete through `audit_chain::prune_through`, which first writes a `prune` row to `telepy_audit_anchor` so verification resumes from it. **Database identity in the anchors file:** each DB has a random chain id (a `kind='chain'` row in `telepy_audit_anchor`, created idempotently by `ensure_chain_id` before the first checkpoint) and every checkpoint line carries it as `db`; verification skips lines of another database (`checkpoints_foreign`) and still compares lines without `db` (written before) — a DB restored / replaced under the same log dir used to report `checkpoint_mismatch` on rows of the old one (production 2026-10-30, row 58). `TableReport` also has `chain_broken_at` / `chain_reason` / `chain_issues` and `checkpoint_broken_at` / `checkpoint_reason` besides the first-issue `broken_at` / `reason`. The chain heads are appended every 10 min and after each prune to `<log_root>/audit-anchors.log` (JSON lines; ship it elsewhere) plus a `checkpoint` anchor row, so a fully recomputed chain is still caught; `GET /api/log/audit/verify` (superusers) walks all three tables and those checkpoints, and the Logs page's "Verify integrity" action shows the result (plus each table's last re-seal and the lines it set aside). **Re-seal (`audit_chain::reseal` / `reseal_plan`, `split_retired` pure; `GET /api/site/health/audit` = dry run, `POST /api/site/health/audit/reseal {fingerprint, note, reauth?}`; tests `tests/audit_reseal.rs` + unit tests incl. 100k rows):** once an admin knows why the chain fails (restored / replaced database, a known edit), the failing tables are re-hashed from the rows as they are (`rehash` walk from the newest prune anchor; edited rows are **not** changed back), and the anchors file gets a `reseal` line (`CheckpointLine.reseal` id + `by` + `note`; the table's head) — verification then sets aside every earlier line of that table (`checkpoints_retired`) and compares from the reseal line on. A reseal line only counts when `telepy_audit_reseal` has the same id (one row per table: rehashed, from_row, retired, the doctor's problem text, who, note; kept for good), so a hand-added line does nothing. Order per table under its head lock: re-hash in a write transaction → append the file line → insert the record → commit (a failed file write rolls back; a line left by a failed commit is unknown to the DB). The endpoint needs superuser + note (1–500) + reauth + the audit-log fingerprint the page showed (409 `changed`, 400 `not_a_problem` unless it fails) and writes an `audit_reseal` gateway event after the new head; any later edit — before or after the re-seal — fails the check again. Not offered by the CLI (the server's cached chain heads would go stale). Frontend: `components/health/AuditResealDialog.tsx` (the card's "Re-seal…" next to Acknowledge; path found ─ re-seal ─ new baseline ─ on record ─ red again, per-table plan, when-to-use / what stays callouts, earlier re-seals paged 5 / 10 / 25 in `telepy.resealHistoryPageSize`), pure + tested `lib/auditReseal.ts`; copy under `health.reseal.*`.
