# Device info — GeoIP, addresses, platform facts, public IP

- **GeoIP + IP-change alerts (`geoip.rs`; tests in `geoip.rs`, `tests/tunnel_endpoint.rs`):** `GeoIp::load(GEOIP_DIR)` reads DB-IP Lite (`dbip-country-lite` / `dbip-asn-lite`) or MaxMind GeoLite2 mmdb with `maxminddb` (readers behind an `RwLock`, `GeoIp::reload` / `Oui::reload` swap them without a restart; nothing is ever sent to an outside service; no files = scope only). **Keeping them current (`datasets.rs` `Datasets` in `state.datasets`, `api/datasets.rs`; test `tests/datasets.rs` against fake DB-IP / IEEE servers with a hand-built tiny mmdb; frontend `components/health/DatasetsPanel.tsx` on Server health → Companion services (`#datasets`), `hooks/useDatasets.ts`, pure + tested `lib/datasets.ts`, copy under `datasets.*`):** `datasets::run` wakes hourly — `pick_up_changes` reloads whatever changed on disk (size / mtime; the CLI subcommands, hand-placed files) — and with the site setting `datasets_auto_update` (default on) looks at most once a day (`check_due`): an *installed* DB-IP file whose month (`<file>.release`, else the mmdb's `build_epoch` month) is not this month gets this month's (`dbip_candidates`: this month then the previous one, never the installed one; 404 = not out yet, `current`), the vendor table is fetched again after `OUI_REFRESH_DAYS` (30); never-installed data is never downloaded on its own, MaxMind files are never replaced. Files are checked (mmdb opens / csv header) and written beside then renamed. Admin API `GET /api/site/datasets`, `POST /api/site/datasets/update {items?: country|asn|oui}` (superusers, 403 `admin_only`, 409 `busy`; runs in its own task so closing the tab doesn't cancel it); audit events `datasets_updated` / `datasets_update_failed` (an automatic failure once per distinct error). Doctor `geoip` / `oui` warn when the data in use is older than 70 / 120 days (`geoip_freshness` / `oui_freshness`, fingerprint = the build date). Test apps point `geoip_dir` / `oui_dir` at their temp dir (`tests/common`), and `Datasets::set_sources` points downloads at a fake server — tests never reach db-ip.com. `GeoIp::json(ip)` = `geo {scope, country, org, asn, source}` next to the device `endpoint`, presence sessions and sign-in rows; `scope` (public / private / loopback / link_local / shared_nat / reserved) is pure std classification — a non-public device IP means a proxy / LB / Docker forward hides the real source, and `TunnelEndpointChip` warns about it. `db::tunnel_endpoints::record_connected` keeps `previous_ip` / `changed_at` (one SQLite upsert with `CASE`) and returns `IpChange`; the gateway's `remember_endpoint` then writes an `ip_changed` event and sends `TUNNEL-IP-CHANGED {tunnel_id, tunnel_name, ip, previous_ip}` to the owner and ADMIN sharees, plus the `tunnel.ip_changed` webhook event (`AppState.hub` and `AppState.webhooks` are shared with the gateway; `with_gateway` takes them from `Gateway::hub()` / `Gateway::webhooks()`). Frontend: `lib/geo.ts` (flag emoji, `Intl.DisplayNames` country names), `components/ui/IpPlace.tsx`, a warning toast on the tunnels page, `logs.event.ip_changed`; attribution "IP geolocation by {source}" in tooltips (DB-IP Lite is CC BY 4.0).
- **Device addresses (`device_info.rs`, `api/whoami.rs`; tests in `device_info.rs`, `tests/tunnel_endpoint.rs`, `tests/sign_ins.rs`):** the gateway's peer is often a proxy's or Docker's internal address (OrbStack / Docker Desktop rewrite published-port sources), so `device_info::run` (30 s loop, started with the gateway unless `DEVICE_PROBE=false`) logs in to each **connected** device that is due (`db::tunnel_endpoints::probe_due`: not asked during this connection, or > 24 h ago; 10-minute per-tunnel cool-down; failures are recorded too, so nothing retries in a loop) with the service key as the tunnel's default (else first) account and runs one read-only script (`sh -c`, else PowerShell): `hostname`, the interfaces (`ip -o -4 addr` / `ifconfig` / `Get-NetIPAddress`, parsed by `lan::parse_networks`) and — only when the peer is not public — `curl`/`wget` of this server's own **`GET /api/whoami`** (public, text/plain, the caller's IP resolved like sign-ins; `PUBLIC_URL`, else `https://SERVER_DOMAIN`). When whoami's answer is not public either (a proxy / Docker in front of Telepy rewrites client addresses — e.g. a TLS proxy whose own Docker hands everyone its bridge address — or the device shares Telepy's NAT), a second exec asks the site setting **`device_ip_lookup_url`** (default `https://api.ipify.org`, blank = never ask a third party; must answer the caller's IP as plain text; only `device_info::safe_url` characters because it goes into the device's shell / cmd.exe, checked on save); the non-public whoami answer is only logged. The endpoint row keeps `hostname`, `lan` (JSON), `probed_at`, `probe_error`, and `public_ip` + `public_source` (`gateway` when its peer is public, `device` = whoami, `lookup` = the lookup URL). **IP-change detection runs on `public_ip`** (`update_public_ip` → `Gateway::announce_ip_change`: `ip_changed` event, `TUNNEL-IP-CHANGED`, webhook), not on the raw peer. List items carry them in `endpoint`; the UI shows `TunnelEndpointChip` (tagged "Public" / 外網: the public IP; the peer only when that is public; otherwise "unknown" with ⚠ and why in the tooltip — never the proxy's / Docker's address dressed up as the device's) and `TunnelLanChip` (tagged "LAN" / 內網: LAN IP, hostname + interfaces on hover). Test with a real shell + curl against a fake upstream: `device_asks_the_lookup_when_whoami_sees_an_internal_address`.
- **Device facts (`device_facts.rs` pure + unit tests, wired in `device_info.rs`; tests `device_facts_and_refresh_now` in `tests/tunnel_endpoint.rs` on a real-shell lab machine, `lib/deviceFacts.ts` + test):** no extra login or loop — the same daily script has a fourth `@@telepy@@` section (`device_facts::POSIX_SCRIPT` / `WINDOWS_SCRIPT`, every command optional and `timeout 1` where it exists; no `"` / `%` in the PowerShell part, it sits inside cmd.exe's `-Command "…"`) printing `KEY=value` lines: OS (`/etc/os-release` / `sw_vers` / `Win32_OperatingSystem`; else the kernel), `uname -sr` / `-m`, uptime (`/proc/uptime`, `now` − `kern.boottime`, `LastBootUpTime`), CPU model (`/proc/cpuinfo` → `lscpu`, `machdep.cpu.brand_string`) + count, memory (`/proc/meminfo`, `hw.memsize` + `vm_stat` free+inactive+speculative), `df -Pk /` (Windows `Get-PSDrive C`), load (`/proc/loadavg`, `vm.loadavg`; none on Windows), `ssh -V` (only a version line counts), reboot pending (`/var/run/reboot-required`, Debian family only, else null). `parse_facts` → `Facts` with `warnings` computed at store time (`device_facts::warnings`: root disk < 10 % or < 2 GB free (`disk_floor_kb`: the 2 GB floor is capped at half the disk, so a router's 100 MB root is judged by the percentage), memory < 10 % available, load1 > 2 × CPUs, reboot pending), stored as JSON in `telepy_tunnel_endpoint.facts` + `facts_at` (a failed read keeps the old facts and sets `probe_error`). Served as `endpoint.facts` / `facts_at` in list items **and the single retrieve** (same `can_see_endpoint` gate) and in MCP `tunnel_status` (`facts`, `warnings`). After every store `DEVICE-FACTS-UPDATED {tunnel_id}` goes to the tunnel audience; each warning kind is announced once per tunnel per 24 h (`DeviceInfoState::should_warn`, in memory, `state.device_info`): a `device_warning` gateway event, `DEVICE-WARNING {tunnel_id, tunnel_name, warnings, details}` to owner + ADMIN sharees and the `tunnel.device_warning` webhook (same audience, also site-wide). **Refresh now:** `POST /api/reverse/server/{id}/probe` (owner / ADMIN; 409 `device_offline`, 429 `too_soon` + `retry_after`, 1 per minute per tunnel) runs the same script over `ssh::pool` (`device_info::probe_pooled` / `refresh`) and answers the fresh endpoint. Frontend: the tunnel page's Device section (`components/tunnels/DeviceFacts.tsx` + `hooks/useDeviceFacts.ts`: PropertyList with memory / disk bars, warning callouts, "checked … ago · next …", Refresh with a cool-down) and its info button (`DeviceFactsInfoDialog`: Telepy ─ daily login ─ device ─✗─ elsewhere, last / next run, the exact commands (`COMMANDS_POSIX` / `COMMANDS_WINDOWS` in `lib/deviceFacts.ts` — keep in sync with the scripts), thresholds with the current value); `DeviceWarningChip` on cards / rows; search `warn:disk|memory|load|reboot|any`; a warning toast on the tunnels page; copy under `deviceFacts.*`.
- **Device public IP (`endpoint`):** every list item (`/keys`, `/dashboard`) and the single-tunnel retrieve carry `endpoint {ip, live, connected_at, last_seen_at}` = the TCP source the gateway saw. Live values come from `StatusState::endpoints()` (set in the gateway's `publish_status` from `ConnInfo`); the last known one is one overwritten row per tunnel in `telepy_tunnel_endpoint` (written on forward register / release, deleted with the tunnel). **Visibility follows device access, not the VIEW/EDIT label** (`permissions::can_see_endpoint`): owner, ADMIN, superuser, or a sharee with ≥1 allowed username — anyone who can open a shell there can `curl ifconfig.me` anyway; status-only sharees get `null`. Never put it in the unscoped `ports`/`latency` maps. Behind an L4 proxy (or Docker userland-proxy / Docker Desktop) the gateway sees the proxy's address. The frontend (`TunnelEndpointChip`) reloads the list quietly after `UPDATE-TUNNEL-STATUS`.
