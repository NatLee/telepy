# Client IP, sign-in history, IP retention

- **Client IP + sign-in history (`client_ip.rs`, `api/sign_ins.rs`, `db/sign_ins.rs`; test `tests/sign_ins.rs`):** `ClientMeta` (extractor; `from_parts` / `from_headers` for WS and MCP) = IP + User-Agent. The IP walks `X-Forwarded-For` **from the right**: chain = XFF entries + socket peer (`ConnectInfo`, enabled in `main.rs`), skip `TRUSTED_PROXY_HOPS` — the leftmost entries are client-controlled, never take them; `CLIENT_IP_HEADER` wins when present. Every login path records one `telepy_sign_in_event` row through `sign_ins::record` (best effort): password / google / passkey, with the second factor (`LoginChallenge.first_factor` carries the first one into `mfa_verify`); failures for existing accounts only (`bad_password` / `inactive` / `mfa_failed` / `google_account_conflict`); 100k rows, 90 days via `db::retention`. `GET /api/auth/sign-ins` (own) and `GET /api/user/users/{id}/sign-ins` (admins) feed `components/layout/SignInHistory.tsx` (Security tab of the preferences modal, admin Manage-user modal; `lib/userAgent.ts` shortens the UA). **Every** request-side IP (sign-ins, web sessions incl. renewals and `note_use`, presence of web sockets, the API call log, MCP / AI audit via `McpPrincipal.ip`, the gateway-over-WebSocket, `/api/whoami`) goes through `ClientMeta` — never read `ConnectInfo` or `X-Forwarded-For` directly; a renewal or use without an address keeps the stored one (`COALESCE`). Laptop SSH presence uses the gateway peer (see PROXY protocol). **Diagnosing it (`client_ip::diagnose`, pure + unit-tested; `GET /api/auth/client-ip-check`, superusers, 403 `admin_only`; tests in `tests/sign_ins.rs`):** the same rule spelled out — `chain [{ip, scope, source: forwarded_for|peer, role: ignored|client|proxy}]`, the address headers present (`CANDIDATE_HEADERS`: X-Real-IP, Forwarded `for=`, CF-Connecting-IP, True-Client-IP, … plus `CLIENT_IP_HEADER`; also CloudFront-Viewer-Address, X-Azure-ClientIP, Fly-Client-IP, DO-Connecting-IP — CloudFront's is `address:port` with an unbracketed IPv6, so `part_ip` always cuts its last `:port`), `ip` / `scope` / `from: chain|header`, `trusted_proxy_hops`, `client_ip_header`, `verdict` (`ok` / `hops_too_low` / `hops_too_high` + `suggest.trusted_proxy_hops` / `use_header` + `suggest.client_ip_header` / `header_private` / `all_private` = the proxy in front already lost the address, nothing in Telepy can fix it / `unknown`), `short_chain` (fewer proxies than configured: the leftmost, client-writable entry is used) and `header_absent`. Frontend: Admin → **Server health** → "How Telepy sees your address" (`components/auth/ClientIpCheck.tsx`, `#client-ip` on `/tunnels/admin/health`; the Sign-in tab only points there; pure + tested `lib/clientIp.ts`): verdict, the hop path on `PathFlow` (always a column of `compact` rows; from a 56rem card (container query) it sits left and the right column holds verdict + fix, then the values — grid rows `auto 1fr` so no gap opens between them; the made-up-address test joins the right column unless the fix list shows), the proxy fix list for `all_private` (never suggests `CLIENT_IP_HEADER` there — a CDN header with a public address would be `use_header`; with no CDN header at all (`lib/clientIp.viaCdn`) it says the request did not pass a CDN, e.g. a Cloudflare record set to DNS only, plus "check from outside your network" for NAT loopback; a spoofable X-Real-IP under `all_private` is explained as the same cause), the raw values, and "Try a made-up address" (re-runs the check with `X-Forwarded-For: 203.0.113.77` + `X-Real-IP: 203.0.113.78`; Telepy recording either = a visitor can choose their address: `.78` = the proxy in front trusts X-Real-IP (nginx `real_ip`, Nginx Proxy Manager's default), `.77` = hops too high). `IpPlace` shows a non-public client address as a warning "Internal address" chip with a popover explaining it (admins get a link to the check) instead of a place. `telepy-server doctor` warns ("client addresses") when the last 50 sign-ins of 30 days all came from internal addresses. **`TRUSTED_PROXY_HOPS` is `client_ip::Hops`** (`Auto` default — `chosen_index` takes the rightmost public entry, none public = the leftmost; `Fixed(n)`); `Hops::parse` reads the env (unset / blank / `auto` / junk = auto); the check JSON carries `hops_mode`, `trusted_proxy_hops` (null in auto), `skipped_hops`, and in auto a public address left of the chosen one is `hops_too_low` (a public-IP proxy in front — the admin's own browser sends no XFF, so not a spoof) with a fixed count suggested; the made-up-address probe in auto with the admin on an internal address = `auto_internal` (only internal visitors, only their own record). Tests use `common::spawn_with(|c| c.trusted_proxy_hops = Hops::Fixed(1))`. **Server health (`doctor.rs` `run_with(config, Result<Db, String>, audit_max_age)` — no side effect on the caller's Db (the CLI's `run` sets the anchors file on its own Db); independent checks run at the same time (`tokio::join!`: DB, keys, DNS, guacd + kasm, GeoIP / OUI reads on `spawn_blocking`, client addresses, the audit chain), so a run takes as long as its slowest check and the order stays fixed; `api/health.rs` `GET /api/site/health` superusers, 403 `admin_only`; `api/health_stats.rs` + `db/server_stats.rs` `GET /api/site/health/stats` (same gate, cheap: no device round-trip, no chain walk); tests `server_health_runs_the_doctor_checks_for_admins` in `tests/sign_ins.rs`, `tests/server_stats.rs`, unit tests in both modules; frontend `app/tunnels/admin/health/page.tsx`, `components/health/` — `ServerHealthView` (tabs + check cards + the overview's status card), `ServerStats` (`LiveNumbers` / `StoragePanel` / `ActivityPanel`) + `StatsHourlyChart`, `ServerHealthInfoDialog` + `ServerHealthFlow` (info diagram) —, `hooks/useServerHealth.ts` / `useServerStats.ts`, pure + tested `lib/serverHealth.ts` / `serverStats.ts` / `serverHealthFlow.ts`):** the `telepy-server doctor` checks on the backend's own open DB — `{checks [{id, name, status: ok|info|warn|fail, detail, checked_at?}], ok, info, warnings, failures, ran_at}`, rerun on every call (no polling). **The audit chain is verified in the background** (`audit_chain::run`: after every 10-minute checkpoint, `verify` walks the three tables in parallel — one spawned task + read connection each — and remembers the `Report` in `db.audit` — `AuditChains::last_verified` / `forget_verified`, the latter at the start of every `reseal`); `GET /api/site/health` reuses it when younger than `VERIFIED_FRESH` (11 min; `verify_recent`, else verifies inline) and the audit check carries `checked_at` = that verification's time, `?fresh=1` (the page's Refresh) verifies now, ack / unack reruns reuse it (same fingerprint the page showed), the re-seal dry run and re-seal verify fresh. Measured on a release build with 300k audit rows: opening the page ~0.93 s → ~55 ms (`/stats` ~25 ms, fetched alongside); a fresh walk (Refresh, the Logs page's Verify) still takes ~1 s, mostly SQLite reads. **Every check has a stable `id`** (`doctor.rs` `check(id, …)` ↔ `lib/serverHealth.ts` `CHECK_IDS`; older answers are recognised by name) that puts it in a group (`GROUP_OF`: config / storage / keys / services / addresses) and picks its copy `health.check.<id>.{title,what,fix}` — when adding a doctor check, add the id on both sides, its group and the three keys. The page has side tabs in `?tab=` (`NavTabs`: a sticky rail once the page itself is ≥ 56rem wide — measured with a ResizeObserver in rem, so it follows the display size; at 1024 px / 130 % a `lg` rail left the content ~260 px —, else a one-line row that scrolls sideways; overview + one per group, each with a status dot and a problem count): **Overview** = a status card (verdict + counts, version / uptime from `/stats`, one cell per group, when it ran — `lib/serverHealth.auditReusedAt` adds the audit chain's own time when the background result was reused), "Needs attention" (warn / fail with a link to their tab), then the live numbers, storage and the last 24 hours. The page fetches `/health` and `/stats` at the same time (`useServerStats` lives in the view) and every block draws as soon as its own data is in (skeletons meanwhile), so the overview never waits for the checks; a group tab = one card per check (failures first: translated title + what it checks, a "How to fix" callout for warn / fail and "If you want it" for notes, the backend's detail verbatim under "Server said"); **Visitor addresses** ends with the address check (`CLIENT_IP_CHECK_HREF` = `?tab=addresses#client-ip`; an old bare `#client-ip` link lands on that tab). `client_addresses` warns when every recent sign-in is internal, but a loopback-only history (signing in on the server itself) is a note. **Acknowledging (`db/health_acks.rs` `telepy_health_ack` one row per check id, `doctor::apply_acks` pure; `POST /api/site/health/ack {check_id, fingerprint, note 1–500, reauth?}` / `DELETE /api/site/health/ack/{check_id}`, both answer the health JSON; test `tests/health_ack.rs`; frontend `components/health/HealthAckDialog.tsx`, pure + tested `lib/healthAck.ts`):** an admin can quiet a known warning / failure with a note. Every check carries a `fingerprint` (`doctor::fingerprint`, short SHA-256 of id + status + detail, or of the stable parts where the detail has moving numbers / OS error text: database, tunnel_keys, client_addresses, guacd, kasm) and an ack holds only for that fingerprint: `ack {by, at, note}` while the result is the same, `stale_ack` once it changed (red again, "acknowledged an earlier result"), and it is deleted when the check turns ok / info. POST reruns the checks: 400 `not_a_problem`, 409 `changed` (fingerprint differs), reauth once the account has a factor; POST / DELETE write a tunnel-less `health_ack` gateway event (into the hash chain). Acknowledged problems leave "Needs attention", tab dots, tiles and the info diagram (grey "Acknowledged" card with the note, Undo, details folded); top-level `acknowledged`; the CLI suffixes "(acknowledged by …)" and doesn't fail on them. The audit_log fingerprint = `audit_chain::fingerprint(&Report)` over each failing table's chain issue + count, first checkpoint issue and `checkpoints_mismatched`, so a later edit / recompute / truncation of the same table changes it — and the detail lists the chain problem and the checkpoint problem separately (`doctor::audit_problem`), so a new edit never hides behind an old checkpoint mismatch. A failing `audit_log` card also offers **Re-seal…** (see Logging → Re-seal): it fixes the chain instead of only quieting it, and an acknowledgement of the old result goes once it passes. **Live block (`/stats`):** `{server {version (only `TELEPY_VERSION`-stamped builds, else null — the crate's 0.1.0 is no release number), started_at, uptime_secs, now}, tunnels {total, online, degraded, offline, never} (= `monitor::health`), gateway {connections, forwards}, sessions {total, by_kind} (presence; agents are `ai` / `browser` there), users {total, active, admins, signed_in_24h}, storage {db_bytes, wal_bytes, data_dir {path, free_bytes, total_bytes} (nix statvfs) | null, recordings_bytes, logs_bytes, carriers_bytes (`CARRIER_DIR`), geoip_bytes (`GEOIP_DIR`), oui_bytes (`OUI_DIR`) (+ `*_truncated` each; walks capped at 20k entries in `spawn_blocking`)}, activity {hours, gateway_events / gateway_problems (the Logs page's problem kinds, `PROBLEM_KINDS`), sign_ins / sign_ins_failed, api_calls / api_errors: 24 hourly buckets, oldest first, subsets included in their totals}, webhooks {total, enabled, paused, failing_recent}}` → tiles (tunnel status bar, sessions per kind, accounts, webhooks), storage = the data disk meter (warning under 10 % free) beside "What Telepy keeps": a one-colour bar list, largest first, sizes printed (pure `lib/serverStats.storageParts`: database, WAL, recordings, logs, device carriers, IP and vendor data = GeoIP + OUI; a stacked bar was rejected — the parts differ by orders of magnitude and the chart palette fails the CVD check), carriers / IP data rows open their panels on the services tab, recordings the admin recordings page; and three hourly bar charts with keyboard tooltips and an sr-only table per chart (wrapped in an `sr-only` div — a table ignores the 1px width and widened phones); a 404 (older backend) renders nothing; Refresh reloads both. **Info button** ("How it works") = `ServerHealthInfoDialog`: visitor ─ proxy / Traefik ─ Telepy backend ─ data on disk, with the gateway (→ devices, not checked), guacd, kasm-browser and GeoIP + OUI beside the backend; each part lit by its checks (`HealthSpotState` adds `warn`), a click opens its tab, "Right now" names the first failing / warning part along the path with that check's own text, then what each part checks and what breaks. `IpPlace`'s "Internal address" chip links admins there and its hint says nothing about proxies / Docker (a user can't act on it); copy under `health.*` (`health.check.*`, `health.stats.*`, `health.flow.*`). Copy under `clientIp.*` / `geo.internal*`.
- **IP retention (`db/retention.rs`):** gateway events, sign-ins and AI audit rows carry IPs; an hourly task deletes rows older than 90 days (row caps stay with each insert).
