# Access model — permissions, roles, timed sharing, access requests, step-up

- **Target accounts dialog ("Manage target users", `components/tunnels/ManageUsersModal.tsx`, `hooks/useManageUsersModal.ts`, pure + tested `lib/targetUsers.ts`):** `GET /api/reverse/server/{id}/usernames` also returns `can_manage`, `admin_sharees` and per account `shared_with` (sharees whose unexpired allow-list holds it, `db::sharing::allowed_counts`; owner / ADMIN only, else null). The dialog sorts the default first, has search (account / who added it) + buckets (all / shared / not shared / default) from 7 accounts, pages through `usePagination` (`telepy.targetUsersPageSize`), a ★ per row to set / clear the default (`PATCH …/default-username`), and "What are these accounts for?" → `TargetUsersInfoDialog` (Telepy users ─ allow-list ─ accounts ─ the device's sshd with live counts, plus what / who / default / keys / remove). Copy under `manageUsers.*`.
- **Permissions:** hierarchical tunnel access — VIEW / EDIT / ADMIN — in `permissions.rs`. Target OS accounts (usernames) are managed only by the owner and ADMIN sharees (unique per tunnel); every other sharee may use **exactly** the allow-list the owner/ADMIN set (empty = none — creating a row never grants it). `permissions::allowed_usernames` is the single gate for terminal, files, SFTP, remote browser, scripts and MCP: the device can't tell Telepy users apart (every backend login to a device uses that tunnel's service key), so this list is the only boundary.
- **Tunnel identity is owner / ADMIN only (`api/tunnels.rs` `apply_update` / `single_json`, `api/serialize.rs`, `api/scripts.rs` `may_get_scripts`; test `tests/tunnel_identity.rs` on the SSH lab):** a sharee's job is to connect, not to look after the tunnel, and public keys add nothing to that. The device key (`key` in every tunnel JSON) and the tunnel's own service key (`service_key` in the single retrieve) are null for everyone below ADMIN; the connection scripts (`/tunnels/server/script/{kind}/…`, `POST …/one-time/token`, and the one-time URL itself, re-checked on use) answer 403 below ADMIN — the ssh config (`/tunnels/server/config*`) stays VIEW because sharees need it. **Changing the device key or `reverse_port`** (PUT / PATCH `/api/reverse/server/keys/{id}`) needs owner / ADMIN (EDIT keeps name, description and default account; sending the current value is not a change — a new key would point the tunnel at another machine). A new key goes through `reverse_keys::device_key_problem_except` (the create rules, its own tunnel excepted); a new key (not just a new comment) or port needs `reauth` once the account has a factor, writes `device_key_changed` (fingerprints only) / `reverse_port_changed` and drops the live connection (`Gateway::disconnect_tunnel_because`). Frontend: the tunnel page's key section only for managers (`canChangeKey`; others get `tunnelDetails.keyManagersOnly`), a key change asks to confirm (`useReauth`), the install-script menu item shows for `can_share`, and the terminal's service-key window explains (`terminal.serviceKeysManagersOnly`) instead of falling back to the shared key.
- **Feature permissions / roles (`features.rs` pure + cache, `db/features.rs`, `api/access.rs`; tests `tests/features.rs` + `roles_never_share_and_groups_never_decide_features` in `tests/group_shares.rs` on the SSH lab + unit tests; frontend `lib/features.ts` (tested), `hooks/useFeatures.ts`, `hooks/useAccessPage.ts`, `components/access/`):** which Telepy *tools* a person may use — orthogonal to tunnel sharing (which decides *which tunnels*); both gates apply, the feature first. Fixed enum `features::Feature` (`tunnels.create`, `tunnels.share`, `terminal`, `toolbox` (snippet writes + the Toolbox panel / menu / dock button; running a snippet still needs `terminal`), `files`, `remote_browser`, `remote_desktop`, `network`, `keys.personal`, `recordings.manage`, `command_rules.manage`, `webhooks.personal`, `mcp.connect`, `api.tokens` (personal API tokens; off = they stop working), `api.docs`; all default on, so upgrades change nothing). Tables `telepy_user_group` (people — not the tunnel / key groups of #229 — split by job with `owner_id` + `purpose`: **roles** `owner_id` NULL + `purpose = 'role'` (admins / SSO rules / SCIM; feature permissions only, **never** a share target; name in `name`, unique among roles ignoring case), **admin-kept groups** `owner_id` NULL + `purpose = 'group'` (admins / SSO rules / SCIM; sharing only) and **personal groups** `owner_id` = their maker + `purpose = 'group'` (sharing only); both group kinds keep their shown name in `display_name` because `name` is UNIQUE table-wide and holds a `group:<random>` / `personal:<owner>:<random>` placeholder (`db::features::placeholder`) — always show `Group::label()` / SQL `db::features::LABEL`; `shareable` is dead since the split (column kept, nothing reads it); see **Sharing with groups**), `telepy_user_group_member` (shared by all three), `telepy_feature_grant` (`subject_kind` user / group / everyone, `allowed`; no row = inherit; `group` = a role). The helpers say which kind they read, so callers never filter: `db::features::{groups, group, name_taken, create_group, update_group, memberships, groups_of}` = **roles only**; `{share_groups, share_group, share_group_name_taken, create_share_group, update_share_group}` = **admin-kept groups only**; `personal_group(s)` = the owner's personal groups; `sharing_group` = admin-kept or personal, never a role (callers still check `Group::shareable_by` — personal → owner only, admin-kept → anyone, role → **false**); `sso_targets` / `sso_groups_of` = roles + admin-kept groups; `grants()` drops `group` rows that don't point at a role (defence in depth). So a group can never get a grant, appear among roles on the access page or affect `end_denied_sessions`, and a role never appears in sharing JSON. Resolution (`features::resolve`, mirrored by `lib/features.ts` `resolveFeature`): superuser = everything → the user's own row (the leaf) → their roles (a deny in any role wins, else an allow; roles in id order for a stable source) → everyone → default. `Features` (owned by the gateway, shared as `state.features`) caches the whole policy ≤ 5 s, invalidated on every write. **One check, `features::check(state, &User, f)`** (403 `{error, code: feature_disabled, feature}`) for any principal: the `AuthUser` extractor maps the route with the pure `features::for_route(method, path)` (unit-tested table — add new routes there; stop / ping / unshare / deleting your keys / listing grants stay open so taking access away always works; `sftp/shell` = the wizard's login test, not files), sockets call `ws::auth::require_feature` (4012), MCP: `mcp.connect` off = `auth::mcp::resolve` refuses the token (401, like a revocation), otherwise `McpPrincipal.denied` + `mcp::refused(p, scope)` map `ssh:exec` → terminal, `ssh:files` → files, `network:scan` → network, `browser:use` → remote_browser (tool error), `lan_hosts` needs network; the gateway refuses user-key logins (laptop SSH) without `keys.personal`, which also gates adding keys, device-key-list adds and key-group writes / grants. Desktop / RustDesk sockets are gated at their REST start (tickets). A write also ends live sessions whose feature their user lost (`features::end_denied_sessions`: web / laptop sessions through `access_recheck::recheck` with the admin as `by`, MCP agent sessions / browsers through `api::sessions::end_entry`; 4009 + `SESSION-ENDED` with `feature`, `reason: feature_disabled` and `detached`) — detached terminal shells included, since they keep their presence entry, and a LAN-host shell also needs `network` (`Feature::needed_by(kind, lan)`, LAN shells found through `state.shells.list()`); the close event says "<Feature> was turned off for this account". API (superusers; web sign-ins only — no `/api/access*` route is on the token allow-list and `features::for_route` leaves them to the handler's admin check, unit test `roles_and_admin_kept_groups_are_never_open_to_tokens`): `GET /api/access` (features + defaults, everyone, `groups` = roles `[{id, name, description, created_at, members, sso_members, grants, scim}]`, `share_groups` = admin-kept groups `[{id, name, description, created_at, members, sso_members [{user_id, provider}], synced, scim, shares [{id, tunnel_id, tunnel_name, owner, permission_type, through, expires_at}]}]`, users with `groups` (role ids) / `sso_admin` / `grants` / `effective {allowed, from, group_id}`); roles: `POST /api/access/groups` (answers `created_id`), `PATCH/DELETE /api/access/groups/{id}` (`members` replaces the list; any `shareable` field = 400 field error; a group id = 404; delete drops its grants, SSO rules, grant records and SCIM mapping; no share reconcile — roles never touch tunnels; there is **no** role preview any more); admin-kept groups: `POST /api/access/share-groups {name, description?, members?}` (`created_id`; members = existing accounts, inactive allowed like roles; ≤ 100), `PATCH/DELETE /api/access/share-groups/{id}` (writes reconcile group shares **inline**; delete ends its group shares with one `group_share` event per tunnel and drops its SSO rules, grant records and SCIM mapping), `POST …/{id}/preview` (`{members}` | `{delete: true}` → `{gain, lose: [{user_id, username, tunnels [{id, name}]}], shares}`, writes nothing; reuses `group_shares::preview`); a role or personal id on any share-group route = 404, and a share-group id on any role route = 404; `PUT /api/access/grants {subject: everyone|group|user, id, feature, value: allow|deny|inherit}` (`group` = roles only, a group id = 404; superuser subjects refused); every write answers the whole policy. Gateway events `user_group` (roles) / `feature_grant` / `share_group` (admin-kept groups) (tunnel-less, admin-only). The profile carries `features: [ids]`; the frontend hides nav items (`NavLink.feature`), open buttons, menu entries, the create button, recording setting, saved-logins tab and add-key buttons (`hasFeature`, admins / older backends = all), `AppLayout` replaces a page of a turned-off feature with `FeatureOffNotice` (`featureForPath`), the share dialog keeps existing shares removable when sharing is off, and a 403 `feature_disabled` refetches the profile (≤ once / 10 s, `api:feature-disabled`). Admin → Users & access: Users, **Roles** (`/tunnels/admin/roles[?role=<id>][&new=1]`, `components/groups/RolesView.tsx`: name / description / members, SSO marks, SCIM note, feature-rule summary — no sharing, no impact previews; shared pieces in `AdminGroupBits.tsx`, info `RolesGroupsInfoDialog.tsx`, copy `roles.*`), **Groups** (`/tunnels/admin/groups[?group=<id>][&new=1]`, `components/groups/AdminGroupsView.tsx`, copy `adminGroups.*`: admin-kept groups with members, shared tunnels and the impact preview before member saves / deletes) and **Feature access** (`/tunnels/admin/access[?user=<id>|?group=<id>]`, linked from the Manage-user modal; the old `/tunnels/settings?tab=access[&user=]` redirects): subject list (Everyone / roles / people with search, red badge = features off) and the subject's matrix (Inherit / Allow / Deny per feature, "Inherits: On (role X)"); the "How it works" button opens `AccessInfoDialog` — lane A default → everyone → roles → person (final) live for a picked person + feature (`laneFor`), lane B tunnel sharing (set per tunnel, through people and groups; roles never touch it). Copy under `access.*`. When adding a feature or a gated route: the enum (+ `ALL`, label), `for_route`, `FEATURES` / `PAGE_FEATURES` in `lib/features.ts`, `access.f.<key>` / `…Hint` in all three dictionaries.
- **People lists at scale (admin):** members of roles, admin-kept groups and personal groups are edited with `components/groups/PeopleMembers.tsx` (current members: search over username / email, pages, remove with undo; add: a type-ahead combobox (`TypeAhead`) and "Paste several" usernames / emails; pure + tested `lib/peopleMembers.ts`) and saved as a **delta** — `POST /api/access/groups/{id}/members`, `POST /api/access/share-groups/{id}/members`, `POST /api/user/groups/{id}/members` `{add?, remove?}` (`db::features::apply_delta`, one transaction; roles → `after_write`, groups → reconcile inline; personal: owner only, active / not yourself / ≤ 200 / adding needs `manages_any`), so two admins editing at once never overwrite each other (`MemberPicker` stays for tunnel / key groups). Role / group lists are compact, sortable, paged, with the selection pinned. Feature access has Everyone + a Roles | People switch, each searched and paged. The Users page filters by role / group, shows each person's role / group counts, selects rows (all matching across pages) for bulk add / remove to roles or groups (groups through the impact preview), its account column is "Account type" (not Role), and on phones the type / status / email fold under the name; the Manage-user modal has a Roles & groups tab (`components/users/UserMemberships.tsx`).
- **Timed sharing (`api/sharing.rs`, `expiry.rs`; test `tests/timed_sharing.rs`):** a share may carry `expires_at` (`tunnels_tunnelsharing.expires_at`, NULL = no end) — set on `POST /tunnels/share/{id}` or changed with `PATCH /tunnels/share/{id}/{uid}/expiry` (`{expires_at: <ISO> | null}`, owner / ADMIN; must be in the future). `sharing::run_expiry` ends due shares every 30 s through `end_share` — the same path as revoke and leave: usernames go back to the owner, the pin and the sharee's device key entries are dropped (keys leave the device), and `TUNNEL-UNSHARED` goes out with `expired: true` (the tunnels page shows it as a warning). `crate::expiry::{parse_expiry, check_expiry}` (RFC 3339 or `YYYY-MM-DD` = end of that UTC day) is shared with personal key expiry. Owners see `expires_at` in `/tunnels/shared-users`; a sharee's list item carries `share_expires_at`. Frontend: `components/tunnels/ShareExpiry.tsx` (form choice, one-click popover on each shared row, the "Ends in …" chip on the sharee's card), pure helpers in `lib/shareExpiry.ts`; copy under `share.expiry.*`.
- **Access requests (`api/access_requests.rs`, `db/access_requests.rs`; test `tests/access_requests.rs` on the SSH lab):** a sharee below ADMIN asks for accounts they can't use yet and/or a higher permission for 15 min – 7 days with an optional reason (`POST /api/reverse/server/{id}/access-requests` `{account_ids, permission, duration_secs, reason}`; one pending per person per tunnel, 409 `request_pending`); `GET` the same path = owner / ADMIN: pending + recent requests (`can_decide`), sharees: their own + every account of the tunnel with `allowed` / `until` (names are visible so they know what to ask for). Owner / ADMIN sharees decide with `POST /api/reverse/access-requests/{rid}/approve` (`{duration_secs?}` overrides) or `/deny`; the requester withdraws with `DELETE`. Decisions are compare-and-set on `status`. An approval is a **temporary grant**: allow-list rows with `expires_at` (`tunnels_tunnelsharingallowedusername.expires_at`; a later grant extends, permanent rows are never touched) and a raised permission with `tunnels_tunnelsharing.base_permission` + `permission_until`. Both stop counting at their time even before the reaper runs (`Sharing::permission()`, the allow-list queries filter `expires_at`); `access_requests::revert_once` (in the 30 s `sharing::run_expiry` loop) deletes the rows / puts the permission back and kicks device keys. A manual permission change (`set_permission`) ends a raise; editing the allow-list keeps a temporary account temporary; ending a share cancels pending requests. Notifications: `ACCESS-REQUEST-CREATED` (owner + ADMINs), `ACCESS-REQUEST-DECIDED` (requester), `ACCESS-REQUEST-UPDATED` (deciders, the actor included, so badges refresh); a grant ending sends `TUNNEL-PERMISSION-UPDATED` with `temporary_ended`. Every step is an `access_request` gateway event (the tunnel's Logs). List items carry `access_requests` (pending count, owner / ADMIN only). Frontend: `components/tunnels/AccessRequests.tsx` — `RequestAccessDialog` (tunnel menu "Request access" for sharees below ADMIN, and the terminal page's no-accounts screen, which reloads once approved), `AccessRequestsPanel` at the top of the share dialog, `TemporaryGrantText` on shared rows; the card's "N to review" chip opens the share dialog; `hooks/useAccessRequests.ts`, pure helpers in `lib/accessRequests.ts`; copy under `share.request.*`.
- **Step-up for sensitive tunnels (`step_up.rs`, `api/step_up.rs`; test `tests/step_up.rs` on the SSH lab):** a tunnel with `require_step_up` (`authorized_keys_reverseserverauthorizedkeys.require_step_up`; owner / ADMIN `PUT /api/reverse/server/{id}/step-up {required, reauth?}` — turning it on needs a second factor of your own (400 `step_up_enroll`), turning it off needs `reauth`) asks **everyone, the owner included**, to confirm with a second factor before a session: `POST /api/auth/step-up {reauth}` → `{token, until, window_secs: 900}` (403 `reauth_required` + methods without a proof, 403 `step_up_enroll` without any factor). The token is browser-bound (SHA-256 in memory, `StepUps` owned by the gateway and shared as `state.step_up`; lost on restart) and travels as the `X-Telepy-Step-Up` header (REST) or the WebSocket auth field `step_up`. Gates: terminal (incl. LAN terminal) and file manager sockets close **4008**; SFTP REST, remote-browser start, desktop start and LAN scan answer 403 `step_up_required` (`api::step_up::check`); AI sessions and MCP `lan_scan` are refused (`mcp::STEP_UP_REFUSAL`; `list_tunnels` shows `requires_step_up`); laptop SSH through the gateway (user-key `direct-tcpip`) passes only while that user confirmed in the web within the window (`StepUps::recent`, like Tailscale SSH check mode), otherwise it is rejected with a `step_up_required` gateway event and a `STEP-UP-REQUIRED` notification. Every tunnel JSON carries `require_step_up`. Frontend: `lib/stepUp.ts` (token in this tab's sessionStorage `telepy.stepUp`, `requestStepUp()` shares one prompt between concurrent callers), `apiFetch` sends the header and retries once after a step-up on 403 `step_up_required`, `reconnectingSocket` / the terminal page / `LanTerminal` send `step_up` and reconnect after a step-up on 4008, `components/auth/StepUpProvider.tsx` (in AppLayout: `ReauthDialog` with a description, or SecuritySettings first when the account has no factor; on `STEP-UP-REQUIRED` the visible tab prompts right away), the card's open buttons confirm before navigating, `components/tunnels/StepUpSetting.tsx` on the tunnel page's Sessions tab, a "Confirm first" chip; copy under `stepUp.*`.
- **Mine vs admin section (`components/layout/AdminViews.tsx`, `api::ViewScope`):** every personal page shows the same thing to everyone — an admin sees only their own there — and the site-wide views live in the sidebar's admin section, grouped into **five areas** (`lib/adminAreas.ts` `ADMIN_AREAS`, pure + tested — a test fails when an `app/tunnels/admin/*` page is in no area): **Users & access** (`/tunnels/admin/users` = the user list with search / filters (`lib/managedUsers.ts`) / paging + the Manage-user modal, `components/users/UsersList.tsx`; `/tunnels/admin/access` = feature access), **Site settings** (`/tunnels/settings`), **Rules & alerts** (`/tunnels/admin/commands`, `/notifications`, `/webhooks`), **Site activity** (`/tunnels/admin/logs`, `/sessions`, `/recordings`, `/activity`, `/api-activity`) and **Server health** (`/tunnels/admin/health`). An area with several pages is one sidebar row (`NavLink.children`, expanded only while inside it; `isLinkActive` also matches children that don't share the parent's URL, so the breadcrumb reads area › page) and `app/tunnels/admin/layout.tsx` hands `AdminAreaNav` (the area's pages as tabs; a select on phones) to every page's `PageHeader` through the `PageHeaderNav` context, so the shared views need no prop. New admin page: add it to `ADMIN_AREAS`. List endpoints take `?scope=mine|all` (`ViewScope::parse`: default mine, `all` from a non-admin = 403 `{code: admin_only}`). Admin pages wrap their view in `AdminGate` (non-admins get a note + a link to their own page) and show `AdminChip`; the personal page shows admins an `AdminViewLink` to the admin version. Copy under `admin.*`. `api::sessions::managed` (permission: admins = every tunnel) vs `managed_in(scope)` (what a list shows).
