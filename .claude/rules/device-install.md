# Device side — key lists, installs, switching, deleting a tunnel

- **Device key lists (`device_keys/`, `api/device_keys.rs`, `db/device_keys.rs`; tests `tests/device_keys.rs`):** Telepy installs users' public keys into a device account's `~/.ssh/authorized_keys` itself, over russh + SFTP with the tunnel's service key (connections borrowed from `ssh::pool`). Each tunnel has a key list (`telepy_device_key`): anyone with access may add **their own** keys (`POST /api/reverse/server/{id}/device-keys`); a key goes into exactly the OS accounts its owner may use there (`permissions::allowed_usernames`, the same gate as the terminal), so unshare (entries deleted), a smaller allow-list, a permission change, a deleted username or a deleted/changed user key all remove it from the device. **A disabled owner** (`auth_user.is_active = 0`, `Entry.owner_active`) drops out of `desired` like an expired key — direct and key-group entries alike, the list rows stay — so the next sync takes the keys Telepy installed off every online device (`access_recheck::kick_device_keys` on disable and on re-enable, offline devices on the 15 s tick once they reconnect; `device_key_owner_disabled` gateway event per tunnel), never touching hand-added lines; the panel greys those entries (`owner_disabled` on entries and view rows: `removing` = being taken off, `manual` = added by hand, Telepy leaves it — a warning chip and the needs-attention bucket, `lib/keyRows.ownerDisabledNote` / `splitUnplaced`), and re-enabling installs them again. Desired state (list × allowed accounts) minus what Telepy installed (`telepy_device_key_installed`) is reconciled by `device_keys::run` (kicks from those handlers + a 15 s tick that also catches devices coming back online; failed accounts retry after 2 min) or `POST …/device-keys/sync` (forced re-read; 409 `device_offline`). Writes are tmp file + `posix-rename@openssh.com` (never a half-written file — the service key lives there; existing mode kept, new files 0600, symlinks followed); **which file is decided by evidence, never by distribution** (`device_keys/locate.rs`, test `keys_go_to_the_file_the_server_reads` with the lab's `MachineOpts { keys_file }`): on POSIX devices one exec lists candidates — the server's own `sshd -T` AuthorizedKeysFile, then `locate::KNOWN_FILES` (`~/.ssh/authorized_keys`, `~/.ssh/authorized_keys2`, `/etc/dropbear/authorized_keys`) — and the one holding Telepy's login key (`service_bares`) is the file; several hold it (a GL-MT3000 had it in both after older SFTP-mode syncs wrote the unread `~/.ssh`) = a throwaway key goes into each in turn and `ssh::device::accepts_key` logs in through the tunnel (only on the write path, `AuthorizedKeysFile::open(…, locked: true)`, since it writes briefly; the line is removed by an exact-count rewrite with `cat >`); a control login with the key in no file must fail first; none = the server's first file, else `~/.ssh/authorized_keys`. SFTP and exec use the same answer (cached `platform::TTL` per port + account in `DeviceKeys::files`, cleared by sync-now); Windows keeps `platform.rs`. The panel shows the real path whenever it is not `~/.ssh/authorized_keys`; Telepy only ever removes keys it installed and never a service key. `GET …/device-keys` also returns `view.accounts` (`device_keys/view.rs`, pure + unit tests): one card per account merging the list, what Telepy installed and the account's authorized_keys **as last read** — rows `service / installed / pending / error / removing / manual (a Telepy user's key added by hand) / unknown / invalid` with `verified` (seen in the file) and `line_count` (a key pasted on several lines is one row; removing it removes every line). It never dials the device: `device_keys::remote` records a snapshot (`DeviceKeys::record_snapshot` / `record_failure`, in memory, keyed by reverse port + account; ignored when older than the tunnel) after every read and write. `POST …/device-keys/sync` = apply + re-read every visible account not read in the last 5 s. Owners / ADMIN sharees see every account and row; others only their allowed accounts and their own keys. The older `GET …/authorized-keys` audit still exists; `POST …/authorized-keys/remove` removes a key that is not in the list (400 `service_key`, 409 `in_key_list`); with `fingerprints: [...]` (≤ 10000) it removes a batch in **one** rewrite of the account's file and answers `{removed, keys, skipped: [{fingerprint, code}]}` instead of erroring (`authorized_keys::plan_removal` / `remove_keys`, pure). `GET /api/reverse/user/keys/devices` is the keys-page matrix (my keys × devices I can use). Tunnel creation accepts `key_list: "mine" | "empty"` (`mine` copies all of the creator's keys into the list once). User keys are parsed with russh on create/update (`checked_key(db, raw, except_id, owner)`: reject garbage, DSA, RSA < 2048, the same key under another comment, another user's tunnel key, any tunnel's service key or Telepy's; your own tunnel's device key is allowed and the key JSON's `device_of [{id, name}]` names those tunnels — `DeviceKeyChip` on the keys list, a property in the key details, its own toast on add) and serialised with `fingerprint` / `key_type` / `bits` / `comment`; the gateway records `last_used_at` / `last_used_ip` on every user-key login. The lab sshd also honours `<home>/<account>/.ssh/authorized_keys` once `Machine::account_home(account)` exists. - **Deleting a tunnel (`api/tunnels.rs` `delete_check` / `destroy`, `device_keys::forget_tunnel`, `api::oauth::detach_tunnel`, `Gateway::disconnect_tunnel`; tests `tests/tunnel_delete.rs` on the SSH lab):** owner / ADMIN only. `GET /api/reverse/server/{id}/delete-check` (DB + memory, no device round-trip) lists online state, login accounts, sharees, people using it, LAN hosts, keys Telepy installed (grouped per key), MCP grants that reach it (`coverage` only / shared / all — `all` only for the tunnel's audience) and open AI sessions. `DELETE /api/reverse/server/keys/{id}?remove_device_keys=&remove_service_key=&revoke_grants=&revoke_grant_ids=` (defaults true / false / false / none; `revoke_grant_ids` = grants to revoke entirely, honoured only where the check says `can_revoke` — your own, admins, or limited to this tunnel, so deleting a tunnel never cuts a sharee's access to their other tunnels) (+ `remove_service`, default false) cleans the device **first, while the tunnel is still up** (per account, one `authorized_keys` rewrite, 20 s limit; the service key only when asked), closes the tunnel's AI sessions (`tunnel_deleted`), deletes the rows, drops the tunnel from every grant's restriction list (revoking the ones left empty when asked), disconnects the device from the gateway, and answers **200** with a report (`accounts[{account, removed, service_key_removed, error}]`, `keys_left` = distinct keys still on the device, `grants_revoked/detached`, `ai_sessions_closed`, `device_disconnected`, `steps`). **Live steps (`DeleteSteps` in `api/tunnels.rs`; `tunnel_service::finish_observed` reports the two waits):** six steps in order — `service` (find + delete what runs it) → `keys` → `stop` (stop scripts + wait for the drop, `secs` 25) → `watch` (`secs` 13) → `telepy` (AI sessions, recordings, rows, grants) → `disconnect` — each pushed to **the person deleting only** as `TUNNEL-DELETE-PROGRESS {tunnel_id, step, state: active|done|warn|failed|skipped, reason?, …counts}` while the request runs, and the ends returned as `steps` (tests assert both). `delete-check` adds `uninstall_script` (`~/.ssh/telepy-<install id>-uninstall.sh`, else the pre-install-id name). **Removing the tunnel service from the device (`tunnel_service.rs`, `templates/remove_tunnel.sh` / `remove_tunnel.ps1`; tested in `tests/tunnel_delete.rs` with a real-shell lab machine (`MachineOpts { shell: true }`: `/bin/sh -c` with HOME / TMPDIR in the scratch home — never let a test run it against the developer's home) and in Debian containers):** every install method is tried — join (systemd system / `--user` unit `telepy-tunnel-<id>`, launchd `com.telepy.tunnel.<id>`, background loop `~/.ssh/telepy-tunnel-<id>.sh` + `@reboot` crontab), the autossh systemd template (`telepy-tunnel.service`, `/var/log/telepy-autossh`), Docker (`SSH_TUNNEL_PORT=<port>` env; compose file too), ssh / autossh scripts (found through the running process's parent), downloaded scripts in `~`, `~/Downloads`, `~/Desktop`, and on Windows the PowerShell loop, scheduled tasks, services (incl. NSSM), Run keys and Startup items. **Only this tunnel's things are touched:** a file or command line is this tunnel's when it refers to its key (`-i <file>`, `IdentityFile`, docker's `KEY_FILE=` / `<path>:/id_rsa`, a container's `/id_rsa` mount — the `.pub` next to it or `ssh-keygen -y` must give the tunnel key) or, for scripts written before the device scripts asked for `-R 0`, when it carries its number (`<port>:localhost:…` / `SSH_TUNNEL_PORT`); processes need a `-R` forward (never `-L`), keys must match the tunnel key, the join uninstall script needs `(#<id>)` plus the name or a join unit we matched, `telepy_known_hosts` only goes when nothing else references it. Phase 1 runs per login account (root first; `sudo -n` when available, else `needs_root` lines with the command to run) over a kept connection, deletes files and writes a one-shot stop script; after the key cleanup the stop scripts are launched detached (`systemd-run` / `setsid` / `nohup`; Windows via WMI `Win32_Process.Create`), stop units / launchd jobs / containers / processes (loops before ssh), delete logs and themselves. The gateway then confirms it: the forward must drop by itself (25 s) and not come back (13 s). Script output is `TELEPY|kind|what|detail` lines (`tunnel_service::parse_items`); `$$` must never appear in these templates and their own PowerShell variables must not be named `t_*` (`safe_substitute`). Frontend: `components/tunnels/DeleteTunnelDialog.tsx` + `hooks/useDeleteTunnel.ts` (collects the progress events), pure + tested `lib/deleteTunnel.ts` (plan, per-step line, verdict, diagram states; its test checks the order against the Rust doc comment): the impact map first (`DeleteImpactMap`: who reaches it ─✂─ tunnel ─✂─ keys and service key per account, every item with an outcome chip that follows the choices live), then "What Telepy will do" = the six steps with each option inside its step (service switch, key switches, one choice per AI app in step 5: single-tunnel revoke / keep, multi-tunnel drop only this tunnel / revoke the app; a step that won't run shows as skipped with why). Delete swaps the map for a Telepy ─ tunnel ─ device diagram (service + authorized_keys states) and the same list lights up live (countdown on the waits, "Step n of 6" + elapsed in the footer); when done each step keeps one result line, a verdict callout on top, the device's items under step 1's details, needs-root commands listed with copy; copy under `deleteTunnel.*`. **`components/flow/ProgressSteps.tsx` + pure `lib/progressSteps.ts` (`stepViews` / `countdown`, tested) are the shared "step by step" list** — waiting / active / done / warn / failed / skipped from a plan + live events + the run phase (a lost start still shows the next step active), a `control` slot for options before the start, `planning` hides "waiting"; generic copy under `steps.*`. Use it for any other long operation that reports steps. **Remote browser start** uses it too (`RemoteBrowserPanel`, pure + tested `lib/browserStart.ts`): the start body may carry `progress_id` and `RemoteBrowser::start_observed` pushes `REMOTE-BROWSER-PROGRESS {tunnel_id, progress_id, step: proxy|browser, state, attempt?, attempts?, secs?, reason?}` to the caller; the third step (`stream`) is the browser's own WS → `ready` → RFB connect; the idle panel shows the three steps as the plan, a failed start keeps the list with the failed step and "Try again". `delete-check` also returns `last_on_machine` (no other tunnel pins this machine's host key) + `same_machine`; the dialog pre-checks "remove the service key" for the last tunnel on a machine (otherwise the machine stays reachable with Telepy's key and has no owner) and explains which other tunnel keeps it.
- **Long requests finish on the server (`api/detached.rs`, `delete_runs.rs`, frontend `lib/longRequest.ts` (pure, tested) + `lib/longFetch.ts`; tests `a_cut_delete_finishes_on_the_server_and_can_skip_a_stuck_device` / `a_survey_finishes_although_a_program_on_the_device_never_answers` in `tests/tunnel_delete.rs`):** a proxy in front gives up on a slow request first (measured on prod: openresty / Nginx Proxy Manager answers 504 after ~90 s; Nginx 60 s, Cloudflare 100 s), and axum then drops the handler's future — a delete or a device-service handover stopped halfway. Handlers that talk to a device for long (`DELETE …/keys/{id}`, `device-install/survey|rename|tidy|switch`) run their work through `api::detached::run`: `tokio::spawn`ed, so a cut request still finishes; when the browser sent `X-Telepy-Request: <id>` the requester gets `REQUEST-FINISHED {request, what, tunnel_id, status, body}` (body = the response it would have had). `longFetch` tags the request, and on 502 / 504 / 520–524 or a dropped connection (not 503 = backend down) calls `onCut` and waits ≤ 6 min for that notification (`LongRequestLost` → `api.cutNoResult`). New long device operations: use both. **One delete per tunnel** (`delete_runs::begin`, keyed by id + created_at; a second → 409 `deleting`; rename / switch refuse while it runs and delete refuses while they run) and **skip the device** = force delete: `POST /api/reverse/server/{id}/delete/skip-device` (whoever may delete; 409 `not_deleting`) makes every device step still running (service, keys, stop, watch — each races `Run::skip_requested`) end as `skipped` with `reason: forced`, while Telepy's own part (rows, grants, disconnect) always runs; keys then only clear Telepy's rows (`CleanupOptions.device = false`) and `keys_left` is the count before. No automatic retries (each would wait out the same stuck device again). The dialog shows "Skip the device" while a device step runs (`lib/deleteTunnel.waitingOnDevice`), a "connection was cut, the delete goes on" note, and `verdict.forced`. **Device scripts can't hang silently:** exec channels send EOF on stdin right after the command (`exec::run_on`; Telepy never writes stdin), `remove_tunnel.sh` does `exec </dev/null`, wraps programs that wait on something outside (sudo, crontab, ssh-keygen, docker — a container engine that is starting or asleep) in `lim <secs>` (portable sh: background + quiet watcher; macOS has no `timeout`), and prints `TELEPY|step|<part>|` before each part; `parse_items` drops step lines and a timeout says `timed out after 90 s while looking at <part> on the device` (`tunnel_service::last_step` / `timeout_message`). A failed survey is due again on the next daily pass (`db::device_install::survey_due`), not a week later.
