# Remote browser panel

Design and internals are in `docs/remote-browser.md`; scripted browsers (MCP `browser_*`, `/api/browser/sessions*`) are in `mcp.md` and `cli.md`; LAN web pages and the dock's browser tab are in `lan.md`.

- **The device's own ports ("On this device"; `api/remote_browser.rs` `device_ports`, pure `lan/device_self.rs` `browse_ports` + `NOT_WEB_PORTS`; tests `browse_ports_put_web_pages_first_and_never_offer_ssh`, step 0 of `a_scan_lists_the_devices_own_services_its_gateway_and_what_changed` in `tests/lan_api.rs`; frontend pure + tested `lib/devicePorts.ts`, `hooks/useDevicePorts.ts`, `components/tunnels/DevicePorts.tsx`):** `GET /api/reverse/server/{id}/remote-browser/ports?username=` (VIEW + step-up + an allowed account, feature `remote_browser`, token scope `browser:use` with the tunnel in the path) runs the scan's `LISTEN_POSIX` (then `LISTEN_WINDOWS`) **once, as the person's own account** over `pool.session_channel` — nothing is probed, nothing is stored, and it works without scan rights because it shows no more than `ss` in their terminal would. `browse_ports` keeps the ports reachable on localhost (`local_ports`) and classifies each: `seen` (the stored `source = self` row's services say http / https — its scheme and title win), `no` (the scan saw another protocol, or the port is in `NOT_WEB_PORTS`), `usual` (`lan/web.rs` table), `maybe` (anything else, tried over http); web first, by port. URLs are always `localhost` (the browser connects from the device). Answer `{tunnel_id, username, listed, scanned, ports [{port, web, scheme, url, title, proto, loopback_only}]}`; errors `{error, code: no_account | username | device_offline | ports_failed}`. Same data: MCP `browser_ports` (audited, refuses step-up tunnels) and `telepy browse ports <tunnel>[@account]` (`port_rows`). The panel asks only while it is on screen (`visible` — the terminal page keeps it mounted behind the terminal) and not in the Network dock (`bare`). **One path diagram links the screens** (`components/tunnels/BrowserStartPath.tsx`, pure `startTarget` in `lib/browserStart.ts`): page to open ─localhost─ device ─①SSH as … ─ Chromium② ─③VNC─ this tab, a row from `@xl`, a column below; grey on the start screen, then the same diagram in the starting card lit from the step events, with the started page (`startedUrl`: `:port` + name from the ports list, a LAN URL, or a new tab) and the queue length (`queuedCount`) on the left; after a failure it stays on the start screen stopped on that step, with the full `ProgressSteps` list and **Try again** (same page) under it. Header: nothing while stopped, **Ports** + **Cancel** while starting, **Ports** + **IME** + **Stop** once connected. **Start screen = two ways to start, either one:** the path, then a **Start right away** card (always a new tab: clears `nextUrlRef`), an "or" rule, and `DevicePorts` titled **Start from a page on this device** (a click = `nextUrlRef` + start; no path diagram there, the steps already draw it). While starting / running the same component sits in the header's **Ports** popover (40rem; title "On this device" + the browser ─SSH─ device path; a click = `openTab`, queued while starting). **Layout for many ports:** a left rail of kinds with counts (`groupPorts` / `PORT_GROUPS`: seen / usual / maybe / no = no URL; a `NativeSelect` below the `@lg` container width), a compact one-line-per-port list of the shown kind (`shownGroup`: the chosen kind, else the first non-empty — follows a search), `usePagination` (`telepy.browserPortsPageSize`), and a search over every kind once there are more than 10 ports (`matchPort`: number substring or name). Unnamed web ports show `localhost:<port>/`. Height stays fixed however many ports the device has (measured with 60). Port names: the scan's title → its protocol → `lib/lanConnect.serviceName` (never "HTTP" for a web port). Copy under `browser.ports.*`.
