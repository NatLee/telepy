# CLAUDE.md — Telepy

## Project Overview

Telepy is a full-stack web application for managing reverse SSH tunnels. It provides a web UI for creating/managing tunnels, a WebSocket-based terminal console, SFTP file management, remote browser sessions (KasmVNC, see `docs/remote-browser.md`), RDP / VNC remote desktops in the browser (guacd, see `docs/remote-desktop.md`), and tunnel sharing with permission controls.

The backend is a single Rust process (`src/backend-api/`, binary `telepy-server`) that serves the REST API and WebSockets **and terminates the devices' reverse SSH tunnels itself** (in-process SSH gateway). The migration from the previous Django backend is documented in `docs/rust-migration-plan.md`; the API/WebSocket contract is byte-compatible with it, so the frontend did not change.

## Tech Stack

- **Backend:** Rust (edition 2021) / axum 0.8 + tokio / sqlx (SQLite) / russh (SSH server for the gateway, SSH+SFTP client to devices) / jsonwebtoken / tower-http
- **Frontend:** Next.js 16 (App Router) / TypeScript / Tailwind CSS 4 / Radix UI / xterm.js
- **Database:** SQLite3 (`/data/db.sqlite3`, Django-era table names kept)
- **Auth:** Google OAuth2 (id_token verified against Google JWKS) + JWT (simplejwt-compatible HS256; `SECRET_KEY` env, legacy default with a startup warning); sign-in lifetimes are site settings, see **Web sign-in sessions** below
- **Infra:** Docker Compose / Traefik v3 (reverse proxy)
- **Browser:** KasmVNC + Chromium in the `kasm-browser` container (per-session Xkasmvnc, WS↔WS relay through the backend; the frontend uses the vendored KasmVNC noVNC fork in `src/frontend/src/vendor/kasm-novnc/`)

## Development Commands

### Docker (primary workflow)

```bash
docker compose up -d --build            # Start all services
docker compose up -d --build backend    # Rebuild the Rust backend only
docker compose up -d --build frontend
```

### CLI wrapper (`telepy.sh` / `telepy.ps1`)

```bash
./telepy.sh keygen            # Generate gateway host keys + backend service key (existing keys are kept; .sh and .ps1 alike)
./telepy.sh create-superuser  # Create an admin account (first user is a superuser anyway)
./telepy.sh shell             # Shell into the backend container
./telepy.sh migration         # Reconcile the DB schema (runs automatically on start)
./telepy.sh backend-debug     # Recreate the backend container and follow its logs
./telepy.sh geoip             # Download DB-IP Lite (country + ASN) into ./telepy-data/geoip; re-run monthly, then restart the backend
./telepy.sh oui               # Download IEEE's OUI registry into ./telepy-data/oui/oui.csv so LAN hosts show their NIC vendor; restart the backend
./telepy.sh doctor            # Read-only health check: .env, containers, web + gateway ports, then `telepy-server doctor` in the backend (exit 1 on ✗)
```

### Backend (local, needs rustup)

```bash
cd src/backend-api
cargo test                    # unit + integration tests (needs ssh/ssh-keygen and, for the SFTP test, a local sftp-server; both skip otherwise)
cargo run -- serve            # DATA_DIR / LOG_ROOT default to ./data ./logs; gateway only when GATEWAY_HOST_KEYS_DIR points at host keys
cargo run -- create-superuser --username admin --password 1234
cargo run -- openapi > openapi.json   # dump the OpenAPI document (no DB / server / login needed)
cargo run -- doctor           # read-only checks: config, DB, service key, gateway host keys, guacd, kasm, GeoIP, audit chain (`--json`; exit 1 on a failure)
cargo run -- import-user-keys keys.json [--dry-run]   # add personal SSH public keys to existing accounts: [{"username", "name", "key", "expires_at"?, "description"?}]; same checks as POST /api/reverse/user/keys; exit 1 when any entry was skipped
```

### Frontend

```bash
cd src/frontend
npm install
npm run dev    # Dev server (port 3000)
npm run build  # Production build
```

## Environment Setup

Copy `.env.example` to `.env` and configure:

- `PROJECT_NAME` — container name suffix (default: `main`)
- `DEBUG` — debug logging (default: `false`); `LOG_LEVEL` overrides the level
- `SECRET_KEY` — JWT signing key (empty = legacy default + warning; set in production)
- `WEB_SERVER_PORT` — Traefik exposed port (default: `8787`)
- `REVERSE_SERVER_SSH_PORT` — port devices connect their reverse SSH to (default: `24242`, published to the gateway's 2222)
- `SOCIAL_GOOGLE_CLIENT_ID` — Google OAuth client ID
- `SERVER_DOMAIN` — server hostname (default: `localhost`)
- `INTERNAL_API_TOKEN` — secret for backend → kasm-browser session-manager calls
- `TRUSTED_PROXY_HOPS` — which X-Forwarded-For entries are proxies: `auto` (default; every internal address at the right end — Traefik, an upstream Nginx Proxy Manager — is skipped, the first public one is the visitor) or a fixed count, Traefik included (`1` = Traefik only, `2` = plus an upstream TLS proxy / LB; needed when a proxy in front has a public IP); `CLIENT_IP_HEADER` — optional header to take the client IP from (e.g. `CF-Connecting-IP`)
- `GEOIP_DIR` / `OUI_DIR` — offline GeoIP databases / IEEE vendor list, container paths (default `<DATA_DIR>/geoip` / `<DATA_DIR>/oui`; compose passes both, empty = default; `./telepy.sh geoip` / `oui` fill the matching `./telepy-data` folder and refuse a path outside `/data`)
- `GATEWAY_PROXY_PROTOCOL_FROM` — IPs / CIDRs of an L4 proxy in front of the gateway that sends a PROXY protocol header (empty = off)

## Architecture Notes

- **Services:** 5 containers via Docker Compose: Traefik, frontend, backend, kasm-browser, guacd (remote desktop engine, only on the internal `telepy-desktop` network with the backend). No Redis, no separate SSH container, no supervisor.
- **Routing:** Traefik routes `/api/*`, `/ws/*`, and a fixed set of `/tunnels/{share,unshare,shared-users,available-users,update-permission,server}` paths to the backend (`backend:8000`); everything else to the frontend. Traefik applies a `compress` middleware to HTTP routers (not `/ws`); the backend also compresses REST responses.
- **SSH gateway (`gateway/`):** the backend listens on 2222 (published as `REVERSE_SERVER_SSH_PORT`) with the host keys from `ssh/ssh_host_keys`. Only public-key auth (tunnel / user keys from the DB) and `tcpip-forward` are accepted — the service key is deliberately **not** accepted (the backend reaches devices in-process; that key sits in every device's `authorized_keys`), a tunnel key may only forward its own port and a user key only ports of tunnels the user owns; `tcpip-forward` only records port → connection — **nothing is bound on the host**, `reverse_port` is just a number; **a tunnel key identifies its tunnel** (test `tests/key_identified.rs`): whatever number the device asks for in `-R` (0 included) the forward is registered under the tunnel's own `reverse_port`, which is also the number the device is told (a user key still has to ask for the number of a tunnel it owns); **a key may be both its owner's tunnel key and their personal key** (the computer they work from is also a device; test `tests/own_device_key.rs`): `identify` then returns `Identity::Tunnel { person: true }` (only when the personal key is the same user's, unexpired, the account active and `keys.personal` on) — forwards follow the tunnel's rule, while the greeting, `direct-tcpip`, laptop presence, step-up and `last_used_at` go through `Identity::person()`; across users a key is never shared; `direct-tcpip` accepts `<tunnel name>:<any port>` as well as `localhost:<number>` (names are unique; matched **ignoring case** because OpenSSH lowercases `HostName` before ProxyCommand's `%h` — `gateway::port_by_name`: the exact match first, then the first case variant this identity may reach, else the exact / only one so the refusal is logged on it; test `a_tunnel_name_with_capitals_survives_ssh_lowercasing_it`), and the generated ssh config's device stanza is `HostName <tunnel name>` / `Port 22`; everything the backend does on a device opens a forwarded-tcpip channel in-process (`Gateway::open_stream`) and, except AI sessions and LAN scans (their own connection via `ssh::device::connect`), runs over `ssh::pool`: one connection per (tunnel, OS account), idle 5 min; **only session channels count** (that is all MaxSessions limits): ≤ 8 per connection via `session_channel` — web terminal tabs, exec (file-manager fallback, desktop screens), device key lists and the macOS resolver's lookups — and a MaxSessions refusal teaches that connection a lower limit for `RELEARN` (2 min); direct-tcpip users (remote-browser SOCKS, desktop / RustDesk, the LAN hop) hold a transport lease from `acquire` that takes no slot; SFTP REST and every file manager share **one** sftp channel per connection (`pool.sftp`, one slot), replaced when `ssh::sftp_watch` sees it closed or with requests unanswered for 15 s (the device's sftp-server answers one request at a time), closed after 5 min unused; the file manager renews it on a failed listing. A bare `russh::Channel` sends no close when dropped — close it yourself (a `ChannelStream` does). **direct-tcpip targets that are names go through `ssh::resolve` first**: Apple's sshd-session aborts on a hostname direct-tcpip and drops the whole connection (every channel on the pool with it), so on Darwin devices (`uname -s`, once per connection) the name is resolved on the device with `/usr/bin/dscacheutil` and the channel opened to the IP — never send a name to a Mac; other OSes get the name as before. See `docs/device-connections.md`. `direct-tcpip` serves the generated ssh config's `ProxyCommand ssh -W` for user keys. **No shell:** a tunnel key's session channel is refused; a personal key gets ≤ 2 session channels per connection that only print a greeting (`gateway/greeting.rs`, pure: the user's language, how to reach devices — `ssh <device>` / `telepy ssh <tunnel>` — and up to 8 reachable devices by the `can_reach_device` rule; Tapi in colour with a pty, plain text for exec) and exit 1 — nothing is ever run, the exec command is ignored; subsystem (sftp), x11, env and agent requests fail (test `tests/gateway_greeting.rs`). **PROXY protocol (`gateway/proxy_protocol.rs`; test `tests/proxy_protocol.rs`):** from `GATEWAY_PROXY_PROTOCOL_FROM` (IPs / CIDRs) the header is **optional and auto-detected**: the gateway peeks at the first byte (`P` / `\r` = v1 / v2 header, SSH always starts with `S`; nothing within 5 s = a client waiting for our banner, treated as direct), reads the header byte-exactly before SSH, and its source replaces the peer everywhere (events, endpoint, presence); `UNKNOWN` / `LOCAL` keep the peer; a malformed header = `refused_proxy` event, a connect-and-close (health check) is dropped silently. Every other source never has a header read (never trust one from unlisted peers — anyone could claim any IP, defeating the IP-change alert). `Lab::start_with(|config| …)` sets it in tests. Device-side scripts are unchanged.
- **Tunnel names = ssh host names (`tunnel_name.rs` pure + unit tests, mirrored by `lib/tunnelName.ts` whose test reads the Rust file; tests `tests/tunnel_names.rs`, `lib/tunnelName.test.ts`):** the generated ssh config is `HostName <name>` through `ProxyCommand ssh -W %h:%p`, so names follow OpenSSH: ASCII letters, digits, `.`, `_`, `-`, starting with a letter or digit, ≤ 63 (`tunnel_name::problem` → `name_empty` / `name_too_long` / `name_first_char` / `name_chars`). Why each exclusion (researched, keep in sync with the "Why?" popover): OpenSSH 9.6's `valid_hostname` refuses a leading `-`, shell metacharacters, whitespace and control characters on the command line (CVE-2023-51385); in ssh_config whitespace separates `Host` patterns, `* ? ! ,` are pattern syntax, `%` is a token in `HostName`, `#` a comment; Telepy uses `@` (`tunnel@account`) and `:` (`tunnel:path`, `-W name:port`). `Host` matching is case-sensitive but ssh lowercases the host it connects to (`ssh.c` `lowercase(host)`), so names are **unique ignoring case** (`db::tunnels::name_taken_ignoring_case`; the UNIQUE constraint itself is case-sensitive, so the check is in the app). Enforced on every way in through `api::tunnels::new_name_problem` (`{host_friendly_name: [msg]}`; taken = `NAME_TAKEN`, which the rename dialog matches on "already exists"): `POST /api/reverse/server/keys`, the wizard's `create/key/{token}` (its duplicate pre-check adds `host_friendly_name_problem`), renames (`PUT/PATCH …/keys/{id}` — **only a changed name** is checked, so an older name still saves its other fields; changing only your own case is allowed) and the one-command join (`--name` / the web name; a hostname becomes a name through `tunnel_name::suggest`, also used by `join::tunnel_name_from`). **Older non-conforming names keep working:** `scripts::render_client_config` writes `HostName localhost` / `Port <reverse_port>` for them (the gateway's loopback form), test `an_older_name_keeps_working_through_the_generated_config`. Frontend: `components/tunnels/TunnelNameHelp.tsx` under the name field of the create wizard, the join panel (`rulesJoin`: empty = hostname) and the details rename — the rules always visible, the offending characters named while typing with a one-click "Use …" (`suggestTunnelName`), a "Why?" popover with the reasons; an older name gets `SshNameChip` on cards / rows (opens the details) and a rename callout with the suggestion; copy under `tunnelName.*`. The lab names generated config files with `file_safe` (an older name may hold spaces).
- **Device-side scripts (`scripts/`, `templates/`):** rendered with Python `string.Template.safe_substitute` semantics (unknown `$names` survive, so shell variables in templates are fine). The Docker flavours use `jnovack/autossh` (env-driven, key mounted at `/id_rsa`, defaults to `~/.ssh/id_rsa`) and reach the device's sshd through `host.docker.internal` (`extra_hosts`/`--add-host host-gateway`, Docker 20.10+ / Docker Desktop); the compose one-liner needs `-f telepy-docker-compose.yml`. Scripts only ever *append* the service key to `authorized_keys`. **Every device script asks for `-R 0`** (`SSH_TUNNEL_PORT=0` in the Docker flavours, the join script too): the gateway identifies the tunnel by its key and assigns the number itself, so the number appears nowhere on the device. There is no public `alpine/autossh` image — don't bring it back. **Every script pins the gateway's host keys** (`ScriptContext.gateway_host_keys` from `Gateway::host_public_keys()`): the bash scripts write `~/.ssh/telepy_known_hosts` (the systemd flavour `/etc/ssh/telepy_known_hosts`) and use `StrictHostKeyChecking=yes` + `HostKeyAlias=telepy-<host>-<port>` (the same alias as the join script), PowerShell writes `%USERPROFILE%\.ssh\telepy_known_hosts`, the Docker flavours mount a host-keyed file at `/known_hosts` (jnovack/autossh pins when it exists; `SSH_STRICT_HOST_IP_CHECK=false`) — the compose comment tells the user to save it next to the file. Without gateway keys every script falls back to the old `StrictHostKeyChecking=no`.
- **Status / latency:** forward registration and release update `StatusState` immediately; a banner round-trip through a forwarded channel every 15 s measures RTT. `monitor/runner.rs` runs the 5 s cycle (debounce FLAP_THRESHOLD 2, latency throttle 5 ms / 6-cycle keep-alive) and emits the `UPDATE-TUNNEL-*` notifications through the in-process hub.
- **Connection history + uptime (`db/tunnel_sessions.rs`, test `tests/tunnel_connections.rs`):** `telepy_tunnel_session` holds one row per forward (ip, connected_at, disconnected_at), opened next to `remember_endpoint` (closing any row still open for that tunnel) and closed in `remember_release`; rows left open are closed at startup (`close_orphans`, at the tunnel's last-seen time); ≤ 500 rows per tunnel, 90-day retention (`db::retention`, IPs), deleted with the tunnel. Uptime is pure math over those spans (`spans` / `covered` / `uptime` / `buckets`, unit-tested) counted **from the first recorded session** (before that there is no data, not downtime). `GET /api/reverse/server/{id}/connections` (anyone who can see the tunnel) → `{tracked_since, uptime {h24, d7}, hourly [24 × 0..1|null], sessions [20 × {ip, connected_at, disconnected_at, seconds}]}`, IPs only per `permissions::can_see_endpoint`; MCP `tunnel_status` adds `uptime_24h`. Frontend: the "Connections" section of the tunnel details dialog (`components/tunnels/TunnelConnections.tsx`, `hooks/useTunnelConnections.ts`).
- **Personal key expiry (test `tests/key_expiry.rs`):** `authorized_keys_userauthorizedkeys.expires_at` (NULL = never) and the site setting `user_key_max_days` (0 = no limit; when set, new / renewed keys must expire within it and keys added without a date get the full lifetime). `POST/PATCH /api/reverse/user/keys` take `expires_at` as RFC 3339 or `YYYY-MM-DD` (end of that day, UTC; the web sends the end of the local day with its offset), validated by the pure `api::user_keys::{parse_expiry, check_expiry}`; serialised as `expires_at` + `expired`. Expired keys: `user_key_owner_by_prefix` ignores them, so the gateway refuses them and logs an `expired_key` event (Logs badge); `device_keys::desired` drops them, so the next sync (15 s tick) removes them from devices, and renewing puts them back; the create wizard leaves them out of the authorize command. Frontend: `lib/keyExpiry.ts` (tested presets / state), `components/keys/ExpiryPicker.tsx` in the add and details dialogs, `KeyExpiryText` on cards (amber within 7 days, red when expired) and a banner on the Keys page. No tunnel (device) key expiry on purpose: an expired device key would cut off a remote device that nobody can reach to renew it. **Admin import (`import_keys.rs`, `telepy-server import-user-keys <file.json> [--dry-run]`; test `tests/import_user_keys.rs`):** for moving personal keys onto accounts from inside the backend container (`docker exec telepy-web-<project> telepy-server import-user-keys /path/keys.json`) instead of touching the live SQLite from outside; input `[{username, name, key, expires_at?, description?}]`; the account must exist and be active; every entry goes through the API's own `api::user_keys::prepare_new` (`validate_full` → `checked_key`: parse / weak keys / taken by any user, comment ignored / tunnel or service key → `new_key_expiry` with `user_key_max_days`) and `insert_new` (unique name → `unique_error`); the same key already on that account = `already there`, not an error; `--dry-run` also checks names and in-file duplicates and writes nothing; output `#<n> <user> "<name>" <SHA256 fingerprint>: added | would add | already there | skipped: <reason>` + a summary line (fingerprints only, never key blobs), exit 1 when anything was skipped; each insert writes a tunnel-less `user_key_import` gateway event "<name> (<fingerprint>) added to <user> by import-user-keys". No hub notification or key-group placement (the key is on no device list yet).
- **Webhooks (`webhooks/` = `catalog.rs` (event names, groups, who receives each, which are site-wide; pure), `text.rs` (the sentence + title in en / zh-TW / ja; pure), `format.rs` (Telepy JSON / Slack / Discord / Google Chat / Teams Adaptive Card / Telegram / ntfy + detection from the URL; mentions neutralised; pure), `sign.rs` (Standard Webhooks HMAC, tested against the spec's vector), `target.rs` (SSRF: public addresses only, `PublicResolver` for delivery), `mod.rs` (dispatch, retries, records, pause); `api/webhooks.rs`, `db/webhooks.rs`; user doc `docs/webhooks.md`; tests `tests/webhooks.rs` + unit tests):** personal webhooks (`telepy_webhook.scope = user`, owner only, others get 404) carry exactly the notifications their owner already gets — every source calls `state.webhooks.emit(Event::new(kind).tunnel(t).to(audience, except_actor).data(…))` with **the same audience as the matching hub notification** (tunnel audience, owner + ADMIN, requester…), and `webhooks::matches` (pure) checks enabled, subscribed, owner ∈ audience, `notify_user_webhooks`, and the tunnel filter (`all_tunnels` or `telepy_webhook_tunnel`; account events ignore it). Site-wide webhooks (`scope = site`, any admin manages them) get only the curated `Kind::site()` set (status ×4, `tunnel.ip_changed`, `tunnel.host_key_changed`, `device.claim_attempt`, `account.sign_in_failed`, `user.created`) for every tunnel or a picked list (`site_tunnels` in `GET /api/webhooks` lists every tunnel for admins). **Site webhook modes + opt-outs (test `tunnel_managers_can_opt_their_tunnels_out_of_default_site_webhooks` + the status test in `tests/webhooks.rs`, unit tests in `webhooks/mod.rs` and `lib/webhooks.test.ts`):** `telepy_webhook.mode` = `default` (the column default, so pre-upgrade site webhooks are default) | `enforced` (create / PATCH `mode`, site only; JSON `mode`, a mode change is an extra `webhook` event). A tunnel's **owner or ADMIN sharee** opts that tunnel out of a *default* site webhook (`telepy_webhook_optout (webhook_id, user_id, tunnel_id)`; `PUT /api/webhooks/{id}/optout {tunnel_ids}` replaces *my* opt-outs — ids must be tunnels I manage (400 `not_manager`) that it covers (`not_covered`), enforced = 400 `enforced`, personal / unknown = 404, answers my summary; `DELETE …/optout` clears mine, enforced too; both ungated in `features::for_route`; each change = a `webhook_optout` event on that tunnel's Logs). ## Internationalization (i18n) — REQUIRED for all frontend UI text

The frontend is fully internationalized (English / 繁體中文 / 日本語, default = browser language).
**Every user-visible string added, changed, or removed MUST go through the i18n system** — never
hardcode display text in components, hooks, or lib error builders.

### How it works

- **Dictionaries:** `src/frontend/src/locales/` — `en.ts` is the **source of truth** for keys
  (`export const en = {...} as const` → `TranslationKey = keyof typeof en`). `zh-TW.ts` and `ja.ts`
  are typed `Record<TranslationKey, string>`, so a missing or extra key is a **compile error**.
  Keys are flat `namespace.camelCase` (e.g. `tunnels.deleteMessage`), namespaced by feature
  (`common`, `nav`, `api`, `login`, `firstLogin`, `tunnels`, `tunnelActions`, `tunnelDetails`,

- **In components/hooks:** `const { t, tn, locale, language, setLanguage } = useI18n()` from

  (`t("tunnels.deleted", { name })`). `tn(key, vars)` accepts ReactNode values so sentences keep
  inline `<code>`/`<strong>` without splitting the translation.

### Rules when changing UI

1. **Add/change a string:** add or edit the key in `en.ts` FIRST, then mirror it in `zh-TW.ts` and
   `ja.ts` (TypeScript fails the build until all three agree). Then use `t("the.key")` in code.
2. **Wording:** in zh-TW a tunnel is always **通道** (never 隧道 — `src/locales/terms.test.ts` fails on it); 通道 also stays for a sound channel.
3. **Remove UI:** delete its keys from all three dictionaries (unused keys rot; the extra-key
   check only catches keys missing from zh-TW/ja, not orphans in en).
4. **Do NOT translate:** keycap glyphs (Esc/Tab/Ctrl/F1…), format examples in placeholders
   (`ssh-rsa AAAA…`, `22`), code/paths inside `<code>` (pass them as `tn()` vars), size units,
   product names (SSH, PowerShell, AutoSSH, Docker), the Telepy brand, and gateway log *messages*
   (rendered verbatim; the event badges next to them are translated via `logs.event.<kind>`).
4. Backend-provided text (server error `detail` fields, log lines) is NOT frontend-translated —
   it renders verbatim. Exceptions with a mapping layer: site-setting labels/descriptions use
   the `siteSettings.<field>.*` keys (fallback = backend meta), and remote-browser start
   errors with a machine-readable `code` (e.g. `device_offline`) map to `browser.*` keys, Google-login errors (`google_*`, `registration_closed`, `account_disabled`; `lib/loginErrors.ts`) map to `login.*` keys, and two-factor errors (`lib/mfa.ts`) map to `security.*` keys.
5. Locale-aware formatting: use `useI18n().locale` for `Date.toLocaleString()` /
   `Intl.DateTimeFormat` instead of hardcoding `'en-US'`.
6. `metadata` in `app/layout.tsx` deliberately stays English (localizing it would force dynamic
   rendering for every route).
