# CLAUDE.md — Telepy

## Project Overview

Telepy is a full-stack web application for managing reverse SSH tunnels. It provides a web UI for creating/managing tunnels, a WebSocket-based terminal console, SFTP file management, remote browser sessions (KasmVNC, see `docs/remote-browser.md`), RDP / VNC remote desktops in the browser (guacd, see `docs/remote-desktop.md`), and tunnel sharing with permission controls.

The backend is a single Rust process (`src/backend-api/`, binary `telepy-server`) that serves the REST API and WebSockets **and terminates the devices' reverse SSH tunnels itself** (in-process SSH gateway). The migration from the previous Django backend is documented in `docs/rust-migration-plan.md`; the API/WebSocket contract is byte-compatible with it, so the frontend did not change.

## Tech Stack

- **Backend:** Rust (edition 2021) / axum 0.8 + tokio / sqlx (SQLite) / russh (SSH server for the gateway, SSH+SFTP client to devices) / jsonwebtoken / tower-http
- **Frontend:** Next.js 16 (App Router) / TypeScript / Tailwind CSS 4 / Radix UI / xterm.js
- **Database:** SQLite3 (`/data/db.sqlite3`, Django-era table names kept)
- **Auth:** Google OAuth2 (id_token verified against Google JWKS) + JWT (simplejwt-compatible HS256; `SECRET_KEY` env, legacy default with a startup warning); sign-in lifetimes are site settings, see **Web sign-in sessions** below
- **Infra:** Docker Compose / Traefik v3 (reverse proxy)
- **Browser:** KasmVNC + Chromium in the `kasm-browser` container (per-session Xkasmvnc, WS↔WS relay through the backend; the frontend uses the vendored KasmVNC noVNC fork in `src/frontend/src/vendor/kasm-novnc/`)

## Development Commands

### Docker (primary workflow)

```bash
docker compose up -d --build            # Start all services
docker compose up -d --build backend    # Rebuild the Rust backend only
docker compose up -d --build frontend
```

### CLI wrapper (`telepy.sh` / `telepy.ps1`)

```bash
./telepy.sh keygen            # Generate gateway host keys + backend service key
./telepy.sh create-superuser  # Create an admin account (first user is a superuser anyway)
./telepy.sh shell             # Shell into the backend container
./telepy.sh migration         # Reconcile the DB schema (runs automatically on start)
./telepy.sh backend-debug     # Recreate the backend container and follow its logs
./telepy.sh geoip             # Download DB-IP Lite (country + ASN) into ./telepy-data/geoip; re-run monthly, then restart the backend
./telepy.sh oui               # Download IEEE's OUI registry into ./telepy-data/oui/oui.csv so LAN hosts show their NIC vendor; restart the backend
./telepy.sh doctor            # Read-only health check: .env, containers, web + gateway ports, then `telepy-server doctor` in the backend (exit 1 on ✗)
```

### Backend (local, needs rustup)

```bash
cd src/backend-api
cargo test                    # unit + integration tests (needs ssh/ssh-keygen and, for the SFTP test, a local sftp-server; both skip otherwise)
cargo run -- serve            # DATA_DIR / LOG_ROOT default to ./data ./logs; gateway only when GATEWAY_HOST_KEYS_DIR points at host keys
cargo run -- create-superuser --username admin --password 1234
cargo run -- openapi > openapi.json   # dump the OpenAPI document (no DB / server / login needed)
cargo run -- doctor           # read-only checks: config, DB, service key, gateway host keys, guacd, kasm, GeoIP, audit chain (`--json`; exit 1 on a failure)
```

### Frontend

```bash
cd src/frontend
npm install
npm run dev    # Dev server (port 3000)
npm run build  # Production build
```

## Environment Setup

Copy `.env.example` to `.env` and configure:

- `PROJECT_NAME` — container name suffix (default: `main`)
- `DEBUG` — debug logging (default: `false`); `LOG_LEVEL` overrides the level
- `SECRET_KEY` — JWT signing key (empty = legacy default + warning; set in production)
- `WEB_SERVER_PORT` — Traefik exposed port (default: `8787`)
- `REVERSE_SERVER_SSH_PORT` — port devices connect their reverse SSH to (default: `24242`, published to the gateway's 2222)
- `SOCIAL_GOOGLE_CLIENT_ID` — Google OAuth client ID
- `SERVER_DOMAIN` — server hostname (default: `localhost`)
- `INTERNAL_API_TOKEN` — secret for backend → kasm-browser session-manager calls
- `TRUSTED_PROXY_HOPS` — trusted reverse proxies in front of the backend, Traefik included (default `1`; `2` with an upstream TLS proxy / LB); `CLIENT_IP_HEADER` — optional header to take the client IP from (e.g. `CF-Connecting-IP`)
- `GEOIP_DIR` — offline GeoIP databases (default `<DATA_DIR>/geoip`; `./telepy.sh geoip` fills it)
- `GATEWAY_PROXY_PROTOCOL_FROM` — IPs / CIDRs of an L4 proxy in front of the gateway that sends a PROXY protocol header (empty = off)

## Architecture Notes

- **Services:** 5 containers via Docker Compose: Traefik, frontend, backend, kasm-browser, guacd (remote desktop engine, only on the internal `telepy-desktop` network with the backend). No Redis, no separate SSH container, no supervisor.
- **Routing:** Traefik routes `/api/*`, `/ws/*`, and a fixed set of `/tunnels/{share,unshare,shared-users,available-users,update-permission,server}` paths to the backend (`backend:8000`); everything else to the frontend. Traefik applies a `compress` middleware to HTTP routers (not `/ws`); the backend also compresses REST responses.
- **SSH gateway (`gateway/`):** the backend listens on 2222 (published as `REVERSE_SERVER_SSH_PORT`) with the host keys from `ssh/ssh_host_keys`. Only public-key auth (tunnel / user keys from the DB) and `tcpip-forward` are accepted — the service key is deliberately **not** accepted (the backend reaches devices in-process; that key sits in every device's `authorized_keys`), a tunnel key may only forward its own port and a user key only ports of tunnels the user owns; `tcpip-forward` only records port → connection — **nothing is bound on the host**, `reverse_port` is just a number; **a tunnel key identifies its tunnel** (test `tests/key_identified.rs`): whatever number the device asks for in `-R` (0 included) the forward is registered under the tunnel's own `reverse_port`, which is also the number the device is told (a user key still has to ask for the number of a tunnel it owns); `direct-tcpip` accepts `<tunnel name>:<any port>` as well as `localhost:<number>` (names are unique), and the generated ssh config's device stanza is `HostName <tunnel name>` / `Port 22`; everything the backend does on a device opens a forwarded-tcpip channel in-process (`Gateway::open_stream`) and, except AI sessions and LAN scans (their own connection via `ssh::device::connect`), runs over `ssh::pool`: one connection per (tunnel, OS account), idle 5 min; **only session channels count** (that is all MaxSessions limits): ≤ 8 per connection via `session_channel` — web terminal tabs, exec (file-manager fallback, desktop screens), device key lists and the macOS resolver's lookups — and a MaxSessions refusal teaches that connection a lower limit for `RELEARN` (2 min); direct-tcpip users (remote-browser SOCKS, desktop / RustDesk, the LAN hop) hold a transport lease from `acquire` that takes no slot; SFTP REST and every file manager share **one** sftp channel per connection (`pool.sftp`, one slot), replaced when `ssh::sftp_watch` sees it closed or with requests unanswered for 15 s (the device's sftp-server answers one request at a time), closed after 5 min unused; the file manager renews it on a failed listing. A bare `russh::Channel` sends no close when dropped — close it yourself (a `ChannelStream` does). **direct-tcpip targets that are names go through `ssh::resolve` first**: Apple's sshd-session aborts on a hostname direct-tcpip and drops the whole connection (every channel on the pool with it), so on Darwin devices (`uname -s`, once per connection) the name is resolved on the device with `/usr/bin/dscacheutil` and the channel opened to the IP — never send a name to a Mac; other OSes get the name as before. See `docs/device-connections.md`. `direct-tcpip` serves the generated ssh config's `ProxyCommand ssh -W` for user keys. Shell/exec/pty are refused. **PROXY protocol (`gateway/proxy_protocol.rs`; test `tests/proxy_protocol.rs`):** from `GATEWAY_PROXY_PROTOCOL_FROM` (IPs / CIDRs) the header is **optional and auto-detected**: the gateway peeks at the first byte (`P` / `\r` = v1 / v2 header, SSH always starts with `S`; nothing within 5 s = a client waiting for our banner, treated as direct), reads the header byte-exactly before SSH, and its source replaces the peer everywhere (events, endpoint, presence); `UNKNOWN` / `LOCAL` keep the peer; a malformed header = `refused_proxy` event, a connect-and-close (health check) is dropped silently. Every other source never has a header read (never trust one from unlisted peers — anyone could claim any IP, defeating the IP-change alert). `Lab::start_with(|config| …)` sets it in tests. Device-side scripts are unchanged.
- **Device-side scripts (`scripts/`, `templates/`):** rendered with Python `string.Template.safe_substitute` semantics (unknown `$names` survive, so shell variables in templates are fine). The Docker flavours use `jnovack/autossh` (env-driven, key mounted at `/id_rsa`, defaults to `~/.ssh/id_rsa`) and reach the device's sshd through `host.docker.internal` (`extra_hosts`/`--add-host host-gateway`, Docker 20.10+ / Docker Desktop); the compose one-liner needs `-f telepy-docker-compose.yml`. Scripts only ever *append* the service key to `authorized_keys`. **Every device script asks for `-R 0`** (`SSH_TUNNEL_PORT=0` in the Docker flavours, the join script too): the gateway identifies the tunnel by its key and assigns the number itself, so the number appears nowhere on the device. There is no public `alpine/autossh` image — don't bring it back. **Every script pins the gateway's host keys** (`ScriptContext.gateway_host_keys` from `Gateway::host_public_keys()`): the bash scripts write `~/.ssh/telepy_known_hosts` (the systemd flavour `/etc/ssh/telepy_known_hosts`) and use `StrictHostKeyChecking=yes` + `HostKeyAlias=telepy-<host>-<port>` (the same alias as the join script), PowerShell writes `%USERPROFILE%\.ssh\telepy_known_hosts`, the Docker flavours mount a host-keyed file at `/known_hosts` (jnovack/autossh pins when it exists; `SSH_STRICT_HOST_IP_CHECK=false`) — the compose comment tells the user to save it next to the file. Without gateway keys every script falls back to the old `StrictHostKeyChecking=no`.
- **Status / latency:** forward registration and release update `StatusState` immediately; a banner round-trip through a forwarded channel every 15 s measures RTT. `monitor/runner.rs` runs the 5 s cycle (debounce FLAP_THRESHOLD 2, latency throttle 5 ms / 6-cycle keep-alive) and emits the `UPDATE-TUNNEL-*` notifications through the in-process hub.
- **Connection history + uptime (`db/tunnel_sessions.rs`, test `tests/tunnel_connections.rs`):** `telepy_tunnel_session` holds one row per forward (ip, connected_at, disconnected_at), opened next to `remember_endpoint` (closing any row still open for that tunnel) and closed in `remember_release`; rows left open are closed at startup (`close_orphans`, at the tunnel's last-seen time); ≤ 500 rows per tunnel, 90-day retention (`db::retention`, IPs), deleted with the tunnel. Uptime is pure math over those spans (`spans` / `covered` / `uptime` / `buckets`, unit-tested) counted **from the first recorded session** (before that there is no data, not downtime). `GET /api/reverse/server/{id}/connections` (anyone who can see the tunnel) → `{tracked_since, uptime {h24, d7}, hourly [24 × 0..1|null], sessions [20 × {ip, connected_at, disconnected_at, seconds}]}`, IPs only per `permissions::can_see_endpoint`; MCP `tunnel_status` adds `uptime_24h`. Frontend: the "Connections" section of the tunnel details dialog (`components/tunnels/TunnelConnections.tsx`, `hooks/useTunnelConnections.ts`).
- **Personal key expiry (test `tests/key_expiry.rs`):** `authorized_keys_userauthorizedkeys.expires_at` (NULL = never) and the site setting `user_key_max_days` (0 = no limit; when set, new / renewed keys must expire within it and keys added without a date get the full lifetime). `POST/PATCH /api/reverse/user/keys` take `expires_at` as RFC 3339 or `YYYY-MM-DD` (end of that day, UTC; the web sends the end of the local day with its offset), validated by the pure `api::user_keys::{parse_expiry, check_expiry}`; serialised as `expires_at` + `expired`. Expired keys: `user_key_owner_by_prefix` ignores them, so the gateway refuses them and logs an `expired_key` event (Logs badge); `device_keys::desired` drops them, so the next sync (15 s tick) removes them from devices, and renewing puts them back; the create wizard leaves them out of the authorize command. Frontend: `lib/keyExpiry.ts` (tested presets / state), `components/keys/ExpiryPicker.tsx` in the add and details dialogs, `KeyExpiryText` on cards (amber within 7 days, red when expired) and a banner on the Keys page. No tunnel (device) key expiry on purpose: an expired device key would cut off a remote device that nobody can reach to renew it.
- **Webhooks (`webhooks/` = `catalog.rs` (event names, groups, who receives each, which are site-wide; pure), `text.rs` (the sentence + title in en / zh-TW / ja; pure), `format.rs` (Telepy JSON / Slack / Discord / Google Chat / Teams Adaptive Card / Telegram / ntfy + detection from the URL; mentions neutralised; pure), `sign.rs` (Standard Webhooks HMAC, tested against the spec's vector), `target.rs` (SSRF: public addresses only, `PublicResolver` for delivery), `mod.rs` (dispatch, retries, records, pause); `api/webhooks.rs`, `db/webhooks.rs`; user doc `docs/webhooks.md`; tests `tests/webhooks.rs` + unit tests):** personal webhooks (`telepy_webhook.scope = user`, owner only, others get 404) carry exactly the notifications their owner already gets — every source calls `state.webhooks.emit(Event::new(kind).tunnel(t).to(audience, except_actor).data(…))` with **the same audience as the matching hub notification** (tunnel audience, owner + ADMIN, requester…), and `webhooks::matches` (pure) checks enabled, subscribed, owner ∈ audience, `notify_user_webhooks`, and the tunnel filter (`all_tunnels` or `telepy_webhook_tunnel`; account events ignore it). Site-wide webhooks (`scope = site`, any admin manages them) get only the curated `Kind::site()` set (status ×4, `tunnel.ip_changed`, `tunnel.host_key_changed`, `device.claim_attempt`, `account.sign_in_failed`, `user.created`) for every tunnel or a picked list (`site_tunnels` in `GET /api/webhooks` lists every tunnel for admins). `key.expiring` / `key.expired` are about **personal SSH keys** (Keys page; tunnel keys never expire) and come from `webhooks/keys.rs` (10-minute loop: within 7 days / expired in the last 48 h, once per key + stage + expiry in `telepy_key_expiry_notice`, a renewal re-arms it). Custom headers (≤ 10, `validate_headers` pure: HTTP-token names, Telepy's own headers refused, visible ASCII values) are sealed in `telepy_webhook.headers` (AAD `telepy-webhook-headers:<id>`) and returned to the webhook's managers; PATCH with `headers` replaces the set. Every delivery is recorded as `sending` before it goes out and finished afterwards (`db::webhooks::fail_unfinished` at startup turns leftovers into failed), stores the event as `event_json`, and can be re-sent (`POST …/deliveries/{id}/redeliver`: same `webhook-id`, current format / language / headers, no retries, not counted, `redelivered_from`; test sends can't). **When adding a notification worth a webhook: add a `Kind` (catalogue order = UI order), its sentence in `text.rs` for all three languages, `EVENT_KEYS` + `webhooks.ev.*` keys in the frontend, and emit it next to the hub notification.** Status events don't go through `emit`: `monitor::runner` keeps one `alerts::Alerts` (pure state machine: a condition must outlast the delay, only announced ones send the end, going down silently clears degraded) **per webhook** with its own `delay` and calls `send_to`; only changes after a webhook exists are tracked. Delivery: per-webhook format + language, `webhook-id` / `webhook-timestamp` / `webhook-signature` / `x-telepy-event` headers (secret `whsec_…` sealed with the vault, AAD `telepy-webhook:<id>`, created lazily, `GET/POST …/secret`), retries after 10 s and 60 s on network errors / 408 / 429 / 5xx (`set_retry_delays` for tests), no redirects, ≤ 30 per webhook per minute (first skip recorded as `skipped`), paused after `PAUSE_AFTER` (20) failures in a row (`paused_reason = failing`, `WEBHOOK-PAUSED` to the owner / every admin; PATCH `enabled: true` clears it), latest 50 deliveries kept with the body (≤ 16 KB, 30 days via `db::retention`). Personal URLs must resolve to public addresses only (save-time `target::check` + the delivery-time resolver + IP-literal check; `private_target`) unless the site setting `notify_private_targets` is on; site webhooks may target anything. Site settings `notify_user_webhooks` / `notify_private_targets` / `notify_max_webhooks` (Notifications tab, which now links to the Webhooks page); the old `notify_webhook_url` / `notify_down_delay` columns stay but left the API — data migration `2026-10-26-site-webhook-from-settings` turned a set URL into a site webhook “Status alerts”. Webhooks are cached 30 s in memory and invalidated by every write; deleted tunnels leave every webhook's list. Site webhook changes are `webhook` gateway events. Frontend: `/tunnels/webhooks[?scope=site]` (nav "Webhooks"; `hooks/useWebhooksPage.ts`, `components/webhooks/` — `WebhookCard`, `WebhookDialog` (URL with live service detection, format, language, grouped event checklist with who receives each + presets, delay, tunnel picker), `DeliveriesDialog`, `SecretDialog` (headers + Node.js / Python verification), `EventCatalog`, `WebhookPausedNotice` in `AppLayout`), pure `lib/webhooks.ts` (tested); copy under `webhooks.*`. `UPDATE-TUNNEL-STATUS` carries `tunnels [{id, name}]`; desktop notifications are per browser (`hooks/useDesktopNotifications.ts`, localStorage `telepy.desktopNotify`, toggle in Preferences → General, mounted in `AppLayout`), shown only while the tab is hidden. No email (no SMTP in Telepy).
- **Tunnel health (`monitor::health`, after Cloudflare's healthy / degraded / down / inactive; test `tests/tunnel_health.rs`):** `online` = forward up and the device's sshd banner comes back through it; `degraded` = forward up but `DEGRADED_AFTER` (2) probes in a row failed (`StatusState::record_probes` counts per port, reset on success) — sshd stopped, firewalled or hung behind a live tunnel; `offline` = connected before, no forward now; `never` = no connection on record (`telepy_tunnel_endpoint` ∪ forward/disconnect gateway events, because the endpoint table is newer than some tunnels). List items carry `health` and `last_seen_at` (time only, no IP, so every viewer gets them). The gateway writes `degraded` / `recovered` events (Logs page badges) and the runner pushes `UPDATE-TUNNEL-HEALTH {tunnel_id, port, health}` to the tunnel audience; MCP `tunnel_status` returns `health`. Frontend: `lib/tunnelHealth.liveHealth` merges the fetched `health` with the live `portsMap`; `TunnelStatusPill` / `StatusDot` (dot: solid green / amber / grey, dashed ring for never), `TunnelLastSeen`, open buttons look offline while degraded, a warning toast when a tunnel degrades.
- **WebSocket:** first frame `{type:"auth", token, …}` within 10 s; close codes 4000/4001 (auth), 4002/4003/4004/4005/4006 (terminal/file manager), 4010 (LAN terminal: the chosen saved login is missing / undecryptable), 4007 (2FA enrolment required), 4008 (step-up required), 4009 (ended from the live sessions page; reason = who), 4015 / 4016 (terminal: the shell to resume is gone / was resumed in another window), 4010 (this browser's sign-in was revoked; reason = user / admin / logout / reuse), 4012 (the feature is turned off for this person — terminal / LAN terminal / file manager / remote browser; reason = feature id), 4403/4404/4011/4013 (remote browser), 4404/4403/4011/4013/4014/4400 (remote desktop — no auth frame there: a one-time `?ticket=` and the `guacamole` subprotocol; the code is repeated as the close reason because guacamole-common-js only reads the reason), 4007 (the admin requires two-step sign-in and the account has not enrolled; every socket except `/ws/notifications/` — the desktop socket needs a ticket from the REST start, which is refused already). Terminal pong is a **binary** frame (so are the terminal's command-rule notices, see Command rules); the other sockets answer `{"type":"pong"}`. **Liveness:** the terminal, file-manager and remote-browser sockets read through `ws::Heartbeat` — a WebSocket Ping every `WS_PING_INTERVAL_SECS` (20; browsers answer on their own, background tabs too), and no frame within `WS_PEER_TIMEOUT_SECS` (40) of a ping ends the session; every send goes through `ws::send` (30 s timeout). Without it a client that vanished without a close frame (laptop asleep, network switch, dropped proxy) kept its session and its presence forever. Test helpers that read a socket must skip `Ping`/`Pong` frames.
- **Terminal page + path pickers (`app/tunnels/terminal/page.tsx`, `components/tunnels/TerminalConnectPanel.tsx`, `hooks/useTerminalConnect.ts`, `components/flow/PathFlow.tsx` + `ConnectNodes.tsx`, `components/desktop/DesktopPathPicker.tsx`, `lib/flow.ts` + `lib/terminalFlow.ts` (pure, tested), `components/tunnels/TerminalFlow.tsx` + `TerminalInfoDialog.tsx`):** `/tunnels/terminal` without `serverId` (sidebar "Terminal", `nav.terminal`) is a **connect picker**: the path diagram *is* the form — your browser ─ Telepy ─ device (device + account selects inside the node, live online / offline + tunnel RTT) ─ shell (the device itself or a LAN host from the topology, plus the login) — and "Open terminal" navigates to the same page with `serverId` (+ `lanHost` / `lanUser`); selection in `?tunnel=&lanHost=`, last device in localStorage `telepy.terminalPick`. The remote desktop page's form starts with the same picker (`DesktopPathPicker`: target select, protocol, port in the last node) and keeps quality / clipboard / login below. `components/flow/PathFlow.tsx` holds the diagram blocks (`FlowPath`, `FlowNode` with an optional `control` slot, `FlowLink`, `FlowSteps`, `FlowNow`; straight lines, `@3xl` row / column) used by the pickers and both info diagrams (`DesktopFlow`, `TerminalFlow`); generic copy is `flow.*`. Passwordless: `POST /api/auth/passkey/options` (discoverable, `mediation: conditional`) → `POST /api/auth/passkey/login`. Management under `/api/auth/mfa*` and `/api/auth/passkeys*`; adding/removing a factor and regenerating recovery codes need a `reauth` proof once the account has any factor (`require_reauth`, 403 `code: reauth_required`), and so does approving an MCP app on the OAuth consent page. Admin reset: `DELETE /api/user/users/{id}/mfa`. TOTP = RFC 6238 SHA-1/6/30 s, ±1 step, last step stored (no replay, compare-and-set); the secret is AES-256-GCM-sealed with a key derived from `SECRET_KEY` (rotating it breaks existing TOTP — users fall back to passkeys / recovery codes / admin reset). Recovery codes: 10, SHA-256 only, issued with the first factor and cleared with the last. Lockout: 10 failures per user per 15 min (a success resets it), 5 tries per `mfa_token`, challenges and WebAuthn ceremonies live in memory for 5 min and are single use. Passkeys use `webauthn-rs` 0.5 (links OpenSSL; `libssl-dev` / `libssl3` in the Dockerfile), RP ID = host of `PUBLIC_URL` / forwarded headers (`localhost` allows any port; IP addresses are rejected because browsers refuse them); credentials are stored as the serialised `Passkey` with the counter updated on use. Error bodies are `{error, code}`. - **LAN discovery + jump hosts (#20; `lan/`, `lan/scan.rs`, `api/lan.rs`, `db/lan.rs`; tests `tests/lan_api.rs` on the SSH lab):** agentless — the scan connects to the device (`ssh::device::connect`, its own connection, not the pool) and every probe is a `direct-tcpip` channel the **device's sshd** opens (needs `AllowTcpForwarding`). The socket tells the browser through **binary** JSON frames `{type:"command", state: blocked|error|pending|approved|denied|cancelled|expired, …}` (pending carries `request` + `can_decide`; outcomes carry `request_id`, `by`, `reason`) — binary frames are no longer only `pong` (`lib/commandRules.parseTerminalFrame`). **MCP `ssh_exec`:** the same check with `source = agent`; blocked = tool error; approve = a request the call waits on for `AGENT_WAIT` (45 s), then "still waiting, run the same command again"; an approved agent request is reused once within 10 min (same grant, tunnel, account, command; `used_at`). **Approvals:** approvers = owner + ADMIN sharees, **including the requester** (an approver's own terminal command shows "Run it" in the banner; their agent's commands still need their click); `telepy_command_event` keeps every block and request (status blocked / pending / approved / denied / cancelled / expired, rule snapshot, `decided_by`, `reason`, ≤ 20k rows, 90 days in `db::retention` because commands can hold secrets); decisions are compare-and-set; pending requests expire after the site setting `command_approval_timeout` (default 300 s, 30–86400; Settings → Command rules tab) through `command_rules::run` (5 s loop; a restart cancels what was pending). `GET /api/command-requests[?status=pending&tunnel_id=&limit=]` (what you decide + your own; superusers see all, but only approvers get `can_decide`), `POST …/{id}/approve`, `…/deny {reason?}`, `…/cancel` (requester). Notifications `COMMAND-APPROVAL-REQUESTED {request, approver_ids}` / `COMMAND-APPROVAL-DECIDED {request}` to approvers + requester. Gateway events `command_blocked` / `command_held` / `command_approved` / `command_denied` / `command_expired` / `command_cancelled` / `command_rule` name the rule but **never the command** (VIEW sharees read Logs). A guard against mistakes, not a security boundary: scripts, aliases, editors and laptop SSH (`direct-tcpip`) are never checked — the UI says so. ## Internationalization (i18n) — REQUIRED for all frontend UI text

The frontend is fully internationalized (English / 繁體中文 / 日本語, default = browser language).
**Every user-visible string added, changed, or removed MUST go through the i18n system** — never
hardcode display text in components, hooks, or lib error builders.

### How it works

- **Dictionaries:** `src/frontend/src/locales/` — `en.ts` is the **source of truth** for keys
  (`export const en = {...} as const` → `TranslationKey = keyof typeof en`). `zh-TW.ts` and `ja.ts`
  are typed `Record<TranslationKey, string>`, so a missing or extra key is a **compile error**.
  Keys are flat `namespace.camelCase` (e.g. `tunnels.deleteMessage`), namespaced by feature
  (`common`, `nav`, `api`, `login`, `firstLogin`, `tunnels`, `tunnelActions`, `tunnelDetails`,
  `wizard`, `terminal`, `detach`, `watch`, `latency`, `kbd`, `files`, `browser`, `scripts`, `config`, `share`, `webhooks`,
  `manageUsers`, `keys`, `groups`, `logs`, `deviceFacts`, `settings`, `security`, `siteSettings`, `prefs`, `apps`, `deleteTunnel`, `language`, `network`, `join`, `commands`, `toolbox`, `ui`).
- **In components/hooks:** `const { t, tn, locale, language, setLanguage } = useI18n()` from
  `@/lib/i18n`. `t(key, vars?)` returns a string; `{var}` placeholders interpolate
  (`t("tunnels.deleted", { name })`). `tn(key, vars)` accepts ReactNode values so sentences keep
  inline `<code>`/`<strong>` without splitting the translation.
- **Outside React** (e.g. `lib/api.ts` error builders): use `translate()` from `@/lib/translate`
  (module-level; the provider keeps its locale in sync).

  the sidebar footer `ScaleSwitcher`, the finer slider in the preferences modal; `hooks/useUiScale.ts`
  mirrors `useThemePreference`). All of them sync server-side via `/api/user/settings`.
- **Type scale:** `globals.css` overrides Tailwind's `--text-*` tokens so every step is 1px larger than
  stock (xs 13 / sm 15 / base 17 / lg 19 / xl 21 / 2xl 25) — jf-openhuninn reads small. Never use
  `text-[Npx]` for UI text: px ignores the display scale; use the tokens or `text-[Nrem]`.
- **Site-setting labels/descriptions:** the settings page prefers dictionary keys
  `siteSettings.<field>.label` / `siteSettings.<field>.description` (localized), falling back
  to the backend `meta` (label/description embedded in `api/site_settings.rs`). **When adding a
  site setting, add the column in `db/schema.rs`, the field in `db/settings.rs` + `api/site_settings.rs`,
  and these two keys to all three dictionaries.**
- The Settings page (`/tunnels/settings`, labelled **Site settings** / 網站設定 in the nav and title, with an "Admins only" chip) is admin-only, tabbed by `?tab=`: Account & registration
  (default) / Sign-in (`signin_*` + `mfa_*`) / Remote browser (`remote_browser_*`) / Remote desktop (`desktop_*`) / AI access (`ai_*`, + MCP endpoint) / Notifications (`notify_*`: personal webhooks on / off, private targets, per-person limit; + a link to the Webhooks page) / Terminal & commands (`terminal_*` + `command_*`, + a link to the site-wide rules) / Users. Site
  settings land in a tab by key prefix, so a new key needs no page change; integer keys ending in
  `_timeout` / `_lifetime` / `_delay` / `_secs` are seconds and are edited as a number plus a unit (`DurationField`). Personal
  preferences live in the sidebar gear modal (`4xl`; tabs: General = language + desktop notifications / Appearance = theme + display size / Terminal / Remote desktop (the last two hidden when that feature is off) / Security / Saved logins / Connected apps / API tokens).

### Rules when changing UI

1. **Add/change a string:** add or edit the key in `en.ts` FIRST, then mirror it in `zh-TW.ts` and
   `ja.ts` (TypeScript fails the build until all three agree). Then use `t("the.key")` in code.
2. **Remove UI:** delete its keys from all three dictionaries (unused keys rot; the extra-key
   check only catches keys missing from zh-TW/ja, not orphans in en).
3. **Do NOT translate:** keycap glyphs (Esc/Tab/Ctrl/F1…), format examples in placeholders
   (`ssh-rsa AAAA…`, `22`), code/paths inside `<code>` (pass them as `tn()` vars), size units,
   product names (SSH, PowerShell, AutoSSH, Docker), the Telepy brand, and gateway log *messages*
   (rendered verbatim; the event badges next to them are translated via `logs.event.<kind>`).
4. Backend-provided text (server error `detail` fields, log lines) is NOT frontend-translated —
   it renders verbatim. Exceptions with a mapping layer: site-setting labels/descriptions use
   the `siteSettings.<field>.*` keys (fallback = backend meta), and remote-browser start
   errors with a machine-readable `code` (e.g. `device_offline`) map to `browser.*` keys, Google-login errors (`google_*`, `registration_closed`, `account_disabled`; `lib/loginErrors.ts`) map to `login.*` keys, and two-factor errors (`lib/mfa.ts`) map to `security.*` keys.
5. Locale-aware formatting: use `useI18n().locale` for `Date.toLocaleString()` /
   `Intl.DateTimeFormat` instead of hardcoding `'en-US'`.
6. `metadata` in `app/layout.tsx` deliberately stays English (localizing it would force dynamic
   rendering for every route).

## Code Conventions

- **License:** AGPL-3.0-only (`LICENSE`), with a commercial license on the side and the pre-October-2026 MIT notice kept in `NOTICE`. New dependencies or vendored code must be AGPL-compatible (MIT / BSD / Apache-2.0 / MPL-2.0 / LGPL are fine; GPL-2.0-only, SSPL, proprietary are not); vendored code keeps its license text next to it (`src/frontend/.gitignore` ignores `*.txt` except `src/vendor/**/LICENSE.txt`). External contributions need the CLA in `CONTRIBUTING.md` (box in `.github/pull_request_template.md`)
- Backend: one module per former Django app under `api/`; handlers return `ApiResult<Json<Value>>` and build errors with `ApiError::{error,detail,field}` so the JSON shape matches what the frontend expects
- Business logic that is pure (permissions, debounce/throttle, template substitution, path resolution) lives in plain functions with unit tests; I/O stays in `api/`, `ws/`, `gateway/`
- Anything on an SSH path (gateway, device login, terminal, SFTP, laptop ProxyCommand/ProxyJump, sharing/username permissions) gets an end-to-end test on `tests/common/lab.rs`: `Lab::start()` runs the real gateway; `lab.machine(name, &[(os_user, &[keys])], allow_jump)` is a device/LAN sshd with per-OS-user `authorized_keys` and a login log (`logged_in(user, key)`); `lab.device(owner, name, &machine)` brings its tunnel up with a real `ssh -NR`; paths: `backend_exec` / `backend_sftp` (russh), `backend_ssh` (OpenSSH), `laptop_exec(user, &[Hop::Tunnel(..), Hop::Direct(..)], cmd)`, `generated_ssh_config`, `terminal` (WS). Users are created in the DB (no pbkdf2), so a scenario runs in seconds — see `tests/ssh_topology.rs`
- DB access goes through `db/*` functions (sqlx, runtime-checked queries against the Django-named tables); never alter or drop an existing column in `schema.rs`
- Frontend uses centralized `apiFetch()` with auto JWT injection and 401 handling
- **All frontend UI strings go through i18n (`useI18n().t` / `tn`) — see the i18n section above**
- Comments are mixed English and Traditional Chinese
- Frontend components follow Shadcn/Radix patterns with `class-variance-authority`
- **UI building blocks** (use these instead of hand-rolling): every dialog is `components/ui/Modal.tsx` (`title`, optional `description` / `icon` / `tone="danger"`, `toolbar` for tabs / filters — a fixed row between header and body, **never put tabs inside the scrolling body** (they get squashed when the body is a shrinking flex child), `footer` for the buttons; the body is the dialog's only scroll area — no fixed-height `max-h-* overflow-auto` boxes inside it — and a built-in "More below" pill (`ui.moreBelow`) appears while it overflows; sizes sm…4xl incl. `xl`; settings-style dialogs pass `nav` (`components/ui/nav-tabs.tsx` `NavTabs`: a left rail from `sm` up, a row above the body on phones, outside the scroll area) plus `fixedHeight` so switching tabs never resizes the dialog — the preferences modal and the tunnel details dialog (Basics / Device / Keys & identity / Sessions / Connections; every panel stays mounted and hidden, unsaved / failing fields dot their tab, `onDetails(id, tab)` opens a tab — the host-key alert → identity, the device warning → device) do; it focuses the panel on open instead of the close button, and becomes a bottom sheet on phones) and confirmations are `ConfirmDialog`; long lists page with `components/ui/pagination.tsx` `Pagination` + `hooks/usePagination.ts` (`usePagination(total, {storageKey, resetKey, sizes?})` — `sizes` defaults to 10 / 25 / 50 / 100, card grids pass `CARD_PAGE_SIZES` — the page size per list in localStorage, back to page 1 when `resetKey` (the search / filter / sort) changes; `useSectionPages` = each group section pages on its own with one size) and the pure `lib/pagination.ts` (tested): search and filters always run over everything first, then the result is paged; click-to-open panels anchored to a control are `components/ui/popover.tsx` (same surface as the dropdown menu; Modal's `MoreBelow` is exported for scroll areas inside one); notices are `components/ui/callout.tsx` (`tone` info / tip / warning / danger, optional `title` line and custom `icon` — no more `bg-blue-50` / 💡 / tinted `bg-warning/[0.07]` boxes; - **Design language** (modelled on the Cloudflare / Tailscale / Teleport consoles, deliberately not their copy): warm-grey neutrals plus one persimmon-orange `primary` (light `#bf511a` with white text, dark apricot `#f88a3d` with dark text) used only for primary actions, focus, the current item and Telepy itself; `success` (green) / `warning` (yellow-leaning amber) / `info` / `destructive` are separate hues — use them for status, never `primary`, and never Tailwind `emerald-*` / `amber-*` / `red-*` classes.
