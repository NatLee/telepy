# バックエンドがデバイスに接続する仕組み

<p align="center"><a href="./device-connections.md">English</a> | <a href="./device-connections.zh-TW.md">繁體中文</a> | <b>日本語</b></p>

ユーザー向けドキュメントの中で、いちばん技術寄りの 1 本です。Telepy のバックエンドからデバイスの sshd までの接続をたどりながら、デバイスがどの経路で入ってくるか、バックエンドが正しいマシンと話していることをどう確かめるか、接続をどう共有するか、どのポートを使うか、そしてデバイスに何を残すかを説明します。

想定している読者は、内部の動きを理解したい管理者や、何かが動かなくなった原因を探している管理者です。トラブルで来た方は、たいてい次のどれかが当てはまります。

- Web の名前が Cloudflare などの Web プロキシの後ろにあり、デバイスが SSH に届かない：[SSH 用に別の名前を使う](#ssh-用に別の名前を使う)
- どのデバイスもロードバランサーのアドレスから来たように見える：[前段に L4 プロキシがある場合：PROXY protocol](#前段に-l4-プロキシがある場合proxy-protocol)
- デバイスのホスト鍵が変わった、または `device_claimed` が出る：[デバイスのホスト鍵を固定する](#デバイスのホスト鍵を固定する)と[1 台のマシンに持ち主は 1 人](#1-台のマシンに持ち主は-1-人)
- デバイス上のサービスに「要変更」や「余分」の印が付いている：[デバイス上の名前](#デバイス上の名前)

## 全体像

![ターミナル接続の経路：ブラウザ、Telepy、デバイスの sshd](images/ja/terminal-flow.png)

デバイス側はごく普通の OpenSSH です。デバイスは自分のトンネル鍵を使って `ssh / autossh -NR '*:0:localhost:22' telepy@<server> -p 24242` を実行します。

- 現在のスクリプトは必ず `-R 0` を要求します。ゲートウェイが鍵からトンネルを特定し、番号は自分で決めます（[トンネルは鍵で見分ける](#トンネルは鍵で見分ける)を参照）。
- スクリプトは `StrictHostKeyChecking=yes` と `HostKeyAlias=telepy-<host>-<port>` でゲートウェイのホスト鍵を固定します。ポート番号を書いた古いスクリプトもそのまま動きます。
- Web ポートしか外に出られないネットワークでは、同じ SSH を WebSocket に包んで通します（[Web ポート](#web-ポートwebsocket)を参照）。

サーバー側でこの接続を受けるのはゲートウェイ（gateway）、つまりバックエンドのプロセスに組み込まれた SSH サーバーです。（以前は別の OpenSSH コンテナが受けていました。）

```
デバイス
  sshd :22
     ▲
     │ トンネル鍵で ssh -NR。トンネル内の各チャンネルは localhost:22 につながる
     ▼
Telepy バックエンド（単一プロセス）
  ゲートウェイ :2222（外部 24242）
     │ forward テーブル：reverse_port → このデバイスの接続（ローカルのポートは使わない）
     │
     ├─ 接続プール：デバイスと OS アカウントごとに SSH 接続 1 本
     │    ├ Web ターミナル：タブごとに PTY チャンネル 1 本
     │    ├ ファイル管理 / SFTP：共有の sftp チャンネル 1 本（exec 代替はコマンドごとに 1 本）
     │    ├ リモートブラウザー：内蔵 SOCKS5、CONNECT ごとに direct-tcpip 1 本
     │    └ LAN ホストへの中継：direct-tcpip 1 本（最後の 1 ホップは今も OpenSSH）
     ├─ AI セッション、LAN スキャン：それぞれ専用の接続（チャンネルはバックエンド内で開く）
     └─ ノート PC：ssh -W <トンネル名>:22 telepy@server（ユーザー鍵）→ チャンネル 1 本
```

どの機能がどの経路を通っても、最後は**デバイスの sshd への SSH ログイン 1 回**になります。バックエンドはそのトンネル専用のサービス鍵（[トンネルごとに 1 本のサービス鍵](#トンネルごとに-1-本のサービス鍵)を参照）でログインし、ノート PC はユーザー自身の鍵でログインします。

| 機能 | デバイスへの届き方 |
|---|---|
| デバイス → サーバー | バックエンド内蔵のゲートウェイへ `ssh -NR`（`-R 0`）。`/ws/gateway/` の WebSocket で包むこともできる |
| Web ターミナル | 共有接続上の PTY チャンネル。同じデバイス・同じアカウントのタブとファイル管理は、SSH ログイン **1 回**を共有 |
| ファイル管理 / SFTP | SFTP REST とすべてのファイル管理が、その接続上の sftp チャンネル **1 本**を共有。sftp サブシステムがなければ、ファイル管理は exec チャンネルで `ls -la` を実行 |
| リモートブラウザー | バックエンド自身の SOCKS5 プロキシ（CONNECT のみ）。CONNECT ごとに共有接続上の direct-tcpip を 1 本使う |
| LAN ホストのターミナル | 共有接続上の direct-tcpip を、使い捨てのローカル入口を通して OpenSSH に渡す。最後の 1 ホップは OpenSSH なので、パスワードを尋ねられる |
| デバイスの鍵リスト | 同じプールから接続を借り、SFTP で `~/.ssh/authorized_keys` を読み書き |
| ノート PC | ゲートウェイ経由の `ProxyCommand ssh -W` |

Rust のバックエンドになる前は、どれもその OpenSSH コンテナを経由していました。ファイル操作のたびに `ssh` や `scp` を起動し、毎回 SSH を 2 段通っていたのです。

## デバイスがゲートウェイに届くまで

![自分のコンピューターから Telepy への接続と、デバイスの接続方法の比較](images/ja/transport-info.png)

デバイスの入り口は 3 通りです。SSH ポートを使う、SSH を WebSocket に包んで Web ポートを使う、またはまず SSH ポートを試してだめなら Web ポートに切り替える。どの入り口でも中身は同じ SSH で、鍵もルールも変わりません。

### SSH ポート

これが既定です。デバイスは `REVERSE_SERVER_SSH_PORT`（24242。コンテナ内では 2222）に接続します。

接続先の名前は `SSH_SERVER_DOMAIN` で、サイト設定 →「サーバー」の「SSH ホスト」でも設定できます。空のままなら Web と同じ名前になります。

### SSH 用に別の名前を使う

![SSH に別の名前が必要になることがある理由](images/ja/ssh-host.png)

Web の名前が Web ポートしか通さないプロキシ（Cloudflare のオレンジ色の雲、ほかの CDN、HTTP ロードバランサー）の後ろにあると、その名前では SSH ポートに届きません。その場合は、サーバーへ直接届く名前を SSH 用に用意します。

- known_hosts のエイリアス（`telepy-<ドメイン>-<port>`）は引き続き Web のドメインを使うので、SSH ホストを変えても Telepy が別のサーバーに見えることはありません。
- すでにインストール済みのデバイスは、設定したときの名前に接続し続けます。
- 設定ページは両方の名前を名前解決し、Cloudflare のアドレスなら見分けます。ほかのプロキシは見分けられません。`doctor` の `ssh_host` チェックも同じです。

SSH 用の名前で Web 画面が開けてはいけません。`PUBLIC_URL` が設定されていて、SSH ホストが別の名前のときは、次のようになります。

- SSH 用の名前で届いたサインインには 421（`ssh_host`）を返し、フロントエンドは正しいアドレスへ案内するページに切り替えます。
- 設定ページでは、いま開いている名前を保存できません。自分を締め出してしまうからです。

これで防げるのは、アドレスの間違いや設定ミスです。偽装された `Host` ヘッダーは防げないので、それにはプロキシからしかオリジンに届かないようにしてください。

### Web ポート（WebSocket）

社内ネットワーク、ホテル、4G ルーターなど、Web ポートしか外に出られないネットワーク向けです。

デバイスの ssh には `ProxyCommand ~/.ssh/telepy-<インストール ID>-ws.sh` が加わります。この小さなラッパーが**キャリア**を実行します。キャリアは、ssh のバイト列を WebSocket のバイナリフレームに包んで Web ポートへ送るプログラムです。

中身はまったく同じ SSH セッションです。同じホスト鍵、同じ鍵ログインと forward のルールで、余計に信頼するものはありません。認証は中の SSH で行うので、別の認証メッセージもありません。

ウィザードの接続ステップか、1 行のコマンドでの追加で選びます（`transport: websocket`）。何がインストールされたかは、「デバイス」タブに `carrier` の項目として表示されます：`binary <target>`、`python3`、`none` のいずれかです。

#### デバイスに入るキャリア

1. **ビルド済みの `telepy-carrier`**（優先）：Rust の静的バイナリで、リリースのたびに x86_64・aarch64・armv7・armv6 の Linux、macOS、Windows 向けにビルドされます。
2. **`python3` と `telepy-ws.py`**（標準ライブラリのみ、`GET /api/join/telepy-ws.py` で配布）：MIPS ルーターなど、ビルド済みバイナリがない CPU 向けです。

参加スクリプトの `--carrier binary|python` で、どちらかに固定できます。

バイナリがデバイスに届くまで：

- デバイスは自分のサーバーの `GET /api/join/carrier/<target>` からダウンロードし、サーバーが `…/sha256` で公開している sha256 と照合します。
- その sha256 はリリースの `SHA256SUMS` から取ったもので、サーバーは Telepy のリリース鍵による正しい署名（`SHA256SUMS.sig`）が付いたものしか受け付けません。
- サーバーは、あるプラットフォームが初めて要求されたときにリリースページから取得し、`CARRIER_DIR`（`<DATA_DIR>/carriers`）にキャッシュします。`telepy-server fetch-carriers` で前もってそろえておくこともできます。
- サイト設定「デバイスのキャリアを最新に保つ」がオンなら（既定でオン）、サーバーは 1 日に 1 回リリースページを確認し、古いコピーをバックグラウンドで置き換えて、すべての管理者とサイト全体の webhook（`carriers.updated` / `carriers.update_failed`）に知らせます。
- 「サーバーの状態 → 関連サービス → デバイスのキャリア」で各プラットフォームのバージョンを確認でき、手動で更新することもできます。

デバイスに HTTP CONNECT プロキシが設定されていれば、どちらのキャリアもそれを通ります（`HTTPS_PROXY` または `--proxy`。`NO_PROXY` も有効です）。サービスには自分の環境変数がないので、参加スクリプトは実行時の環境にあるプロキシをラッパーに書き込みます。

#### ゲートウェイから見えるもの

- 送信元 IP は `X-Forwarded-For` から取ります。どの項目をプロキシとみなすかは、サイト設定 →「サーバー」の「信頼するプロキシ」（または `TRUSTED_PROXY_HOPS`）で決まります。既定の `auto` は、右端に並ぶ内部アドレスをすべてプロキシとして扱います。
- ポートは 0 として記録されます。接続情報、`accepted` イベント、トンネル一覧の `endpoint.transport` には `websocket` と記録されます。
- 接続数の上限（`GATEWAY_MAX_CONNECTIONS`）は、2 つの入り口を合わせて数えます。

#### ノート PC から Web ポートで

ノート PC もこの方法で接続できます。SSH 設定ダイアログの「Telepy への接続方法」で「Web ポートのみ」、または「自動」（`--tcp` が付き、まず SSH ポートを試します）を選びます。`telepy-ws.py` を `~/.ssh/telepy-ws.py` に保存すると、サーバーのブロックに ProxyCommand が 1 行加わります。

`telepy ssh / scp / sftp` はこのヘルパーを使わず、既定で Web ポートを通ります（[cli.ja.md](./cli.ja.md) を参照）。

### 自動：まず SSH ポート

`transport: auto` は、ウィザードと 1 行のコマンドでの追加の既定値です。

- キャリアには `--tcp <SSH ホスト>:<port>` が渡されます。接続のたびにまず SSH ポートへ直接つなぎ、ゲートウェイの `SSH-` バナーが届いて初めて成功とみなします。
- つながらなければ（ファイアウォール、または Web の名前が Web ポートしか通さないプロキシの後ろにある場合）、WebSocket に切り替えます。
- WebSocket で通じたことは 30 分間覚えておき（一時ディレクトリの小さなファイル）、その後はまた SSH ポートから試します。
- WebSocket で接続したあとも、最初の 10 分ほどは SSH ポートを試し直します（10 秒後、30 秒後、70 秒後……計 6 回）。通じたらキャリアはその接続を終え、WebSocket を覚えていたことも忘れるので、サービスは数秒後に SSH ポートからつなぎ直します。理由：サーバーの再起動直後は、SSH ポートが Web ポートより数秒遅れて開くことがあります（コンテナの前のポート転送が、コンテナ同士のネットワークより遅れるため）。その隙間で再接続したデバイスは、次に切れるまで遅い経路に残ってしまいます。6 回試し終えたらもう試さないので、使用中の接続が後から切られることはありません。
- どちらを通ったかは stderr、つまりサービスのログに書かれます。
- キャリアがまったくないデバイス（その CPU 向けのビルド済みバイナリも python3 もない）は SSH ポートだけを使い、参加時にそう表示されます。

1 行のコマンドでの追加は `--auto` を使い、実際にインストールした内容を登録時に報告します（`facts.transport`、`facts.carrier`）。Telepy はそれをトンネルの接続方法（`way_in`）として保存します。

### 内蔵 SSH クライアント

デバイスによっては、SSH クライアントがゲートウェイと話せなかったり（標準の OpenWrt の dbclient）、そもそも SSH クライアントがなかったりします。その場合は同じ `telepy-carrier` がトンネル全体を自分で張ります。デバイスに OpenSSH クライアントがなければ、1 行のコマンドでの追加がこれを選びます（`--client builtin`）。

```
telepy-carrier tunnel --identity <key> --known-hosts <file> --server <SSH host>:<port> [--ws <url>] --forward 0:<sshd>
```

- ゲートウェイとは自分で SSH を話します。ホスト鍵を固定し、鍵でログインし、`tcpip-forward` 0 を要求します。
- ゲートウェイが開くチャンネルを、1 本ずつデバイスの sshd につなぎます。
- 30 秒ごとの keepalive を自前で持ち、接続が切れたら終了して、サービス管理に再起動を任せます。
- 接続方法（SSH ポート、Web ポート、自動）と CONNECT プロキシは上と同じです。サービスは `~/.ssh/telepy-<インストール ID>-ws.bin` を直接実行します。

詳細と制限は [device-join](device-join.ja.md#1b-内蔵-ssh-クライアントtelepy-carrier-tunnel) を参照してください。

### 自前のキャリアを使う

Telepy のキャリアはあくまで手助けで、必須ではありません。ssh の stdin / stdout をゲートウェイへの TCP 接続につなげるプログラムなら、何でもデバイスの `ProxyCommand` になれます。

Web ポートすらそのままでは通れないネットワーク（SNI によるフィルタリング、TCP の帯域制限）なら、[wstunnel](https://github.com/erebe/wstunnel) のような汎用トンネルで、Telepy に手を入れずに対応できます。

1. バックエンドのネットワーク上に `wstunnel server` のコンテナを 1 つ追加し、`--restrict-to backend:2222` を付けます（`--restrict-http-upgrade-path-prefix` で秘密のパスも設定します）。
2. Traefik で 1 つのパスをそこへ振り向けます。
3. デバイスには `ProxyCommand wstunnel client -L stdio://backend:2222 wss://<host>/<path>` を設定します。

中身は相変わらず Telepy の SSH です。鍵も、ホスト鍵の固定も、forward のルールも同じです。

失うもの：

- ゲートウェイからは wstunnel のコンテナが接続相手に見えるので、デバイスのグローバルアドレスは毎日の調査を待ってから、遅れて分かります。
- 接続方法の表示が SSH over WSS ではなく SSH になります。
- 手動で入れたサービスのことは、「デバイス」タブには分かりません。

必ず押さえておくこと：

- wstunnel server は既定ですべてを通します。`--restrict-to` がなければ、compose の内部ネットワークへの開けっぱなしの中継になり、guacd やリモートブラウザーのセッションマネージャーにも届いてしまいます。
- Telepy は wstunnel を同梱も管理もしません。wstunnel のプロトコルはメジャーバージョン間で変わるので、各デバイスのクライアントもコンテナに合わせて更新する必要があります。

### 前段に L4 プロキシがある場合：PROXY protocol

ゲートウェイの前に L4 プロキシ（nginx stream、HAProxy の `mode tcp`、クラウドの NLB）があると、どの接続もプロキシから来たように見えます。

プロキシを、サイト設定 →「サーバー」の「SSH ゲートウェイの PROXY protocol 送信元」か、`.env` の `GATEWAY_PROXY_PROTOCOL_FROM` に登録します。

- IP または CIDR を、カンマか空白で区切って書きます。空ならオフです。
- `.env` で設定した場合は `.env` が優先され、ページの欄はロックされます。
- 以後、プロキシが送る v1 / v2 ヘッダーの送信元が、あらゆる場所で元の接続相手の代わりに使われます。イベント、endpoint、トンネルを使っている人、IP 変更のアラートです。

ゲートウェイの扱い：

- **あってもなくてもよく、自動で判別**：ゲートウェイは最初の 1 バイトをのぞき見ます。SSH は必ず `S` で始まり、PROXY ヘッダーは `P` か `\r` で始まります。5 秒間何も届かなければ、バナーを待っている直接接続のクライアントとみなします。
- **1 バイトも読みすぎない**：ヘッダーの終わりでぴったり読むのをやめ、その後の SSH には一切触れません。そのため設定を間違えても、直接接続するデバイスを締め出すことはありません。
- v1 の `UNKNOWN` と v2 の `LOCAL` は、元の接続相手をそのまま使います。形式の壊れたヘッダーや、5 秒以内に送り終わらないヘッダーは拒否し、`refused_proxy` イベントとして記録します。接続してすぐ切るだけのもの（ヘルスチェック）は記録しません。
- **登録していない送信元のヘッダーは決して読みません**：読んでしまうと誰でも好きな IP を名乗れるようになり、IP 変更のアラートが意味をなさなくなります。

デバイス側のスクリプトは変更不要です。

## トンネルは鍵で見分ける

鍵でログインした時点で、ゲートウェイにはどのトンネルかが分かっています。そのため、デバイスが forward を要求するときに、どの番号を指定しても関係ありません。

- 0 を要求しても、他人の番号を要求しても結果は同じです。forward は必ずトンネル自身の番号（`reverse_port`）で記録され、デバイスに返されるのもその番号です。
- 要求された番号が違っていた場合は、`forward` イベントにその旨が記録されます。
- ユーザー鍵ではトンネルを特定できないので、これまでどおり、持ち主が所有するトンネルの番号しか forward できません。

デバイス側のスクリプトは必ず `-R 0` と書きます（Docker 版では `SSH_TUNNEL_PORT=0`、1 行のコマンドでの追加も同じ）。番号はサーバーにしか存在しません。

トンネルを削除するときの削除スクリプトも、同じように**鍵**でトンネルの持ち物を探します。コマンドラインやファイル中の `-i <鍵ファイル>` や `IdentityFile`、Docker の `KEY_FILE=` や `<path>:/id_rsa`、コンテナが `/id_rsa` にマウントしている鍵が対象です。隣の `.pub`、または `ssh-keygen -y` の結果がトンネル鍵と一致する必要があります。ポート番号を書いた古いスクリプトは、従来どおり番号で見分けます。

1 行のコマンドでの追加が作ったバックグラウンドループを再実行するときは、このトンネル専用の known_hosts ファイル（`telepy-<インストール ID>.known_hosts`）で古い ssh を見つけます。番号では見分けられず、鍵ファイルは別の Telepy サーバーのトンネルにも使われているかもしれないからです（[他のサーバーのものには触れない](#他のサーバーのものには触れない)を参照）。

### ノート PC はトンネル名で接続する

ノート PC の `direct-tcpip` は、`localhost:<番号>` のほかに `<トンネル名>:<任意のポート>` も受け付けます。トンネル名はサイト全体で一意です。そのため、生成される ssh config のデバイスのブロックは、ただの `HostName <名前>` / `Port 22` になり、`ProxyCommand ssh -W %h:%p <サーバーのブロック>` を経由してつながります。古い設定ファイルもそのまま使えます。

名前は大文字と小文字を区別せずに照合します。OpenSSH は `HostName` を小文字にしてから `%h` に入れるからです（`MyBox` はゲートウェイに `mybox` として届きます）。完全に一致するものが優先され、なければこの鍵で届くトンネルを選びます。以前は完全一致だったので、名前に大文字を含むトンネルは拒否されていました（`administratively prohibited`）。

接続できる人は変わりません。所有者、ADMIN、または許可されたアカウントを 1 つ以上持つ共有相手です。要確認のトンネルは、先に Web 画面での確認が必要です。次の場合、ゲートウェイは個人鍵をログインの段階で拒否します。

- 鍵の有効期限が切れている（`expired_key` イベントとして記録）
- アカウントが無効になっている
- 管理者がその人の「個人 SSH 鍵」機能をオフにしている

### トンネル名は OpenSSH のルールに従う

トンネル名は ssh_config のホスト名も兼ねるので、OpenSSH のルールに従います。使えるのは英字、数字、`.` `_` `-` だけで、英字か数字で始まり、最大 63 文字、大文字と小文字を区別せずに一意である必要があります。それ以外の文字が使えない理由は次のとおりです。

- 空白は ssh_config で 1 つの名前を 2 つに分けてしまい、OpenSSH 9.6 以降はコマンドラインでも拒否します。
- `%` は `%h` のように展開されてしまいます。
- `* ? ! ,` はパターン用の文字で、`#` はコメントの始まりです。
- `@` と `:` は Telepy 自身が `<トンネル>@<アカウント>` と `<トンネル>:<パス>` で使っています。

このルールができる前からある名前も、引き続き使えます。生成される設定ではそれらを `HostName localhost` / `Port <番号>` と書き、Web 画面が所有者に名前の変更を勧めます。

### 1 つの ssh config に複数の Telepy

- サーバーのブロックのエイリアスは `telepy-<ドメイン>-<port>`（`HostKeyAlias` と同じ文字列）で、Telepy サーバーごとに 1 つなので、複数のサーバーが 1 つの設定の中で干渉し合いません。
- 古い共有の `telepy-ssh-server` ブロックは、このサーバーのものだと確信でき、ほかに使っているものがない場合に限って、インストールコマンドが削除します。
- 2 台のサーバーに同じ名前のデバイスがある場合、インストールコマンドは既存のブロックの ProxyCommand がどのサーバーを経由するかを確認します。別のサーバーのものなら、上書きせずに残し、残した名前を一覧で示します。
- どちらかのサーバーに「名前の接頭辞」（個人設定 `ssh_alias_prefix`。たとえば `work-` → `ssh work-pi`）を設定すれば、両方を並べて使えます。

## 正しいマシンにつながっているか

デバイスには Telepy のユーザーの見分けがつきません。見えるのは、自分が信頼しているサービス鍵だけです。そこで Telepy は 3 つのことを自分で確かめます。相手のマシンが前回と同じであること、そのマシンが 1 つのアカウントのものであること、そしてマシンが自分のトンネルの鍵しか信頼していないことです。

### デバイスのホスト鍵を固定する

バックエンドはデバイスに接続するたびに、デバイスの sshd が示すホスト鍵を確認します。

- **最初の接続**：その鍵を記録します（初回の接続を信頼する TOFU）。たいていは、デバイスが参加した直後にバックエンド自身が行う確認のためのログインです。
- **後で別の鍵になった**：ハンドシェイクを拒否し、新しい鍵を確認待ちとして残し、所有者と共有相手に通知します。
- **対処**：所有者か ADMIN がトンネルの詳細を開き、「鍵と識別」→「デバイスの識別」で指紋をデバイス上のものと見比べてから「この鍵を信頼」を押します。「消去」を押すと固定が外れ、次の接続で鍵を記録し直します。

なぜここまでするのか。トンネル鍵を手に入れた人は、`-R` を自分の sshd に向けてデバイスになりすますことができます。そうなると、ターミナルへの入力、アップロードしたファイル、リモートデスクトップのパスワードを横取りされてしまいます。鍵を固定しておけば、なりすましはハンドシェイクの段階で止まり、サービス鍵でのログインは送られもしません。

ノート PC も同じ方法でデバイスを確認します。生成される ssh config のデバイスのブロックでは、`UserKnownHostsFile ~/.ssh/telepy_known_hosts` と `HostKeyAlias <サーバーのエイリアス>-device-<トンネル ID>` を使います。

- Telepy が鍵を固定済みなら、ブロックは `StrictHostKeyChecking yes` になり、固定した行はサーバーの行と同じファイルに入ります。インストールコマンド、`telepy config install`、`telepy ssh` のどれもまとめて保存します。
- まだ固定していなければ `accept-new` になり、ノート PC が初回の接続で鍵を記録し、以後は別の鍵を拒否します。
- 所有者が新しい鍵を信頼したら、ノート PC ではインストールコマンドを 1 回実行し直す必要があります。

以前のデバイスのブロックは `StrictHostKeyChecking no` だったので、トンネルが他人の sshd に向けられると、ノート PC の `ssh <デバイス>` はそのままそこへ入ってしまいました。

### 1 台のマシンに持ち主は 1 人

デバイスが共有のサービス鍵を信頼している間は（最初はすべてのデバイスがそうで、古いデバイスは今もそうです）、あるマシンの sshd にトンネルを向けられる人なら誰でも、「自分のトンネル」のアカウント一覧でそのマシンにログインできてしまいます。root も含めてです。向けるのは難しくありません。そのマシン上のどのアカウントからでも、同じ LAN や VPN からでも、`-R <port>:<そのマシン>:22` を実行すれば済みます。これを止めるのが固定したホスト鍵で、これがそのままマシンの身元にもなります。

**固定する前に、同じ鍵をほかに誰が信頼しているかを確認します。**

- 別のアカウントのトンネル：ハンドシェイクを拒否します。エラーは `device managed by another account` で始まり、API とリモートデスクトップはエラーコード `device_claimed` を返します。
- 拒否されたトンネルには `claim_refused` が記録されます。そのマシン本来のトンネルには `claim_attempt` が記録され、所有者と ADMIN の共有相手に `DEVICE-CLAIM-ATTEMPT` の通知が届きます。通知は鍵ごとに 1 回だけです。
- 「この鍵を信頼」も「消去してから再接続」も同じルールに従うので、どちらも抜け道になりません。
- 自分の別のトンネル：通常どおり固定され、`GET …/host-key` の `same_machine` に表示されます。

**参加スクリプトは登録の時点でホスト鍵を送ります**（デバイス自身で `ssh-keyscan` を実行）。

- 別のアカウントのマシンは、トンネルを作る前に拒否されます（409）。メッセージは、所有者に共有を頼むか、複製した VM ならホスト鍵を作り直すよう勧めます。
- 自分の別のトンネルなら `SAME_MACHINE_AS` が返り、Web 画面でそのことを知らせます。
- 新しいトンネルのホスト鍵はその場で固定されるので、最初の接続で目の前の鍵を何でも信じることはもうありません。
- 再参加のときは、まだ固定がない場合か、少なくとも 1 つの鍵が一致する場合にだけ固定を追加します。すべての鍵が変わっていれば、接続時の確認で拒否されます。

**同じ考え方のルールがほかにもあります：**

- デバイス鍵はサイト全体で一意で、コメントや所有者は関係ありません。デバイス鍵には、他人の個人鍵（自分の個人鍵なら構いません。普段使っているコンピューターもデバイスになれます）やサービス鍵は使えません。ゲートウェイは鍵しか見ないので、先に登録されたトンネルがその鍵のデバイスとして扱われてしまうからです。
- ゲートウェイ経由でノート PC から SSH するには、許可されたアカウントが 1 つ以上必要です。1 つもない共有相手は、デバイスの sshd へのチャンネルを開けません。許可リストが唯一の境界で、ADMIN はそのリストを管理する立場なので例外です。

トンネルを削除すると、固定も一緒に消えます。マシンは持ち主のいない状態に戻り、次にそこへ向けられたトンネルが固定します。削除時には、トンネル自身のサービス鍵が必ずデバイスから取り除かれます。古い共有の鍵がまだデバイスに残っている場合は、削除ダイアログで「共有の Telepy キーも … から取り除く」にチェックを入れてください（そのマシンの最後のトンネルなら最初からオンです）。そうして初めて、マシンが本当に Telepy から離れます。

### トンネルごとに 1 本のサービス鍵

固定が他人のマシンを締め出すのに対し、トンネルごとの鍵は問題を根元から取り除きます。以前はサイト全体でサービス鍵が 1 本だけ（`SSH_IDENTITY`）で、すべてのデバイスがそれを信頼していました。今は次のとおりです。

- 各トンネルは、必要になった最初のときに自分専用の ed25519 の鍵ペアを作ります。
- 秘密鍵は `SECRET_KEY` から導いた鍵で封印して、データベースに保存します。
- 公開鍵（`… telepy-tunnel-<id>`）は、ウィザード、1 行のコマンドでの追加、Docker のスクリプト、トンネルの詳細に渡されます。デバイスが許可するのはこの 1 本だけです。

実際の動きは次のとおりです。

- **ログインの順番**：まずトンネル鍵を使い、デバイスにまだトンネル鍵が入っていないときだけ共有の鍵に戻ります。トンネル鍵でログインできたら、そのアカウントを確認済みとして記録します。
- **古いデバイスの移行**：次の鍵の同期で、トンネル鍵がすべてのログインアカウントに入り、次の接続からはそれを使います。共有の鍵がアカウントから外れるのは、**同じマシン上でそのアカウントを載せているすべてのトンネル**が自分の鍵でログインし終えてからです（イベント `service_key_migrated`）。
- **手動での削除**：デバイスの鍵パネルは共有の鍵に「共有 · 旧」と表示します。管理者は同じルールのもとで手動で外せます。
- **サーバーの引っ越し中**：サイト設定 →「サーバー」の「デバイスの共有サービス鍵を残す」（または `.env` の `KEEP_SHARED_SERVICE_KEY=true`）をオンにすると、共有の鍵は自動でも手動でも外されず、すべてのデバイスに残ります。以前の Telepy サーバーがまだ同じ鍵で同じデバイスにログインしている間に使います。トンネル鍵は変わらずインストールされ、変わらず先に使われます。
- **トンネルの削除**：そのトンネル自身の鍵は必ずデバイスから取り除かれます。削除ダイアログのサービス鍵のオプションは、今は共有の鍵だけを対象にしています。
- **衝突しない**：トンネルのサービス公開鍵は、デバイス鍵や個人鍵として登録できません。

> [!WARNING]
> `SECRET_KEY` を変えると封印した鍵が開けなくなり、該当するトンネルは共有の鍵に戻ります。開けない鍵の数は `doctor` の `tunnel keys` チェックで分かります。共有の鍵がすでに外されたデバイスは、もう一度許可し直す必要があります（ウィザードのステップ 3、または 1 行のコマンドでの追加）。

## デバイスとアカウントごとに接続を 1 本共有

クリックのたびに SSH ログインし直していては遅いうえ、デバイスの認証ログが不正侵入の試みのように見えてきます。そこでバックエンドは**トンネルと OS アカウントの組ごとに SSH 接続を 1 本**保ち、その上にチャンネルを開きます。

- 同じ OS アカウントの利用を許可された Telepy ユーザー同士は 1 本の接続を共有し、それぞれ自分のチャンネルを使います。権限は、借りる前にこれまでどおり確認します。
- 接続は最初に使うときに開き、すべてバックエンドの中で完結します。デバイスのトンネル上に forwarded-tcpip チャンネルを開き、その上でデバイスの sshd とハンドシェイクします。同時に複数のリクエストが来ても、ハンドシェイクは 1 回だけで、残りはそれを待ちます。

### セッション数の上限（MaxSessions）

OpenSSH の MaxSessions が制限するのはセッションチャンネル（shell、exec、sftp）だけで、direct-tcpip は対象外です。そのため、プールもセッションチャンネルだけを数えます。

- セッションチャンネルに当たるのは、ターミナルのタブ、exec、デバイスの鍵リスト、macOS の名前解決です。
- 1 本の接続で同時に使えるのは最大 8 本です。sshd の MaxSessions の既定値は 10 なので、2 本は余らせています。デバイスは、こちらが閉じた処理を終えてから（shell はまず終了する必要があります）枠を空けるので、返した直後の枠をすぐ使うと拒否されることがあるからです。
- デバイスが MaxSessions をもっと小さくしていてチャンネルを拒否した場合、プールはその接続が実際に何本まで持てるかを覚えて、2 本目の接続を開きます。拒否は一時的なこともあるので、覚えた上限は 2 分で失効します。
- direct-tcpip だけを開く機能（リモートブラウザーの SOCKS、リモートデスクトップと RustDesk、LAN の中継）は、代わりにリース（lease）を借ります。リースは接続が回収されないようにするだけで、枠は使いません。以前はそれぞれが 1 枠使っていたので、リモートブラウザーとリモートデスクトップを開いていると、ターミナルのタブに使える枠が 2 つ減っていました。

### ファイルは sftp チャンネル 1 本を共有

SFTP のリクエストには番号が付いているので、何人が同時に 1 本のチャンネルを使っても問題ありません。そこで接続ごとに sftp チャンネルは 1 本だけ開き、SFTP REST とすべてのファイル管理がそれを使います。

- **利点**：リクエストのたびにチャンネルを開き直し、サブシステムを要求し、INIT を行う必要がなくなります。これはトンネル上で何往復もかかる処理です。ファイル管理をいくつ開いても、使う枠は 1 つです。
- **代償**：デバイスの sftp-server は一度に 1 つのリクエストしか処理しないので、1 つのリクエストが詰まると（たとえば応答しないネットワークドライブ）全員が待たされます。
- **安全策**：バックエンドは送ったリクエストと受け取った応答を数えています。チャンネルが閉じたとき、またはリクエストが待っているのに 15 秒間何も届かないときは壊れたものとみなし、次に借りる人には新しいチャンネルを渡します。ディレクトリ一覧の取得に失敗したファイル管理は、自分でチャンネルを取り替えて 1 回だけやり直します。
- **アイドル**：5 分間使われなければ sftp チャンネルを閉じて枠を返します。接続自体がまだ使われていても同じです。
- **sftp サブシステムがない**：デバイスに拒否されたら、ファイル管理はその返事が届いた時点で exec に切り替え、SFTP 起動の 10 秒のタイムアウトを待つことはありません。

### アイドル接続、タブ、オフラインのデバイス

- 何も借りられておらず、5 分以上アイドルの接続は閉じられます（30 秒ごとに確認）。
- デバイスが切断すると接続は自ら無効になり、開いているターミナルのタブは閉じられ、次に使うときに再接続します。
- ターミナルのタブ 1 つがチャンネル 1 本で、タブを閉じればそのチャンネルだけが閉じます。以前は `killpg` 1 回が共有の ControlMaster に当たり、すべてのタブがまとめて閉じることがありました。効率はよいのですが、向きが逆でした。
- オフラインのデバイスには、タイムアウトを待たずにすぐ close コード 4005 を返します。

### Mac とホスト名

Apple の `sshd-session` には落とし穴があります。宛先が**名前**の direct-tcpip を受け取ると、権限分離の子プロセスが fork の後に getaddrinfo を呼んで abort し、SSH 接続ごと落ちてしまうのです。

Chromium は SOCKS で必ず名前を送るので、リモートブラウザーはページを開いた瞬間にこれを踏みます。共有接続では、同じデバイス・同じアカウントのターミナルのタブやファイル管理も道連れになります。そこで、SOCKS プロキシや LAN の中継が direct-tcpip を開く前に、バックエンドは次のようにします。

- 接続ごとに OS を 1 回確認します（`uname -s`）。
- Darwin なら、**デバイス上で** `/usr/bin/dscacheutil` を使って名前を IP に解決し（IPv4 優先。内部の名前や `.local` の名前も通常どおり使えます）、その IP に対してチャンネルを開きます。
- ほかの OS では、これまでどおり名前をデバイスに渡して解決させます。`ssh -D` と同じです。

Mac での細かい点：

- 同じ名前を同時に問い合わせても実行は 1 回で、同時に走る問い合わせは最大 2 件です。どれもセッションチャンネルを 1 本借りるので、上の上限に数えられます。
- 解決できた結果は 60 秒、解決できなかった結果は 10 秒キャッシュします。
- 解決できなければ、その CONNECT は失敗します。名前を Apple の sshd に渡すことは**絶対に**ありません。

### 共有で何が減るか

同じデバイス・同じアカウントなら、2 回目の操作からハンドシェイクは発生しません。テストで測った数字です。

- ディレクトリ一覧を 5 回連続：ログイン 1 回、sftp チャンネル 1 本
- 同時に 12 リクエスト：ログイン 1 回、sftp チャンネル 1 本
- ターミナルのタブ 3 つとファイル管理：ログイン 1 回
- リース 10 個とセッションチャンネル 8 本：ログイン 1 回

## ポート：どこで使い、足りなくなるか

| ポート | 用途 | 数 | 足りなくなるか |
|---|---|---|---|
| 24242、8787 | 外部向け：デバイスのトンネルと Web 画面（Web ポートを使うデバイスも 8787 を使う） | 固定 | いいえ |
| `reverse_port` | トンネルごとの**番号** 1 つ。ゲートウェイはデバイスの forward をこの番号で記録する。**ローカルのポートは一切使わない** | トンネル 1 本につき 1 つ | 番号の空きはおよそ 64,500 トンネル分 |
| SOCKS ポート | リモートブラウザーのセッションごとに 1 つで、ブラウザーのコンテナが接続してくる。Chromium の SOCKS は認証情報を扱えないので、共有できない | セッション数の上限まで | いいえ |
| LAN ホスト用の使い捨て入口 | LAN ホストのターミナルを開くたびに、`127.0.0.1:<一時ポート>` が接続を 1 本待つ（30 秒誰も来なければ閉じる） | 開いている LAN ターミナルの数 | いいえ |
| リモートデスクトップの折り返しポート | RDP / VNC のセッションごとに使い捨ての listener が 1 つ（ランダムなポート、guacd のアドレスだけを受け付ける）。guacd が接続するとデバイスの direct-tcpip につながり、listener は閉じる | 開いているデスクトップセッションの数 | いいえ |

バックエンドがデバイスに届くときは loopback の TCP を一切通らないので、一時ポートが尽きることも、TIME_WAIT がたまることもありません。`reverse_port` はただの番号なので、コンテナ内の何とも衝突せず、割り当てるときは使用中の番号を飛ばすだけです。

## デバイス上の名前

### 名前を変えた理由

以前デバイスに入れていたものの中には、人やサーバーの名前を含むものがありました。

- 手書きの移行スクリプトが入れた `telepy-natlee.service`、`info.natlee.telepy`、`telepy_natlee_known_hosts`
- 1 行のコマンドでの追加が作る unit の説明に書かれたトンネル名
- すべてのトンネルで共通の `telepy-tunnel.service`。同じマシン上の 2 本のトンネルが互いに上書きしていました。
- `~/.ssh/telepy_known_hosts`。2 台目のサーバーが参加すると、1 台目のホスト鍵を上書きしていました。

他人のマシンに `telepy-natlee` があれば、誰がサーバーを運用しているかが分かってしまいます。そのうえ Telepy は何をインストールしたかを把握していなかったので、削除のときは推測するしかありませんでした。

### インストール ID

各トンネルは、必要になった最初のときに `[a-hj-km-np-z2-9]` から 8 文字のランダムな ID を引きます。ID はサイト全体で一意で、トンネルと一緒に削除されます。デバイス上の名前はすべてこの ID から作ります。

| 対象 | 名前 |
|---|---|
| systemd の unit（system、`--user`、autossh のサービス） | `telepy-<id>.service` |
| launchd のジョブ | `com.telepy.tunnel.<id>` |
| バックグラウンドループ | `~/.ssh/telepy-<id>.sh` |
| ホスト鍵 | `telepy-<id>.known_hosts` |
| アンインストールスクリプト | `telepy-<id>-uninstall.sh` |
| Web ポートのキャリア | `telepy-<id>-ws.*` |
| Docker コンテナ | `telepy-<id>` |

unit の説明には `Telepy reverse tunnel <id>` としか書きません。

- ID にはユーザー名もドメインもトンネル名も含まれないので、トンネルの名前を変えてもデバイスには手を入れずに済みます。トンネルのページで ID を検索すれば、そのトンネルが見つかります。
- ハッシュではなくランダムにしたのは、記録がなければどのみち元の名前には戻せず、ハッシュだと `SECRET_KEY` と一緒に変わってしまうからです。
- `telepy-` の接頭辞は残し、デバイスの管理者が何なのか分かるようにしています。出どころの分からないサービスが SSH で外へつなぎ続けていたら、どう見てもマルウェアです。よその管理者への第一印象としては、できれば避けたいところです。
- ssh のコマンドには、接続先のサーバー名（`telepy@<ドメイン>`、`HostKeyAlias`）が今も書かれています。接続そのものに必要だからです。

### インストール内容の調査

削除に使う削除スクリプトには、調査モードもあります。何も変更せず、見つけたものを報告するだけです。unit や plist のパス、ループ、実行中の ssh プロセスとその所有者、crontab の行、コンテナ、鍵、known_hosts ファイルが対象です。

結果は保存され、次のタイミングで更新されます。

- 1 行のコマンドでの追加が確認まで済んだあと
- 毎日のデバイス確認のとき（一度も調査していないか、前回の調査から 7 日以上たっている場合）
- トンネルの詳細の「デバイス」タブ、「デバイス上のインストール」で「再確認」を押したとき

Windows のスクリプトは削除しかできず、調査はまだ実装されていません（プラットフォームだけを返します）。

調査が対処していること：

- **ログインアカウントが読めないファイル**：root で動く unit は鍵を `/root/.ssh` に置くことが多く、`ubuntu` のようなアカウントからは読めません。ログインアカウントが `sudo -n` を使えるなら、鍵、unit、ループのスクリプトを `sudo -n cat` / `test -f` / `ssh-keygen -y -P ''` で読みます（読み取りのみ。同じファイルは 1 回しか尋ねません）。
- **鍵を指定していないサービス**：コマンドが鍵ファイルを指定しておらず、このゲートウェイのポートを明示的に指定していて、`-R` を持つ場合は、実行しているアカウントの既定の鍵（`~/.ssh/id_ed25519`、`id_ecdsa`、`id_rsa`…）と照合します。実行しているアカウントは、プロセスの所有者、unit の `User=`、plist の `UserName`、何も書いていないシステムレベルの unit なら root、それ以外はログインアカウントです。既定の鍵はその人自身のファイルなので、削除で消すことはありません。
- **launchd の plist**：plist は引数を 1 つずつ別の `<string>` に入れるので、照合の前に 1 行につなげます。そうしないと `-p` も `-i` も読めません。
- **OpenWrt**：procd の init スクリプト（`/etc/init.d/*`。`/etc/rc.common` があるときだけ見ます）と `/etc/rc.local` の行も、同じルールで見分けます。削除のときは、init スクリプトを disable してから停止スクリプトが stop して削除し、rc.local はその行だけを取り除きます。
- **Dropbear のコマンド長の上限**：OpenWrt のルーターでよく使われる Dropbear は、9000 文字を超える exec コマンドを受け付けませんが、このスクリプトは 25 KB あります。6000 文字を超えるスクリプトは分割して送り（`printf >> <一時ファイル>`）、最後の exec でそのファイルを実行して削除します。これならどの sshd でも受け付け、BusyBox の ash（Alpine）でも動作を確認しています。

### 他のサーバーのものには触れない

同じ鍵が 2 台の Telepy サーバーで使われていることがあり、以前は鍵だけで照合したせいで、もう一方のサーバーの unit まで外してしまったことがあります。そこで今は、ファイルやコマンドラインにポートが書かれていて（`-p N`、`'-p' 'N'`、`Port=N`、`SSH_REMOTE_PORT=N`）、そのどれもこのゲートウェイの `REVERSE_SERVER_SSH_PORT` でなければ、別のサーバーのものとみなします（`kept other-server`）。削除、調査、名前の変更のいずれもそれを飛ばします。ポートを書いていないものは、従来どおり見分けます。

### オフラインにせずに名前を変える

Telepy が付けたのではない名前（手書きや移行スクリプトで作られたもの。たとえば `telepy-natlee.service`）には「要変更」の印が付き、トンネル一覧にも「変更が必要なサービス名」と表示されます。「デバイス上で名前を変更」を押すと、プライベートな名前に置き換わります。

厄介なのは、名前を変えるコマンド自体がこのトンネルを通って届くことです。古いサービスを先に止めるのは、乗っている足場を自分で外すようなものです。そこで、新しいサービスを先につなぎ、古いほうはその後で外します。

1. **計画**：もう一度調査し、実行中の ssh（`-i`、`-p`、`-R` の宛先、`user@host`、ProxyCommand）と見つかった古いサービスから計画を立てます。方式は元と同じです。systemd のシステム unit はシステム unit のまま元の `User=` を使い、`--user` の unit、LaunchAgent、ループは今それを動かしているアカウントで動かします。システムレベルには root か `sudo -n` が必要です。鍵、サーバー、ポート、転送先は変えず、known_hosts はこのゲートウェイのホスト鍵で書き直します。計画を止める理由（Windows、root が必要、解釈できないコマンド、相対パスの鍵など）は Web 画面で説明します。
2. **引き継ぎの準備**：しばらくの間、同じトンネル（同じトンネル鍵で見分けます）の 2 本目の接続を拒否しません。その forward は待機として記録し、成功を返すので、新しい ssh が `ExitOnForwardFailure` で終了することはありません。forward は古い接続に残ったままです（イベント `standby_forward`）。
3. **インストール**：古い接続を通して行います。ファイルは古いものの隣に書いてから名前を変え、新しいサービスを起動します。
4. **待機**：待機中の接続が現れるのを待ち（既定で 45 秒）、それを通して 1 回ログインします。
5. **切り替え**：forward を新しい接続に移します（イベント `handover`）。古い接続はまだ生きていますが、もうトンネルは運んでいません。
6. **古いものの撤去**：**新しい**接続を通して行います。探し方は削除と同じですが、ID で名付けたものはすべて飛ばし、鍵も残します。古い unit、plist、ループ、crontab の行、古い known_hosts（ほかに使うものがなければ）、古いアンインストールスクリプトを取り除き、停止スクリプトはいつもどおりバックグラウンドで動きます。
7. **確認**：古い接続が切れ、forward が新しい接続に残っていて、13 秒以内にほかの接続が現れないことを確かめます（現れたら、何かが古いサービスを再起動しているということです）。最後にもう一度調査します（イベント `service_renamed`）。

手順 2〜5 のどこかで失敗したら、Telepy は古い接続を通していま入れたものを取り除き、引き継ぎの準備を解除します。古いサービスには一切触れておらず、トンネルはその間ずっとオンラインのままです。途中で古い接続がたまたま切れても、待機中の接続が自動で引き継ぐので、そこでもオフラインにはなりません。

代償は 1 つだけです。古い接続が閉じるとき、このデバイスで開いている Web ターミナルとファイル管理が 1 回だけ再接続します。チャンネルが古い TCP 接続の上にあったからです。

次の 2 種類の名前は、この手順が要りません。

- **Telepy 自身の以前の名前**（1 行のコマンドでの追加の `telepy-tunnel-<n>.service` / `com.telepy.tunnel.<n>` / `telepy-tunnel-<n>.sh`、autossh の `telepy-tunnel.service`、コンテナ `telepy-tunnel`）は人の名前を含まず、削除のときも見分けられます。「Telepy の以前の名前」と表示され、変更するかどうかは任意です（「それでも変更」）。
- **`/etc/rc.local` の行**は、Telepy が自分で置き換えることはしません（名前の変更は `unsupported` を返します）。手で変えるか、1 行のコマンドでの追加をもう一度実行してください。プライベートな名前でインストールし直します。なお、OpenWrt の init スクリプトはほかのサービスと同じように名前を変えられます。

### 1 台のマシンに複数の人やサーバー

- 別々の Telepy アカウントが、同じマシンにトンネルを向けることはできません（[1 台のマシンに持ち主は 1 人](#1-台のマシンに持ち主は-1-人)を参照）。
- OS アカウントが違う場合や、別のサーバーに接続する場合、以前は共通の名前がぶつかっていました。`telepy-tunnel.service`、コンテナ `telepy-tunnel`、`/etc/ssh/telepy_known_hosts`、`~/.ssh/telepy_known_hosts`、そしてトンネル番号で名付けた `telepy-tunnel-<n>`（データベースを複製した 2 台のサーバーでは番号が同じになります）です。今はすべてインストール ID で名付けています。
- 1 つの OS アカウントが**同じ鍵で** 2 台のサーバーに接続している場合：削除のとき、もう一方のサーバーへ接続するもの（unit、スクリプト、実行中の ssh）が `~/.ssh/telepy_tunnel_*` を使っている限り、その鍵は残します（`kept key … another server`）。1 行のコマンドでの追加のループが止めるのは自分の ssh だけで、鍵ではなく known_hosts ファイルで見分けます。
- 調査は、別のサーバーへ接続するものを `kept other-server "<file or ssh> (port N)"`、共有の鍵を `note key-shared <path>` として報告します。「デバイス」タブの「このデバイスの接続先」の図は、これをもとにサーバーごとに 1 行ずつ描きます。

> [!NOTE]
> データベースを丸ごと複製して 2 台目のサーバーを動かすと、インストール ID も複製されるので、2 台が同じデバイスに入れるものは同じ名前になります。

### 削除時の後片付け

- 削除では、新しい名前の unit、launchd のラベル、ループ、アンインストールスクリプト、キャリアのファイル、`telepy-<id>.known_hosts` を見分けます。
- known_hosts ファイルは、unit、plist、ループ、`~/.ssh/config`、CLI の設定のどれも使っていないときだけ削除します。デバイスは誰かのノート PC でもあることが多く、`~/.ssh/telepy_known_hosts` はそのノート PC の ssh config が使っているかもしれないからです。
- 1 行のコマンドでの追加をやり直したときに、同じトンネルが古い名前（`telepy-tunnel-<id>`）でインストールされているのを見つけたら、先にそれを止めて取り除いてから新しいものを入れます。2 つが同じトンネルを奪い合うことはありません。

### 余分なコピー

名前だけでは「人が付けた名前」と「別のインストール ID」を区別できません。`telepy-natlee` も ID のように見えるからです。これは実際のルーターで起きました。調査がある init スクリプトを名前の変更が必要なものとして示しましたが、実は削除したトンネルの残りでした。しかも再参加のときに新しい鍵が**同じ**鍵ファイルに書き込まれていたので、その残りは新しいトンネルの鍵をそのまま使っていて、再起動すると両方が起動してトンネルを奪い合う状態でした。

そこで Telepy は 3 つの問いを立てます。名前に関係するのは最後の 1 つだけです。

1. **このトンネルのものか？** このトンネルの鍵を使い、このゲートウェイに接続しているか。
2. **動いているのはどれか？** 調査で見えた ssh がすべてインストール ID で名付けたもの（コマンドラインに `telepy-<id>.known_hosts` を含む）なら、そのトンネルのほかのサービスやコンテナは、名前が何であれ**余分なコピー**です。名前の変更が必要なものではなく、名前の変更は `extra` を返します。
3. **名前から人が分かるか？** プライベートなのは、インストール ID から作った名前だけです。トンネルを削除すると、その ID、名前、所有者を台帳に記録し、新しい ID がそれと重なることはありません。名前に含まれる `telepy-<x>` や `com.telepy.tunnel.<x>` は、台帳と一致したときだけ、その削除済みトンネルの残りとして表示します。トンネル名は同じ所有者にしか見せません。Telepy の以前の標準の名前は、決まった一覧です。

「デバイス」タブの「余分なコピーを削除」（または `POST …/device-install/tidy`）には引き継ぎが要りません。余分なコピーは、いまつながっている側ではないからです。

1. もう一度調査します。余分なコピーが実際にあること、Windows でないこと、システムレベルのものなら root でログインできることが条件です。
2. **現在の**接続を通して、名前の変更と同じ後片付けを行います。ID で名付けたものはすべて飛ばし、鍵は残します。init スクリプトは disable してから停止スクリプトが stop して削除し、known_hosts ファイルはそのコピーが使っていたものだけを一緒に削除します。
3. 13 秒間見守ります。接続は保たれ、forward は動かず、ほかの接続も現れないことを確かめます。
4. もう一度調査して確認します（イベント `service_extra_removed`）。

削除スクリプトは `~/.ssh/telepy-*.sh` も調べます。このトンネルの鍵でこのサーバーに接続するループは、動いていなくてもこのトンネルのものとみなすので、削除したトンネルが残した休眠中のループも見つかります。

## まだできていないこと

- **AI セッションと LAN スキャンは、今も専用の接続を開きます。** 1 つの AI セッションは同時に最大 4 本のチャンネル（コマンドと対話シェルで共用）に加えて SFTP を使うので、1 セッションとして数えると、プールはデバイスの MaxSessions の使用量を少なく見積もってしまいます。チャンネルはすでにバックエンド内で開いていてポートも使わないので、接続を共有しても省けるのはハンドシェイク 1 回だけです。そのため、まだ移していません。
- **`reverse_port` の上限。** トンネルはすでに鍵で見分けており、デバイスが `-R` でどの番号を要求しても関係なく、ノート PC も `ssh -W <トンネル名>:22` を使います。ただし `reverse_port` は今もトンネルごとの 16 ビットの内部番号です。トンネルがおよそ 6 万本を超えたら、もっと大きな整数に広げる必要があります。型と割り当て処理を変えるだけで、デバイスにもノート PC にも手を入れる必要はありません。そんな悩みなら大歓迎です。
