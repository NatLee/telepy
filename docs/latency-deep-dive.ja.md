# あの「ms」はどこから来るのか？ —— Telepy のレイテンシ表示ウィジェット

<p align="center"><a href="./latency-deep-dive.md">English</a> | <a href="./latency-deep-dive.zh-TW.md">繁體中文</a> | <b>日本語</b></p>

> **2026年10月の更新：** バックエンドを Rust で書き直したことで、第3・4・5節で説明している
> 「Bash プローブ → Redis → update_ports ポーリング」の仕組みは、内蔵の SSH gateway に置き換わりました
> （この3節には「Django 時代」と付けてあり、設計の背景として原文のまま残しています）。現在の姿は次のとおりです。
>
> - **オンライン / オフライン**は接続イベントです。gateway が `tcpip-forward` の登録または解放を受け取った時点で `StatusState`（`monitor/mod.rs`）を更新します。`ss -tln` のサンプリングはもう行いません。
> - **レイテンシ**：`Gateway::probe_latency`（`gateway/mod.rs`）が15秒ごと（`GATEWAY_PROBE_INTERVAL_SECS`）に、各 forward へ
>   forwarded-tcpip チャネルを開き、デバイスの sshd バナーの先頭1バイトを読みます。測り方は同じで、子プロセスも Redis も不要です。すべて並列に実行し、プローブ1回あたりのタイムアウトは4秒です。
>   結果は `StatusState::record_probes` を通じてそのままメモリに入ります。
> - **常駐の配信役**は `monitor/runner.rs` です（5秒ごとに1ラウンド、`main.rs` が起動します）。デバウンスとスロットリングの規則は `update_ports` からそのまま移植しました
>   （`monitor/ports.rs`：`FLAP_THRESHOLD` 2、5 ms / 6ラウンドの keep-alive）。
> - **測れないことも情報です**：forward は残っているのに、バナーが2回連続（`DEGRADED_AFTER`）で読めない場合、そのトンネルは **degraded** になります（第5節末の番外編2を参照）。
>
> フロントエンドと ping/pong を説明している第1・2・6節は、今も現役です（ファイル名は更新済み）。

> 1バイトの世界旅行と、そのタイムの計り方。

Telepy のターミナルのタイトルバーにある、小さなバッジ。

```
You ●──23ms──● Telepy ●──87ms──● Device   Σ 110ms
```

無害そうに見えますよね。でもその裏には、ブラウザ、Django、Redis、SSH コンテナ、
そして Bash で書いた「貧乏人の ping」までを横断する一連のサプライチェーンがありました。
（これは Django 時代の話です。今は途中の駅が Rust の1プロセスと内蔵の SSH gateway にまとまりましたが、バイトの通る道は同じです。）

## 1. 世界は2つに分かれている

![ターミナルの説明図に区間ごとの往復時間が表示されます](images/ja/terminal-flow.png)

エンドツーエンドのレイテンシは2つのホップに分け、それぞれ別に測り、別の担当が持っています。

| ホップ | 何を測るか | 誰が測るか | どのくらいの頻度か |
|---|---|---|---|
| You → Telepy | ブラウザとサーバーの間の WebSocket の RTT | フロントエンドの `useTerminalPage` | 5秒ごと |
| Telepy → Device | SSH gateway とリモートデバイスの sshd の間のトンネル RTT | バックエンドの `Gateway::probe_latency`（Django 時代：SSH コンテナの `probe_latency.sh`） | 15秒ごと |

なぜエンドツーエンドで測らないのか。
測れないからです。ブラウザはデバイスに届かず、デバイスもブラウザの存在を知りません。
そこで会計士のやり方をとります。帳簿を分けてつけ、最後に合計（Σ）します。
どちらの数字も片道ではなく**往復**の RTT です。光速に文句をつけるのはやめてください。

## 2. ホップ1：ping/pong と「pong がバイナリな理由」

フロントエンドは5秒ごとに、ターミナルの WebSocket へ次の1行を投げます。

```json
{ "action": "ping" }
```

バックエンド（`src/backend-api/src/ws/terminal.rs`。Django 時代は `tunnels/consumers.py`）は `pong` を返します。注目してほしいのは、これが**バイナリフレーム**でありテキストではないことです。

これはエンジニアの気まぐれではありません。
ターミナルの `onmessage` には鉄の掟があります。
> **テキストフレームはすべて `term.write()` で画面に書き込む**。PTY 出力の幹線道路だからです。
もし pong をテキストで返すと、vim の中に5秒ごとに突然 `pong` と出て、まるで心霊現象です。
バイナリで返せば、フロントエンドは「文字ではなく制御メッセージだ」と判断し、時計を見て `Date.now() - pingSentAt` を計算し、state を更新します。画面には傷ひとつ付きません。

フレームの型ひとつで、無数のコードレビューが救われました。

その後、この「バイナリ = 制御メッセージ」という約束は他の機能にも使われるようになりました。切断後もセッションを残すための `shell` メッセージ、コマンドルールの `command` 通知、
「誰が見ているか」を伝える `watchers` は、いずれもバイナリの JSON です。フロントエンド（`lib/commandRules.ts` の `parseTerminalFrame`）は、まず中身がちょうど `pong` かどうかを見て、
違えば JSON として解釈します。テキストフレームは従来どおりすべて `term.write()` に入ります。

その他の WebSocket（通知、単一トンネルの状態、ファイルマネージャー）のアプリケーション層 ping には、テキストの `{"type":"pong"}` で応答します。守るべき xterm がないからです。
ターミナル、ファイルマネージャー、リモートブラウザには、サーバー側の WebSocket Ping ハートビート（`ws::Heartbeat`、20秒ごと、40秒応答がなければ切断）もあり、
close を送らずに相手が消えた接続を検出します。これは生存確認であり、レイテンシの測定には使いません。

## 3. ホップ2：カーネルが嘘をついた日

いちばん素直なのはカーネルに聞くことです。`ss -ti` はもともと TCP 接続ごとの RTT を報告してくれて、無料でリアルタイムです。
私たちも最初はそう考えました。

そこに docker-proxy が現れました。

デバイスの制御用 TCP が、手前の docker-proxy や L4 ロードバランサーで**終端**されていると、
カーネルから見える「相手」は、実は同じマシン上の proxy です。そこでカーネルは自信満々に報告します。

> RTT ≈ 0ms。このデバイスはお隣さんです！

実際のデバイスは数百キロ離れたデータセンターにいて、3段の NAT 越しに手を振っています。カーネルの RTT でレイテンシを測るのは、
「家から玄関まで」の距離で「家から駅まで」を見積もるようなもので、間違ったものを正確に測っているだけです。

### 解決策：アクティブプローブ、主演は Bash（Django 時代）

`ssh/custom_scripts/custom-services.d/probe_latency.sh` のやり方は荒っぽいですが正確です。

1. `ss -tln` で、すべてのリバーストンネルのポート（sshd が `127.0.0.1` に bind している `-R` の転送ポート）を探します。
2. 各ポートについて、Bash の隠し技 `/dev/tcp` で直接 TCP 接続を開きます。nc のインストールも ICMP も不要で、
   Bash 自身がネットワークツールです。
3. `$EPOCHREALTIME`（マイクロ秒精度）で時刻を取り、**1バイトだけ読みます**。

```bash
s=$EPOCHREALTIME
exec 3<>/dev/tcp/127.0.0.1/$port
IFS= read -r -N1 _b <&3        # 対象デバイスの sshd バナーの先頭1バイトを待つ
e=$EPOCHREALTIME
```
この1バイトは、リモートデバイスの sshd のバナー（`SSH-2.0-...` の `S`）です。
ポイントは次のとおりです。
接続要求は**確立済みのリバーストンネル**を通ってデバイスに届き、バナーもトンネルを通って戻ってきます。行って帰ってくるのが、本物のネットワーク往復です。

docker-proxy はカーネルを騙せますが、デバイスのバナーまでは作り出せません。
バイトは本当に全行程を走り切る必要があり、物理は賄賂を受け付けません。

### 並列化：遅いデバイスは自分だけを遅くする

プローブは並列に発射され（`&` + `wait`）、1回あたりのタイムアウトは4秒です。眠り込んだデバイスが消費するのは自分の4秒だけで、他の20台を道連れにはしません。合計時間は全部の足し算ではなく、最も遅い1台にほぼ等しくなります。

このスクリプトを、3秒周期でポート使用状況を更新する監視スクリプト（後で出てくる update_ports）のサンプリングと意図的に**分けている**のも、そのためです。レイテンシのプローブがどれだけタイムアウトしても、オンライン / オフラインの判定を止めてはいけません。脈拍を測る看護師と血圧を測る看護師は別の人、というわけです。

### 現在：同じ手口を、gateway が自分でノックする

Rust 版の gateway は、それ自体がリバーストンネルの反対側の端なので、もう `127.0.0.1` のポートを経由する必要はありません。`Gateway::probe_latency`
（`src/backend-api/src/gateway/mod.rs`）は、各 forward に直接 forwarded-tcpip チャネルを開きます。`ssh -R` が外部からの接続を受けたときに開くのと同じものです。
デバイス上の ssh クライアントがそれを自分の sshd につなぎ、ここでも**1バイトだけ読み**、0.1 ms まで計時します。

- 並列（`join_all`）、プローブ1回のタイムアウトは4秒（`PROBE_TIMEOUT`）、15秒ごとに1ラウンド（`GATEWAY_PROBE_INTERVAL_SECS`）です。
- 脈拍と血圧が別の看護師なのは今も同じです。オンライン / オフラインは forward の登録 / 解放イベントで決まり、プローブがいくらタイムアウトしてもトンネルがオフラインになることはありません。
  ただし連続して失敗すると **degraded** になります（第5節の番外編2）。
- 前段に L4 proxy があっても、Docker が送信元アドレスを書き換えても、正確に測れます。バイトが通るのはトンネルの中であって、カーネルが見ているあの TCP ではないからです。

## 4. Redis：2つの世界の引き渡し窓口（Django 時代）

スクリプトは結果を `port rtt_ms` の複数行にまとめ、Redis に一括で上書きします。

```bash
cat "$TMPDIR"/* | redis-cli -x SET ss_probe_latency
```

バックエンド側には小さな落とし穴がありました。このキーは `redis-cli` が生で書いたもので、Django cache のキープレフィックスが**付いていません**。そのため `cache.get("ss_probe_latency")` は、正直に `None` を返すだけです。
そこでコードでは redis-py で直接つないで読んでいます（以前は毎ラウンド `redis-cli` のサブプロセスを起動していたので、そのコストも省けます）。

> 読めなければ `None` を返す、でかまいません。ただし「このラウンドのサンプルは使えない」と「レイテンシが0」は別物だと心得てください。両者を混同するシステムは、いつか夜中にあなたを叩き起こします。

**現在：** 引き渡し窓口はもうありません。プローブ結果は `StatusState::record_probes`（`monitor/mod.rs`）を通じて直接メモリに入り、測れなかったポート
は表に載りません（0 ではありません）。「使えない」と「0」の区別は残っていて、gateway が起動していないときは `StatusState::latency()` が `None` を返し、そのラウンドは配信されません。

## 5. update_ports --loop：常駐の配信役（Django 時代。現在は `monitor/runner.rs`）

> **現在：** `monitor::runner::run` は同じ配信役の Rust 版で、5秒ごとに1ラウンド動きます。以下の手順、スロットリング、2系統の配信はそのまま引き継いでいますが、
> 第1ステップだけは Redis から受け取る必要がなくなり、`StatusState` を直接読みます。

`update_ports` は5秒ごとに1ラウンド動く、常駐の Django 管理コマンドです（`--loop` モード。以前は5秒ごとに Django 全体をコールドスタートしていたので、CPU に定期的な不整脈のようなスパイクが出ていました）。

各ラウンドの手順は次のとおりです。
1. Redis から `ss_probe_latency` を読み、cache の `ports_latency` に書き込む。
2. レイテンシを配信する。しかも**「状態が変わっていなければ早期リターン」より前**に、意図的に置いています。
   > そうしないと、接続が安定したトンネル（状態がずっと変わらない）のレイテンシが最初の数字のまま固まり、博物館の展示品になってしまいます。

### スロットリング：心拍のたびにプレスリリースを出す必要はない

RTT は本来、数ミリ秒は揺れます。87、89、86、88……。毎ラウンド配信すると、
誰にも違いが分からない数字のために、全フロントエンドが5秒ごとに再レンダリングすることになります。そこで次のようにします。

- どれかのポートが **5ms 以上**変化した、またはポートが現れた / 消えた場合 → 配信する。
- そうでなければ黙っていますが、最大6ラウンドためたら強制的に1回配信します（keep-alive）。接続したばかりで前の便を逃したフロントエンドを気づかうためです。

### 配信は2系統

- **メインページ**：各ユーザーにレイテンシを送ります。payload には、**そのユーザーに権限のある**ポート（所有者と共有相手）だけを入れます。
  現在は通知 `UPDATE-TUNNEL-LATENCY {latency: {"<port>": rtt_ms}}` で、`/ws/notifications/` を通ります。
  > 他の人のトンネルのレイテンシは見えません。これはプライバシーであり、礼儀でもあります。
- **ターミナルページ**：単一トンネルのリアルタイム更新です。Django 時代は Web ターミナルのグループへ送っていました。現在は hub の `tunnel_update` →
  `/ws/tunnel_connection/{id}/` 上の `latency_update {tunnel_id, reverse_port, rtt_ms}` です（ターミナルページと作成ウィザードの両方がこれを購読します）。

### この節の番外編：キーが int だったせいでサイト全体が巻き添えに

payload の port は**文字列**のキーに変換する必要があります。channel layer は msgpack でシリアライズしており、新しいバージョンのデフォルトは `strict_map_key=True` です。int をマップのキーにすると、**アンパック側**で `ValueError` が爆発します。

さらにすごいことに、channels_redis の共有受信ループのせいで、この地雷は同じ worker 上の**どの** consumer でも爆発し、ターミナルを使っていた無関係なユーザーまで全員切断されます。

> `str(port)` ひとつの差が、「正常に動く」と「謎の集団切断事件」を分けます。

今は channel layer がなく（通知はプロセス内の hub を通り、JSON にシリアライズされます）、それでもキーは文字列のままです。フロントエンドと JSON が元からそれを期待しているからです。

### 番外編2：測れないことも、測れたうちに入る

Rust 版はもうひとつ計算します。forward は確かに残っているのに、バナーがいつまでも返ってこない。デバイスの sshd が止まった、ファイアウォールに遮られた、またはハングした場合です。
トンネルはオンラインに見えて、実際には何もつながりません。そこで `StatusState::record_probes` は、ラウンドごとに各 port の「連続失敗回数」を記録し（成功でゼロに戻る）、
`DEGRADED_AFTER`（2）回連続で失敗したら **degraded** とします（`monitor::health`：online / degraded / offline / never。Cloudflare Tunnel を参考にしています）。

- gateway は `degraded` / `recovered` イベントを書き込みます（そのトンネルの Logs ページで見られます）。
- runner は「状態が変わっていなければ早期リターン」より前に、degraded になったポートを比較し、変化があれば見える人に `UPDATE-TUNNEL-HEALTH {tunnel_id, name, port, health}` を送ります。
  状態イベントを購読している webhook にも渡します（それぞれ自分の遅延タイマーを持ちます）。
- 一覧の各項目は `health` を持ち、フロントエンドの `lib/tunnelHealth.liveHealth` がそれをリアルタイムの port 状態と合成します。琥珀色の点、オフラインのように見える開くボタン、
  degraded になったときの警告トーストが出ます。

1回の失敗はカウントしません。デバイスがたまたま忙しくて、4秒以内にバナーを返せないことはよくあるからです。

## 6. フロントエンド：数字に服を着せる

- **ホーム**（トンネル一覧）は、REST を1回呼び（`/api/reverse/server/dashboard`。1リクエストで `{tunnels, ports, latency}` を取得します。以前は3つの並列リクエストで、
  そのうちの1つが今も残る `/api/reverse/server/status/latency` でした）、`{port: rtt_ms}` を土台として受け取ります。以降はすべて `UPDATE-TUNNEL-LATENCY` で更新されます。
  サンプリングが使えないときは `latency` が `{}` になり、ホームに数字が出ないだけです。
- **`LatencyIndicator`**：携帯電話の電波表示風の4本バーです。60ms 未満は緑4本（優秀）、60〜150 は緑3本（良好）、150〜300 は琥珀2本（普通）、300 超は赤1本（不良。デバイスを月に置いていないか確認することをおすすめします）。測れないときは？ グレーのバーと `—` を出し、決して適当な 0ms は書きません。
- **`TerminalLatencyBadge`**：ターミナルページのタイトルバー（`TerminalHeader`）にある、2ホップのフロー経路です。
      `You ●──● Telepy ●──● Device`。線の上をデータの光の点が流れるアニメーションが走ります。You → Telepy はこのタブ自身の ping/pong、
      Telepy → Device は `/ws/tunnel_connection/{id}/` の `rtt_ms` から来ます。ホバーまたはタップで区間ごとの内訳が見られます。
- **経路図**：ターミナルページの info ダイアログ（`TerminalFlow`）では、「あなた ─ Telepy」と「Telepy ─ デバイス」の2本の線に同じ2つの往復時間を表示します。
  リモートデスクトップのストリーム統計（[`remote-desktop.ja.md`](./remote-desktop.ja.md)）も、monitor が測ったトンネルのレイテンシを区間のひとつ（`tunnel_ms`）として使います。
- **ヘルス状態**：一覧のステータスの点 / ラベルは、online（緑）、degraded（琥珀）、offline（グレー）、never（破線の輪）に分かれます。第5節の番外編2を参照してください。
- **レイアウトずれへのこだわり**：変化する数字はすべて、固定幅かつ `tabular-nums` のセルに入れています。
  `72ms` が `115ms` になっても、レイアウトはびくともしません。レイテンシが上がったせいで跳ね回るレイテンシのバッジほど、皮肉なものはありませんから。

## 7. まとめ：1バイトの履歴書

1. gateway は15秒ごとに、すべてのリバーストンネルへ「ノック」（forwarded-tcpip チャネル1本）を送り、ストップウォッチを押して、バナーの先頭1バイトが泳いで戻ってくるのを待ちます。
2. 結果はそのままメモリ（`StatusState`）に入ります。2回連続で戻ってこなければ degraded として記録します。
3. 常駐の `monitor/runner.rs` が5秒ごとにそれを受け取り、スロットリングしたうえで、プロセス内の hub を通じて権限のある人に配ります（キーはやはり文字列です）。
4. フロントエンドはそれを電波バーとフロー経路として描き、ブラウザからサーバーまでの区間は自前の ping/pong（バイナリ！）で別に測ります。
5. 2つの区間を足すと ≈ あなたとデバイスの間の、現実世界での距離になります。

（Django 時代のバージョン：ステップ1は SSH コンテナの Bash、ステップ2は Redis の `ss_probe_latency`、ステップ3は `update_ports` + channel layer でした。）

設計哲学をひとことで言うと、**人づてに聞いた話（カーネル、proxy）は信じず、自分で全行程を走り切ったバイトだけを信じる。**
