# あの「ms」はどこから来るのか？

<p align="center"><a href="./latency-deep-dive.md">English</a> | <a href="./latency-deep-dive.zh-TW.md">繁體中文</a> | <b>日本語</b></p>

ターミナルページのタイトルバーには、小さなレイテンシのバッジがあります。

```
You ●──23ms──● Telepy ●──87ms──● Device   Σ 110ms
```

見た目は単純です。このページでは、それぞれの数字がどこから来て、どのくらいの頻度で測られ、本物の値にするために Telepy が何をしているのかを説明します。

## 2つの区間を別々に測る

![ターミナルの説明図に区間ごとの往復時間が表示されます](images/ja/terminal-flow.png)

全行程を一度に測る方法はありません。ブラウザはデバイスに届かず、デバイスはブラウザの存在を知らないからです。そこで Telepy は区間ごとに測り、最後に合計します（それが Σ です）。

| 区間 | 何を測るか | 誰が測るか | 頻度 |
|---|---|---|---|
| あなた → Telepy | ブラウザとサーバーの間の WebSocket の往復時間 | ブラウザ上のターミナルページ | 5秒ごと |
| Telepy → デバイス | トンネルを通ってデバイスの SSH サーバーまで行って帰る時間 | バックエンド内蔵の SSH gateway | 15秒ごと |

どちらも片道ではなく往復時間（RTT）です。2つを足すと、あなたとデバイスの間の実際の往復にかなり近い値になります。

## 区間1：ブラウザから Telepy まで

ターミナルページは5秒ごとに、WebSocket で次の1行を送ります。

```json
{ "action": "ping" }
```

バックエンドは `pong` を返しますが、これはテキストではなくバイナリフレームです。ページはかかった時間を計算し、バッジを更新します。

なぜバイナリなのでしょうか。ターミナルページは、テキストフレームをすべてそのまま画面に書き込みます。シェルの出力がテキストフレームで届くからです。pong をテキストで返すと、vim の中に5秒ごとに `pong` と現れます。やけに時間に正確な幽霊のようです。バイナリフレームなら、ページは「出力ではなく制御メッセージだ」と分かるので、画面には何も影響しません。

ターミナルの接続で届くほかの制御メッセージも、同じ決まりに従います。切断後もシェルを残しておくためのメッセージ、コマンドルールの通知、「誰が見ているか」の一覧は、どれもバイナリの JSON です。ページはバイナリフレームを受け取ると、まず中身がちょうど `pong` かどうかを確かめ、違えば JSON として読みます。

ほかに知っておくとよいことが2つあります。

- ほかの WebSocket（通知、単一トンネルの状態、ファイルマネージャー）は、ping にテキストの `{"type":"pong"}` で答えます。守るべきターミナル画面がないからです。
- サーバーは、ターミナル、ファイルマネージャー、リモートブラウザの接続にも20秒ごとに WebSocket Ping を送り、40秒応答がなければ切断します。挨拶なしに消えたブラウザを見つけるための仕組みで、生存確認であってレイテンシの測定ではありません。

## 区間2：Telepy からデバイスまで

### カーネルに聞けばよいのでは？

いちばん手軽なのはカーネルに聞くことです。`ss -ti` は TCP 接続ごとの RTT を最初から報告してくれますし、タダです。最初はそう考えていました。

困るのは、サーバーの手前に docker-proxy や L4 ロードバランサーがあるときです。デバイスの TCP 接続はその proxy で終端され、しかも proxy は同じマシン上にいます。そのためカーネルは、自信満々に RTT はほぼ 0 ms だと報告します。

実際のデバイスは、数百キロ離れたデータセンターで3段の NAT 越しに手を振っているかもしれません。カーネルの数字は正確ですが、測っている距離が違うのです。

### ノックして、1バイトだけ読む

そこで Telepy は、トンネルそのものを通して測ります。

1. gateway が、デバイスのリバーストンネルにチャネルを開きます。転送ポートに誰かが接続したとき、`ssh -R` が開くのと同じ種類のチャネルです。
2. デバイス上の ssh クライアントが、そのチャネルをデバイス自身の SSH サーバーにつなぎます。
3. gateway はストップウォッチを押し、1バイトだけ読みます。SSH サーバーのバナーの先頭1バイト（`SSH-2.0-...` の `S`）です。

この1バイトは、トンネルを通って行って帰ってくるしかありません。だから測れるのは本物のネットワーク往復です。proxy はカーネルをだませても、デバイスのバナーまでは作り出せません。物理法則に袖の下は通じないのです。

同じ理由で、手前に L4 proxy があっても、Docker が送信元アドレスを書き換えても、値は正確です。バイトが通るのはトンネルの中で、カーネルが見ている接続ではないからです。

細かい点は次のとおりです。

- 15秒ごとに1ラウンドです。間隔はバックエンドの上級者向け変数 `GATEWAY_PROBE_INTERVAL_SECS` で変えられます。
- すべてのトンネルを並列に測り、1回あたりのタイムアウトは4秒です。居眠りしているデバイスが使うのは自分の4秒だけで、ほかのデバイスを待たせません。
- ストップウォッチの精度は 0.1 ms です。

プローブの役目は測ることだけです。トンネルがオンラインかオフラインかは、トンネルそのもの、つまりデバイスが forward を登録したか解放したかで決まります。プローブが何度タイムアウトしても、トンネルがオフラインになることはありません。ただし、失敗が続くと変わることが1つあります。次の節で説明します。

## ノックに誰も答えないとき：低下

forward は残っているのに、バナーがいつまでも返ってこないことがあります。デバイスの sshd が止まった、ファイアウォールに遮られた、またはハングした場合です。トンネルはオンラインに見えるのに、実際には何もつながりません。

そこで Telepy は、トンネルごとにプローブの失敗回数を数えます。2回続けて失敗するとトンネルは「低下」になり、1回成功すればカウントは0に戻ります。1回の失敗は数えません。忙しいデバイスが4秒以内にバナーを返せないことは、ときどきあるからです。

トンネル一覧には4つの状態が表示されます。

| 状態 | 表示 | 意味 |
|---|---|---|
| オンライン | 緑の点 | トンネルがつながっていて、デバイスの sshd もトンネル越しに応答している |
| 低下 | 琥珀色の点 | トンネルはつながっているが、sshd が2回続けてプローブに応答していない |
| オフライン | グレーの点 | 以前は接続していたが、今はトンネルがない |
| 未接続 | 破線の輪 | 接続の記録がない |

トンネルが低下したとき、または回復したとき：

- そのトンネルのログページに「SSH 応答なし」または「SSH 復旧」のイベントが記録されます。
- そのトンネルが見えるすべての人に通知が届きます。一覧には琥珀色の点が出て、トンネルを開くボタンはオフラインのような見た目になります。低下したときは警告のトーストも出ます。
- 状態イベントを購読している webhook にも届きます。送信までの待ち時間は webhook ごとの設定に従います。

「測れなかった」が0と表示されることはありません。プローブに失敗したトンネルには数字がなく、バッジはグレーのバーと `—` を表示します。それらしい 0 ms をでっち上げることはしません。gateway がそもそも動いていないときは、そのラウンドのレイテンシは送られません。

## 数字が画面に届くまで

バックエンドでは、5秒ごとに1ラウンド動くループがあります。最新のプローブ結果を受け取り、それを見てよいブラウザへ送ります。

- **意味のあるときだけ送る**：RTT は常に数ミリ秒揺れています（87、89、86、88…）。そのたびに全ページを5秒ごとに描き直すのは無駄なので、どれかのトンネルが 5 ms 以上変化したとき、またはトンネルが現れた・消えたときだけ送ります。それ以外は黙っていますが、黙るのは最大6ラウンドまでで、そこで必ず1回送ります。接続したばかりのページを長く待たせないためです。
- **ほかに変化がなくても送る**：レイテンシは、ループの「何も変わっていなければここで終わり」というチェックより前に送ります。そうしないと、とても安定したトンネルは、最初に測った数字をずっと表示し続けることになります。
- **オンライン / オフラインはデバウンスする**：トンネルの状態が2ラウンド続けて変わったときだけ、変化として知らせます。
- **自分のトンネルだけ**：レイテンシが届くのは、自分が所有しているトンネルと、自分に共有されているトンネルの分だけです。ほかの人のトンネルのレイテンシは見えません。

数字は2つの経路で届きます。

- トンネル一覧には、通知用の接続 `/ws/notifications/` で届きます。
- ターミナルページと「トンネルを作成」ウィザードは、そのトンネル専用の状態接続 `/ws/tunnel_connection/{id}/` を購読し、そのトンネルの数字をリアルタイムで受け取ります。

## 数字の見せ方

トンネル一覧は、まず `GET /api/reverse/server/dashboard` を1回呼びます。トンネル、ポート、レイテンシを1リクエストで返すエンドポイントです。その後はリアルタイムの更新に従います。サンプルがないときは `latency` が `{}` になり、一覧に数字が出ないだけです。以前からある `/api/reverse/server/status/latency` エンドポイントも残っていて、`{"<port>": rtt_ms}` を返します。

レイテンシは、携帯電話の電波表示のような4本のバーで表示します。

| 往復時間 | バー | ラベル |
|---|---|---|
| 60 ms 未満 | 緑4本 | 非常に良い |
| 60〜150 ms | 緑3本 | 良好 |
| 150〜300 ms | 琥珀色2本 | 普通 |
| 300 ms 超 | 赤1本 | 悪い（デバイスが月面に設置されていないか、念のため確認をおすすめします） |
| 測れなかった | グレーのバーと `—` | — |

ターミナルページでは：

- タイトルバーのバッジは、2つの区間を `You ●──● Telepy ●──● Device` という経路として描き、線の上を光の点が流れます。最初の区間はこのタブ自身の ping/pong、2つ目は状態接続から届くトンネルの数字です。ホバーまたはタップすると、区間ごとの内訳と合計が見られます。
- 説明ダイアログ「ターミナルのしくみ」でも、「あなた ─ Telepy」と「Telepy ─ デバイス」の線に同じ2つの往復時間を表示します（このページの先頭の図です）。

リモートデスクトップのストリーム統計も、トンネルのレイテンシを区間の1つとして使っています。[リモートデスクトップ](./remote-desktop.ja.md)を参照してください。

変化する数字はすべて、固定幅で等幅数字のセルに入れています。`72ms` が `115ms` になっても、レイアウトは動きません。

## 全行程を5つのステップで

1. gateway は15秒ごとに、すべてのリバーストンネルへノックを送り、デバイスの SSH バナーの先頭1バイトが戻るまでの時間を測ります。
2. 結果はそのままバックエンドのメモリに入ります。2回続けてノックに答えがなければ、トンネルは低下になります。
3. バックエンドのループが5秒ごとに結果を受け取り、つまらない変化は見送って、残りを見る権限のある人に送ります。
4. ブラウザは電波バーと経路のバッジを描き、サーバーまでの区間は自分の ping/pong（バイナリ！）で別に測ります。
5. 2つの区間を足すと、あなたとデバイスの間の現実の距離にかなり近い値になります。

設計の考え方をひとことで言えば、人づての話（カーネル、proxy）は信じず、自分で全行程を走り切ったバイトだけを信じる、です。

## 内部の話

ここから先の2つは、ソースを読む人や歴史に興味がある人向けです。どちらも Telepy の動作には関係しません。

<details>
<summary>コード上の名前（コントリビューター向け）</summary>

- プローブは `Gateway::probe_latency` です。タイムアウトは `PROBE_TIMEOUT` の4秒、間隔は `GATEWAY_PROBE_INTERVAL_SECS`（デフォルト15）から取ります。結果は `StatusState::record_probes` に入り、ポートごとの RTT と連続失敗回数が記録されます。
- 測れなかったポートは、レイテンシの表に載りません（0 になるのではありません）。gateway が動いていないときは `StatusState::latency()` が `None` を返し、そのラウンドは配信されません。
- 配信ループは、バックエンドのポート監視です（5秒ごとに1ラウンド）。定数は `FLAP_THRESHOLD` 2（オンライン / オフラインのデバウンス）、5 ms の変化しきい値、6ラウンドの keep-alive、`DEGRADED_AFTER` 2 です。
- メッセージは、`/ws/notifications/` 上の `UPDATE-TUNNEL-LATENCY {latency: {"<port>": rtt_ms}}`、`/ws/tunnel_connection/{id}/` 上の `latency_update {tunnel_id, reverse_port, rtt_ms}`、ヘルスの変化を伝える `UPDATE-TUNNEL-HEALTH {tunnel_id, name, port, health}` です。
- ヘルスは `online` / `degraded` / `offline` / `never` の4つで、Cloudflare Tunnel を参考にしています。gateway は `degraded` / `recovered` イベントを書き込みます。一覧の各項目は `health` を持ち、フロントエンドがそれをリアルタイムのポート状態と合わせます。
- フロントエンドでは、タイトルバーのバッジ、電波バー、説明図がそれぞれ `TerminalLatencyBadge`、`LatencyIndicator`、`TerminalFlow` です。リモートデスクトップのストリーム統計では、トンネルの区間を `tunnel_ms` と呼びます。
- これらの payload では、ポートは常に文字列のキーです。理由は下の int キーの話を参照してください。

<details>
<summary>Django 時代のやり方</summary>

2026年10月にバックエンドを Rust で書き直す前は、同じ考え方をもっと多くの部品で実現していました。SSH コンテナの中の Bash スクリプト、間に入る Redis、配信を担当する Django のコマンドです。測り方そのものは同じでした。

**プローブ**：スクリプトは `ss -tln` で、sshd が `127.0.0.1` に bind しているリバーストンネルのポートを探しました。各ポートに Bash の組み込み機能 `/dev/tcp` で TCP 接続を開き（nc も ICMP も不要です）、`$EPOCHREALTIME`（マイクロ秒精度）で時刻を取って、1バイトだけ読みます。

```bash
s=$EPOCHREALTIME
exec 3<>/dev/tcp/127.0.0.1/$port
IFS= read -r -N1 _b <&3        # 対象デバイスの sshd バナーの先頭1バイトを待つ
e=$EPOCHREALTIME
```

プローブは並列に実行され（`&` + `wait`）、1回あたりのタイムアウトは4秒です。合計時間は全部の足し算ではなく、いちばん遅いデバイスとほぼ同じでした。このスクリプトは、3秒ごとにポートの使用状況を記録するサンプリングとは意図的に分けてあり、プローブがどれだけ遅くてもオンライン / オフラインの判定は止まりませんでした。

**引き渡し**：スクリプトは結果を `port rtt_ms` の複数行にまとめ、Redis に一括で上書きしました。

```bash
cat "$TMPDIR"/* | redis-cli -x SET ss_probe_latency
```

このキーは Django cache のキープレフィックスなしで直接書かれていたので、`cache.get("ss_probe_latency")` は常に `None` を返すだけでした。そこでバックエンドは redis-py で直接つないで読むようにし、ついでに毎ラウンド `redis-cli` のサブプロセスを起動するコストもなくしました。

**配信役**：`update_ports --loop` という、5秒ごとに1ラウンド動く常駐の Django 管理コマンドです。さらに前の版では、5秒ごとに Django 全体をコールドスタートしていました。上で説明した規則（レイテンシを「変化なしなら終わり」より前に送る、5 ms のしきい値、6ラウンドの keep-alive、2つの経路）は、ここからそのまま引き継いだものです。

**int キー事件**：channel layer は msgpack でシリアライズしており、新しい msgpack のデフォルトは `strict_map_key=True` です。マップのキーが整数だと、アンパック側で `ValueError` が発生します。channels_redis は worker ごとに受信ループを共有しているため、整数のポートをキーにしたレイテンシの payload が1つあるだけで、同じ worker 上のすべての consumer が巻き添えになりました。ターミナルを使っている最中の人も含めてです。`str(port)` ひとつで直りました。

今は channel layer がありません（通知はプロセス内の hub を通り、JSON にシリアライズされます）。それでもキーは文字列のままです。フロントエンドも JSON も、もともとそれを前提にしているからです。

</details>
