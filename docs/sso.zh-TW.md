# 單一登入（OIDC）

<p align="center"><a href="./sso.md">English</a> | <b>繁體中文</b> | <a href="./sso.ja.md">日本語</a></p>

Telepy 可以讓大家用公司或組織的身分提供者登入，不必另外記一組 Telepy 密碼。Okta、Microsoft Entra ID、Google Workspace、Keycloak、Authentik、Dex，以及其他支援 authorization code + PKCE 的 OpenID Connect 提供者都能用。每新增一個身分提供者，登入頁就多一顆按鈕，例如「使用 Okta 登入」。

密碼照樣能用，passkey、Google 登入和 Telepy 自己的兩步驟驗證也都還在。單一登入是多一種進來的方式，不是取代其他方式，也不會強迫任何人用。

## 需要什麼

- Telepy 的管理員帳號。
- 能在身分提供者那邊登記應用程式的權限。
- `PUBLIC_URL` 設成 Telepy 的網址，例如 `https://telepy.example.com`（網站設定 → 伺服器，或 `.env`）。沒設的話，回呼網址會跟著你剛好用來開網頁的網址走，哪天網址一換，身分提供者就會拒絕。

## 設定身分提供者

### 在身分提供者那邊

1. 登記一個新的 **web 應用程式**。有的身分提供者叫它 OIDC client、應用程式註冊或 confidential client。
2. Redirect URI 填 Telepy 為這個身分提供者顯示的回呼網址，長得像 `https://telepy.example.com/api/auth/oidc/okta/callback`，`/callback` 前面那段是它在 Telepy 的代號。
3. 允許 `openid`、`email`、`profile` 這三個 scope。
4. 抄下 issuer 網址、client ID 和 client secret。

沒有 secret 的公開 client 也可以。這時 Telepy 只靠 PKCE，身分提供者會接受，資安審查則會很樂意拿來討論。

### 在 Telepy 這邊

1. 打開**網站設定 → 登入 → 單一登入（OIDC）**，按**新增身分提供者**。
2. 填上按鈕要顯示的名字。
3. 貼上 issuer 網址，按**檢查**。Telepy 會讀身分提供者的 discovery 文件和簽章金鑰，告訴你找到了什麼，或為什麼這個網址不能用。
4. 如果還沒登記，把對話框裡的回呼網址登記到身分提供者那邊。
5. 填 client ID 和 secret，決定帳號規則（下一節），存檔。
6. 按**試登入**。你在身分提供者那邊登入一次，Telepy 會顯示收到的 claim，以及它會怎麼處理：登入哪個帳號、建立新帳號，或拒絕。試登入不會讓任何人登入，也不會建立帳號。
7. 結果沒問題就把它打開，登入頁就會出現它的按鈕。

小提醒：新的身分提供者可以先關著存起來，試過再打開。關著的身分提供者也能試登入。

### 各家的小地方

| 身分提供者 | Issuer 網址 | 值得知道 |
| --- | --- | --- |
| Okta | `https://<你的組織>.okta.com` 或 `https://<你的組織>.okta.com/oauth2/default` | 用應用程式登入政策所屬的那一個 |
| Microsoft Entra ID | `https://login.microsoftonline.com/<租戶 id>/v2.0` | 常常沒有 `email`，使用者名稱請選 **preferred_username**。Entra 不送 `email_verified`，所以「依 email 連結」永遠不會生效 |
| Google Workspace | `https://accounts.google.com` | Google 會放行**所有** Google 帳號，一定要填**允許的 email 網域** |
| Keycloak | `https://<主機>/realms/<realm>` | |
| Authentik | `https://<主機>/application/o/<應用程式代號>/` | 結尾的斜線照 Authentik 顯示的保留 |
| Dex | Dex 設定裡的 `issuer` | |

## 誰進得來

有人用身分提供者登入時，Telepy 依這個順序決定是哪個帳號：

1. **連結過**：跟上次同一個 Telepy 帳號。Telepy 用身分提供者固定的使用者 ID（`sub`）找，不是用 email，因為 email 會變。
2. **依已驗證的 email 連結**（預設關閉）：email 相同的既有帳號，而且身分提供者要說這個 email 驗證過。只對你們組織自己管的身分提供者打開。誰在那邊握有某個 email，就能拿到用那個 email 的 Telepy 帳號，管理員也一樣。
3. **第一次登入時建立帳號**（預設開啟）：用 email 的 `@` 前面，或 `preferred_username` 取名建一個新帳號。名字已經有人用了，Telepy 會拒絕並說明，不會自己亂猜。
4. 其他情況一律不放行，由本人把既有帳號連結起來（下一節）。

**允許的 email 網域**（預設空白）套用在透過這個身分提供者的每一次登入，既有帳號也一樣。身分提供者只放自己人進來時留空就好；它會放全世界進來時（Google、多租戶的 Entra 應用程式）就要填。

身分提供者的「建立帳號」開關跟上面的「註冊」設定無關，「註冊」管的是密碼註冊和 Google 登入。

帳號決定之後，規則跟平常一樣：停用的帳號進不來，有兩步驟驗證的帳號照樣要過 passkey 或驗證碼。身分提供者自己的 MFA 發生在這之前，在身分提供者那邊。沒錯，這可能代表要過兩次 MFA；Telepy 寧可問兩次，也不要一次都沒問。

## 群組與角色

身分提供者本來就知道誰在哪個團隊。Telepy 可以直接用這些群組，設定在身分提供者的**群組與角色**頁：

- **只有這些群組能登入**：不在任何一個列出群組裡的人，按這個身分提供者的按鈕會被擋下。空白 = 身分提供者放行的人都可以。
- **群組 → Telepy 角色**：身分提供者的群組可以讓人成為**管理員**，或把人放進 Telepy 的**組織群組**（「使用者與權限 → 組織群組」裡的那些，它們的功能規則決定誰能用終端機、檔案、遠端桌面等等）。好幾條規則可以指向同一個角色；一個人會拿到他所在每個群組的角色。

每次有人用那個身分提供者登入，規則就套用一次，而且有幾條自己的規矩：

- 群組名稱要完全相同，大小寫也算。
- Telepy 只會拿掉**這個身分提供者給過的**。管理員手動給的成員資格或管理員身分，就算那個人在身分提供者那邊離開了對應的群組，也照樣留著。
- ID token 完全沒有群組 claim 時，要看這個人：身分提供者之前給過他東西，表示 claim 有設好，沒送就代表他現在不在任何群組（Keycloak 和 Entra ID 在使用者沒有群組時會整個省略這個 claim），給過的會收回；從沒給過他東西就什麼都不改，因為 Telepy 分不出「不在任何群組」和「沒設定送出群組」，寧可不猜。claim 在但是空的，一律代表「不在任何群組」。
- 最後一位啟用中的管理員絕不會被降級，網站不會變成沒人管。
- 角色套用之後，那個人自己的 Telepy 兩步驟驗證照樣要過。

在「功能權限」頁，來自身分提供者的成員和管理員會標上大樓圖示。在那裡拿掉只維持到他下次登入，所以請到身分提供者那邊改群組。**試登入**會先列出身分提供者送來的群組和會改什麼，真的改之前就看得到。

### 各家怎麼送群組

| 身分提供者 | 群組 claim | 要設定什麼 |
| --- | --- | --- |
| Okta | `groups` | 在應用程式（或授權伺服器）加一個 groups claim，用「以 telepy- 開頭」之類的篩選 |
| Microsoft Entra ID | `groups` 或 `roles` | `groups` 送的是物件 ID 不是名字；應用程式角色（`roles`）通常比較好讀 |
| Google Workspace | | Google 的 ID token 沒有群組，請改用允許的 email 網域 |
| Keycloak | `groups` 或 `realm_access.roles` | 加一個 Group Membership mapper（claim 名稱 `groups`，關掉 full path），或用 realm 角色 |
| Authentik | `groups` | 跟著 `profile` scope 一起送 |
| Dex | `groups` | 在 scope 加上 `groups` |

## 把通道分享給群組

群組也可以開放通道。在通道的分享視窗，**群組**分頁可以把它分享給一個群組，設定權限、成員可以登入的帳號和期限（可不設），跟分享給一個人一樣。之後群組裡每個人都會拿到這條通道（各自一筆分享），而且跟著群組走：加入的人拿到、離開的人失去，開著的連線也會結束。單一登入規則和 SCIM 會讓組織群組跟身分提供者同步，所以最後是身分提供者的群組決定誰能用哪些通道。

群組有兩種：

- **組織群組**由管理員、單一登入規則或 SCIM 維護，帶著功能規則。管理員要在「使用者與權限 → 組織群組」打開**可以分享**，它才會出現在分享視窗；所以為了功能規則建的群組（例如不能用終端機的外包）不會被大家看到。關掉之後，分享給這個群組的通道全部結束。關掉之前，以及改成員、刪群組之前，頁面會先列出誰會多了或少了哪些通道。
- **個人群組**是能分享通道的人在**群組**分頁裡自己建的。只有建立的人看得到，也從不改變任何人能用的功能。分享給它的通道，只在建立的人還擁有那條通道，或經由自己的分享或組織群組在上面有 Admin 時才算數；不然那筆分享會暫停，成員經由它拿不到東西，直到情況改變。所以失去 Admin 之後，你分享出去的就真的停了。

- **直接分享給某人時，以他自己的分享為準。** 群組不會改它。按**單獨設定這個人**，可以把經由群組的分享改成他自己的。
- **好幾個群組會加起來。** 同時在兩個被分享的群組裡的人，取比較高的權限、兩邊所有的帳號，以及比較晚的期限。
- **要改就改群組。** 經由群組的分享不能一個人一個人撤銷、修改或自己離開：把人移出群組，或修改、停止群組的分享。存取申請照樣可以疊加在上面。
- 跟分享給個人一樣，只有通道主人和它的 Admin 能分享給群組。每次變更都會記在通道的**紀錄**裡。

## 連結既有的帳號

每個人都可以在**偏好設定 → 安全性 → 單一登入**連結自己的帳號：

1. 按身分提供者旁邊的**連結**。帳號有兩步驟驗證的話，先確認是你本人。
2. 到身分提供者那邊登入，回來會看到一頁說已經連好了。

之後按那個身分提供者的按鈕就會登入這個帳號。**解除連結**同樣要先確認。Telepy 不會讓你拿掉最後一個登入方式：要先留下密碼、passkey 或另一個連結。

## 命令列

`telepy login` 是透過瀏覽器登入。瀏覽器還沒登入 Telepy 時，它的登入頁一樣有單一登入的按鈕，所以 CLI 不用額外設定就能用單一登入。

## 登出

預設登出 Telepy 只結束 Telepy 的登入；身分提供者那邊的登入還在，所以下次按它的按鈕可能直接就進來了。要兩邊一起登出，在身分提供者的設定打開**登出 Telepy 時也登出身分提供者**，並把它顯示的**登出後回來的網址**（`https://<telepy>/login`）登記到身分提供者那邊：Okta 叫 sign-out redirect URI，Keycloak 叫 valid post logout redirect URI，Entra 是應用程式的 redirect URI。

之後有人按登出，Telepy 會把瀏覽器帶到身分提供者的登出頁，用這次登入的 ID token 當提示，身分提供者再把它送回 Telepy 的登入頁。只有本人自己按登出時才會這樣：被管理員登出、從其他裝置登出或登入過期，都不會把人帶去身分提供者。沒有公開登出端點的身分提供者（例如 Google）只能登出 Telepy；按**檢查**就看得到你的有沒有。

## 身分提供者自動建立帳號（SCIM）

沒有 SCIM 時，單一登入是在某人第一次登入時才建立帳號。有了 SCIM，身分提供者會先把帳號管好：建立帳號、更新名字和 email、有人離開就停用，也會同步群組。Okta 和 Microsoft Entra ID 都支援。

要打開它，在**網站設定 → 登入 → 單一登入**打開那個身分提供者，到**自動建立帳號（SCIM）**分頁按**建立權杖**。權杖要馬上複製：Telepy 只留它的雜湊，之後不會再顯示。接著把基底網址 `https://<telepy>/api/scim/v2` 和權杖交給身分提供者：

| 身分提供者 | 在哪裡 | 基底網址填在 | 權杖填在 |
| --- | --- | --- | --- |
| Okta | 你的 App → General → Provisioning 選 SCIM，再到 Provisioning → Integration | SCIM connector base URL（unique identifier field 填 `userName`；勾 push new users、profile updates 和 groups） | Authentication mode 選 HTTP Header |
| Microsoft Entra ID | 企業應用程式 → 佈建 → 自動 | 租用戶 URL | 祕密權杖 |

身分提供者可以做的事：

- **建立帳號。** 使用者名稱取 `userName` 的 `@` 前面那段，整理方式跟單一登入的使用者名稱一樣。已經有同名的帳號時不會被接管：身分提供者會收到衝突，由你決定怎麼處理。
- **修改帳號。** 名字和 email 跟著身分提供者。
- **停用帳號。** `active: false` 跟在這裡停用帳號一樣：網頁登入和進行中的工作階段都會結束，MCP 代理的工作階段會關掉，Telepy 裝過的金鑰也會從裝置拿掉。重新啟用就能再進來。最後一位啟用中的管理員不會被停用。
- **刪除帳號。** 刪除只會停用帳號，不會真的刪掉，所以錄影、紀錄和通道都留著。之後身分提供者再建立同一個人，會拿回同一個帳號。
- **推送群組。** 每個群組會變成一個 Telepy 組織群組（就是**功能權限**用的那種），成員照身分提供者送來的。跟其他新的組織群組一樣，要等管理員打開才能拿來分享。不是它建立的人不會被移出這些群組；名字跟現有 Telepy 群組一樣的會被拒絕；身分提供者刪掉的群組，這裡也會刪掉。

身分提供者建立的人第一次用單一登入時，Telepy 會把這次登入連到他的帳號（email 或使用者名稱相同），不管有沒有打開「用已驗證的 email 連結」。

只有確認過本人的管理員能建立權杖。**換一個權杖**會讓舊的立刻失效；**關掉**會停止自動建立帳號，但它建好的帳號和群組都會留著。這個權杖只能用在 `/api/scim/v2`，其他地方都不行。使用者清單會標出哪些帳號由身分提供者管理；你在這裡對它們做的修改，可能會被身分提供者下一次同步改回去。每次帳號和群組的變更都會出現在管理區的**稽核日誌**。

## Telepy 會檢查什麼

- **每次登入都綁在開始登入的那個瀏覽器。** 一開始 Telepy 會給瀏覽器一個 HttpOnly cookie。回呼網址如果在別的瀏覽器打開（例如別人傳給你的），誰都不會因此登入。
- **每個身分提供者有自己的回呼網址**，給這一家的回應不能拿去冒充另一家。
- **ID token** 必須用身分提供者公開的金鑰簽章（RSA、ECDSA 或 EdDSA；沒簽章和 HMAC 的 token 一律不收），issuer、audience、期限和這次登入的 nonce 都要對。
- **每樣東西都只能用一次。** state、code 和最後給瀏覽器的票券都只能用一次，而且幾分鐘內就失效。
- Client secret 用 `SECRET_KEY` 加密存放，存檔後就不會再顯示。

身分提供者的每次變更、每次連結或解除連結，都會出現在管理區的**稽核日誌**。登入會以「單一登入」出現在每個人的登入紀錄裡。

## 不成功的時候

| 頁面上寫 | 通常是 |
| --- | --- |
| 還沒有 Telepy 帳號連到這個登入 | 沒有開「建立帳號」，這個人也還沒連結。請他用其他方式登入再連結，或把建立帳號打開 |
| 已經有同名的 Telepy 帳號 | 那個使用者名稱有人用了。請他用那個帳號登入，再連結身分提供者 |
| 這個 email 網域的帳號不能在這裡登入 | Email 不在**允許的 email 網域**裡 |
| 請在開始登入的同一個瀏覽器完成登入 | Cookie 不見了：換了瀏覽器、無痕視窗關掉了，或這個網站的 cookie 被擋 |
| 單一登入沒有成功 | 最常見是 client secret、redirect URI 或時鐘。後端紀錄會寫是哪一個（`[OIDC]` 開頭的那幾行） |
| 身分提供者拒絕了這次登入 | 身分提供者那邊給 Telepy 的設定：redirect URI、允許的 scope，或這個人沒被指派到這個應用程式 |
| 這個登入方式只讓特定群組進來，但身分提供者沒有送來你的任何群組 | 有設定**只有這些群組能登入**，但 ID token 沒有群組 claim。通常是這個人不在任何群組（Keycloak 和 Entra ID 這時會省略 claim）；不然就檢查 claim 名稱，或身分提供者那邊的群組設定 |
| 你在身分提供者的群組不能在這裡登入 | 這個人不在任何一個列出的群組裡 |

其他狀況先跑一次**試登入**，它會把身分提供者送來的東西原原本本列出來。
