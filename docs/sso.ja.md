# シングルサインオン（OIDC）

<p align="center"><a href="./sso.md">English</a> | <a href="./sso.zh-TW.md">繁體中文</a> | <b>日本語</b></p>

Telepy では、Telepy のパスワードの代わりに組織の ID プロバイダーでサインインできます。Okta、Microsoft Entra ID、Google Workspace、Keycloak、Authentik、Dex のほか、認可コードフローと PKCE に対応した OpenID Connect プロバイダーなら使えます。プロバイダーを追加するたびに、サインインページに「Okta で続行」のようなボタンが 1 つ増えます。

パスワードはそのまま使えます。パスキー、Google サインイン、Telepy 自身の 2 段階認証も残ります。シングルサインオンは入り口が 1 つ増えるだけで、ほかの方法を置き換えるものではなく、誰かに使用を強制することもありません。

## 必要なもの

- Telepy の管理者アカウント。
- ID プロバイダーでアプリケーションを登録できる権限。
- Telepy のアドレスを設定した `PUBLIC_URL`（例：`https://telepy.example.com`。サイト設定 → サーバー、または `.env`）。未設定だとコールバックのアドレスが今アクセスしているアドレスに合わせて変わり、アドレスが変わった日にプロバイダーに拒否されます。

## プロバイダーの設定

### プロバイダー側

1. 新しい **Web アプリケーション**を登録します。OIDC クライアント、アプリの登録、コンフィデンシャルクライアントなどと呼ばれることもあります。
2. リダイレクト URI には、Telepy がこのプロバイダー用に表示するコールバックのアドレスを入れます。`https://telepy.example.com/api/auth/oidc/okta/callback` のような形で、`/callback` の直前が Telepy でのスラッグです。
3. スコープ `openid`、`email`、`profile` を許可します。
4. issuer URL、クライアント ID、クライアントシークレットを控えます。

シークレットのないパブリッククライアントでも動きます。その場合 Telepy は PKCE だけに頼ります。プロバイダーは受け入れてくれますが、セキュリティレビューでは話題にされがちです。

### Telepy 側

1. **サイト設定 → サインイン → シングルサインオン（OIDC）**を開き、**プロバイダーを追加**を選びます。
2. ボタンに表示する名前を入れます。
3. issuer URL を貼り付けて**確認**を押します。Telepy がプロバイダーの discovery ドキュメントと署名鍵を読み、見つかった内容か、そのアドレスが使えない理由を表示します。
4. まだなら、ダイアログに表示されたコールバックのアドレスをプロバイダーに登録します。
5. クライアント ID とシークレットを入れ、アカウントのルール（次の節）を決めて保存します。
6. **テストサインイン**を押します。プロバイダーで一度サインインすると、Telepy が受け取ったクレームと、それをどう扱うか（どのアカウントにサインインするか、作成するか、拒否するか）を表示します。テストで誰かがサインインしたりアカウントが作られたりはしません。
7. 結果に問題がなければプロバイダーをオンにします。サインインページにボタンが出ます。

ヒント：新しいプロバイダーはオフのまま保存してテストし、それからオンにしましょう。オフのプロバイダーでもテストできます。

### プロバイダーごとの注意

| プロバイダー | Issuer URL | 知っておくとよいこと |
| --- | --- | --- |
| Okta | `https://<組織>.okta.com` または `https://<組織>.okta.com/oauth2/default` | アプリのサインインポリシーが属する方を使います |
| Microsoft Entra ID | `https://login.microsoftonline.com/<テナント ID>/v2.0` | `email` がないことが多いので、ユーザー名は **preferred_username** を選びます。Entra は `email_verified` を送らないため、メールでの連携は適用されません |
| Google Workspace | `https://accounts.google.com` | Google は**すべての** Google アカウントを通します。**許可するメールドメイン**は必ず入れてください |
| Keycloak | `https://<ホスト>/realms/<realm>` | |
| Authentik | `https://<ホスト>/application/o/<アプリのスラッグ>/` | 末尾のスラッシュは Authentik の表示どおりに残します |
| Dex | Dex の設定の `issuer` | |

## 誰が入れるか

プロバイダーでサインインすると、Telepy は次の順でアカウントを決めます。

1. **連携済み**：前回と同じ Telepy アカウント。メールアドレスは変わりうるので、プロバイダーの固定のユーザー ID（`sub`）で探します。
2. **確認済みメールで連携**（既定はオフ）：同じメールアドレスの既存アカウント。ただしプロバイダーがそのメールを確認済みと示した場合だけです。自組織で運用しているプロバイダーでのみオンにしてください。そこでメールアドレスを持つ人が、そのアドレスの Telepy アカウント（管理者も含む）を使えるようになります。
3. **初回サインインでアカウントを作成**（既定はオン）：メールの `@` の前、または `preferred_username` から名前を付けて新規作成します。その名前が使われていれば、推測はせずに理由を示して拒否します。
4. それ以外は入れません。既存アカウントは本人が連携します（次の節）。

**許可するメールドメイン**（既定は空欄）は、そのプロバイダー経由のすべてのサインインに適用され、既存アカウントも対象です。プロバイダーが自組織の人しか通さないなら空欄で構いません。誰でも通す場合（Google、マルチテナントの Entra アプリ）は入れてください。

プロバイダーの「アカウントを作成」は、その上にある「登録」設定とは関係ありません。「登録」はパスワードでの登録と Google サインインを対象にしています。

アカウントが決まったあとはいつもどおりです。無効なアカウントは入れず、2 段階認証のあるアカウントはパスキーかコードを求められます。プロバイダー自身の MFA はその前に、プロバイダー側で行われます。つまり MFA が 2 回になることがあります。Telepy は 1 回も聞かないよりは 2 回聞く方を選びます。

## グループとロール

プロバイダーは、誰がどのチームにいるかをすでに知っています。Telepy はそれをプロバイダー設定の**グループとロール**で使えます。

- **サインインできるグループ**：指定したどのグループにも入っていない人は、このプロバイダーのボタンで入れません。空欄 = プロバイダーが通した人すべて。
- **グループ → Telepy のロール**：プロバイダーのグループで、**管理者**にしたり、Telepy の**組織グループ**（ユーザーとアクセス → 組織グループにあるもの。その機能ルールで、ターミナル、ファイル、リモートデスクトップなどを誰が使えるかが決まります）に入れたりできます。同じロールを指すルールは複数あってもよく、所属するすべてのグループのロールが付きます。

ルールはそのプロバイダーでサインインするたびに適用され、次の決まりがあります。

- グループ名は大文字・小文字を含めて完全一致で照合します。
- Telepy が外すのは**このプロバイダーが付与したもの**だけです。管理者が手動で付けたメンバーシップや管理者権限は、プロバイダー側で対応するグループから外れても残ります。
- ID トークンにグループのクレームがまったくない場合は、その人によります。プロバイダーが以前その人に何かを与えていれば、クレームは設定済みなので、ないことは今どのグループにもいないことを意味します（Keycloak と Entra ID はグループがない人ではクレームごと省きます）。そのため、プロバイダーが与えたものを外します。一度も与えていなければ何も変えません。「どのグループにもいない」と「グループを送る設定がない」を区別できないため、推測しません。クレームがあって空の場合は、常に「どのグループにもいない」という意味です。
- 最後の有効な管理者は降格しないので、管理者がいないサイトにはなりません。
- ロールの適用後も、その人自身の Telepy の 2 段階認証は通常どおり求められます。

機能の権限ページでは、プロバイダーから来たメンバーと管理者にビルのアイコンが付きます。そこで外しても次のサインインまでしか続かないので、変更はプロバイダー側のグループで行ってください。**テストサインイン**では、実際に変わる前に、プロバイダーが送ったグループと変わる内容を確認できます。

### プロバイダーごとのグループの送り方

| プロバイダー | グループのクレーム | 設定すること |
| --- | --- | --- |
| Okta | `groups` | アプリ（または認可サーバー）に groups クレームを追加し、「telepy- で始まる」などのフィルターを付けます |
| Microsoft Entra ID | `groups` または `roles` | `groups` は名前ではなくオブジェクト ID を送ります。アプリロール（`roles`）のほうが読みやすいことが多いです |
| Google Workspace | | Google の ID トークンにはグループがありません。許可するメールドメインを使ってください |
| Keycloak | `groups` または `realm_access.roles` | Group Membership マッパー（クレーム名 `groups`、フルパスはオフ）を追加するか、レルムロールを使います |
| Authentik | `groups` | `profile` スコープと一緒に送られます |
| Dex | `groups` | スコープに `groups` を追加します |

## トンネルをグループと共有する

グループでトンネルを開くこともできます。トンネルの共有ダイアログの**グループ**タブで、グループと共有できます。権限、メンバーがログインできるアカウント、期限（任意）は、人と共有するときと同じです。グループの全員がそれぞれ自分の共有としてトンネルを使えるようになり、グループに従います。入った人は使えるようになり、抜けた人は使えなくなって開いているセッションも終了します。シングルサインオンのルールと SCIM が組織グループをプロバイダーと同期するので、結果として ID プロバイダーのグループが、誰がどのトンネルを使えるかを決めます。

グループには二種類あります。

- **組織グループ**は管理者、シングルサインオンのルール、SCIM が管理し、機能ルールを持ちます。管理者が「ユーザーとアクセス → 組織グループ」で**共有できる**をオンにして初めて共有ダイアログに出るので、機能ルールのために作ったグループ（ターミナルを使わせない外部委託先など）が皆に見えることはありません。オフにすると、そのグループへのトンネル共有はすべて終了します。その前に、またメンバーの変更や削除の前にも、誰がどのトンネルを得る・失うかがページに表示されます。
- **個人グループ**は、トンネルを共有できる人が**グループ**タブで自分で作るものです。作った本人にしか見えず、誰の機能も変えません。個人グループへの共有は、作った人がまだそのトンネルの所有者であるか、自分の共有か組織グループ経由で Admin を持っている間だけ有効です。そうでなくなると共有は一時停止し、状況が変わるまでメンバーはそこから何も得られません。Admin を失えば、共有したものも本当に止まります。

- **個別に共有した人はその共有が優先されます。** グループでは変わりません。**この人を個別に設定**で、グループ経由の共有を個別の共有に変えられます。
- **複数のグループは合算されます。** 共有された二つのグループに入っている人は、高いほうの権限、両方のすべてのアカウント、遅いほうの期限になります。
- **変更はグループで行います。** グループ経由の共有は一人ずつ取り消したり、変更したり、抜けたりできません。グループから外すか、グループの共有を変更・停止してください。アクセス申請はその上に重ねて使えます。
- 人との共有と同じく、グループと共有できるのはトンネルの所有者と Admin だけです。変更はすべてトンネルの**ログ**に残ります。

## 既存アカウントとの連携

誰でも**環境設定 → セキュリティ → シングルサインオン**で自分のアカウントを連携できます。

1. プロバイダーの横の**連携**を押します。2 段階認証があるアカウントは、先に本人確認をします。
2. プロバイダーでサインインします。戻ると、連携が完了したことを示すページが表示されます。

以後、そのプロバイダーのボタンでこのアカウントにサインインできます。**連携を解除**も同じ確認のあとで行えます。最後のサインイン方法は外せません。先にパスワード、パスキー、または別の連携を残してください。

## コマンドライン

`telepy login` はブラウザーでサインインします。ブラウザーがまだ Telepy にサインインしていない場合、そのサインインページにも同じシングルサインオンのボタンが出るので、CLI は追加設定なしでシングルサインオンを使えます。

## サインアウト

既定では、Telepy からのサインアウトは Telepy のサインインだけを終わらせます。プロバイダー側のセッションは残るので、次にボタンを押すとそのまま入れることがあります。両方を終わらせるには、プロバイダーの設定で**Telepy からサインアウトするときにプロバイダーからもサインアウト**をオンにし、表示される**サインアウト後のリダイレクト URI**（`https://<telepy>/login`）をプロバイダーに登録します。Okta では sign-out redirect URI、Keycloak では valid post logout redirect URI、Entra ではアプリのリダイレクト URI と呼ばれます。

その後サインアウトを押すと、Telepy はこのサインインの ID トークンをヒントとしてブラウザーをプロバイダーのサインアウトページへ送り、プロバイダーが Telepy のサインインページに戻します。これは本人がサインアウトしたときだけです。管理者や別の端末によるサインアウト、期限切れでは、プロバイダーへは行きません。サインアウトのエンドポイントを公開していないプロバイダー（Google など）では、Telepy からのみサインアウトします。**確認**ボタンで、使っているプロバイダーにあるかどうかがわかります。

## プロバイダーによるアカウント作成（SCIM）

SCIM がなければ、シングルサインオンは最初のサインイン時にアカウントを作ります。SCIM を使うと、プロバイダーがその前からアカウントを管理します。アカウントの作成、名前とメールアドレスの更新、退職した人の無効化、グループの同期です。Okta と Microsoft Entra ID はどちらも対応しています。

オンにするには、**サイト設定 → サインイン → シングルサインオン**でプロバイダーを開き、**プロビジョニング（SCIM）**タブで**トークンを作成**を押します。トークンはすぐにコピーしてください。Telepy はハッシュしか保存しないため、二度と表示されません。次に、ベース URL `https://<telepy>/api/scim/v2` とトークンをプロバイダーに渡します。

| プロバイダー | 場所 | ベース URL の入力先 | トークンの入力先 |
| --- | --- | --- | --- |
| Okta | アプリ → General → Provisioning で SCIM、次に Provisioning → Integration | SCIM connector base URL（unique identifier field は `userName`、push new users・profile updates・groups にチェック） | Authentication mode は HTTP Header |
| Microsoft Entra ID | エンタープライズ アプリケーション → プロビジョニング → 自動 | テナントの URL | シークレット トークン |

プロバイダーができること：

- **アカウントの作成。** ユーザー名は `userName` の `@` より前の部分で、シングルサインオンのユーザー名と同じように整えます。同じユーザー名のアカウントが既にある場合は引き継ぎません。プロバイダーには競合が返り、どうするかはあなたが決めます。
- **アカウントの変更。** 名前とメールアドレスはプロバイダーに従います。
- **アカウントの無効化。** `active: false` はここでアカウントを無効化するのと同じです。Web のサインインと実行中のセッションが終了し、MCP エージェントのセッションが閉じ、Telepy が入れた鍵はデバイスから外れます。再び有効にすればアクセスが戻ります。最後の有効な管理者は無効化されません。
- **アカウントの削除。** 削除はアカウントを消さずに無効化するので、録画・ログ・トンネルは残ります。後でプロバイダーが同じ人を作成し直すと、同じアカウントが戻ります。
- **グループの送信。** それぞれのグループが Telepy の組織グループ（**機能アクセス**で使うもの）になり、メンバーはプロバイダーが送った通りになります。ほかの新しい組織グループと同じく、管理者がオンにするまで共有には使えません。プロバイダーが作成していない人はそのグループから外されません。既存の Telepy グループと同じ名前は拒否され、プロバイダーが削除したグループはここでも削除されます。

プロバイダーが作成した人が初めてシングルサインオンでサインインすると、Telepy はそのサインインをその人のアカウント（メールアドレスかユーザー名が同じもの）に連携します。確認済みメールアドレスでの連携がオンかどうかは関係ありません。

トークンを作れるのは本人確認をした管理者だけです。**トークンを差し替え**ると古いものはすぐに使えなくなり、**オフにする**とプロビジョニングは止まりますが、作成されたアカウントとグループはすべて残ります。トークンが届くのは `/api/scim/v2` だけです。ユーザー一覧には、プロバイダーが管理しているアカウントに印が付きます。そのアカウントにここで加えた変更は、プロバイダーの次の同期で元に戻ることがあります。アカウントとグループの変更はすべて管理者の**監査ログ**に残ります。

## Telepy が確認すること

- **サインインは、それを始めたブラウザーに結び付けられます。** 最初に Telepy がブラウザーへ HttpOnly の Cookie を渡します。別のブラウザーで開いたコールバックのアドレス（誰かから送られてきたものなど）では、誰もサインインしません。
- **プロバイダーごとにコールバックのアドレスが別**なので、あるプロバイダー宛ての応答を別のプロバイダーのものとして使えません。
- **ID トークン**は、プロバイダーが公開している鍵（RSA、ECDSA、EdDSA。署名なしや HMAC のトークンは受け付けません）で署名され、issuer・audience・期限・このサインインの nonce が一致している必要があります。
- **すべて 1 回限りです。** state、コード、最後にブラウザーが受け取るチケットは、どれも数分以内に 1 回だけ使えます。
- クライアントシークレットは `SECRET_KEY` で暗号化して保存し、保存後に表示することはありません。

プロバイダーの変更、連携と解除はすべて管理エリアの**監査ログ**に残ります。サインインは各自のサインイン履歴に「シングルサインオン」として表示されます。

## うまくいかないとき

| ページの表示 | よくある原因 |
| --- | --- |
| このサインインに連携した Telepy アカウントはまだありません | アカウント作成がオフで、本人もまだ連携していません。別の方法でサインインして連携してもらうか、アカウント作成をオンにします |
| 同じユーザー名の Telepy アカウントがすでにあります | そのユーザー名は使われています。そのアカウントでサインインしてプロバイダーを連携してもらいます |
| このメールドメインのアカウントはここではサインインできません | メールが**許可するメールドメイン**にありません |
| サインインを始めたのと同じブラウザで完了してください | Cookie が失われました。別のブラウザー、閉じたプライベートウィンドウ、このサイトの Cookie のブロックなど |
| シングルサインオンに失敗しました | 多いのはクライアントシークレット、リダイレクト URI、時計のずれです。バックエンドのログ（`[OIDC]` の行）に原因が出ます |
| プロバイダーがリクエストを拒否しました | プロバイダー側の Telepy 用設定です。リダイレクト URI、許可スコープ、またはこの人がアプリに割り当てられていない |
| このサインイン方法は特定のグループだけを通しますが、プロバイダーからあなたのグループが届いていません | **サインインできるグループ**が設定されていますが、ID トークンにグループのクレームがありません。多くの場合、その人がどのグループにも入っていません（Keycloak と Entra ID はそのときクレームを省きます）。そうでなければクレーム名か、プロバイダー側のグループ設定を確認してください |
| プロバイダーでの所属グループでは、ここにサインインできません | 指定したどのグループにも入っていません |

それ以外は、まず**テストサインイン**を実行してください。プロバイダーが送ってきた内容がそのまま表示されます。
